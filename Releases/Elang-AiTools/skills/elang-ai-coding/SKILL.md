### 1. 易语言原生**不支持 Unicode**

易语言的「文本型」内部就是 **ANSI 字节流**（中文 Windows 上即 GBK），不是 Unicode：

- 一个汉字占 **2 字节**，一个 ASCII 字符占 **1 字节**。
- emoji / Unicode 符号 / 日韩文在原生文本型里**根本表达不了**，硬塞进去就是乱码或问号。
- **别把 C# / Python / JS 里「字符串 = Unicode 码点序列」的直觉套过来。** 那套直觉在这门
  语言里几乎每一步都会踩坑。

### 2. 处理 Unicode 的标准姿势：转成 USC2

要用 UTF-8 / Unicode 数据，走精易模块这套**编码转换链**，把内容变成纯 ASCII 的
`\uXXXX` 转义文本（USC2）—— 变 ASCII 之后，易语言原生文本函数才 hold 得住：

| 精易模块命令 | 参数（名称, 类型） | 返回 | 备注（源码原文） |
|---|---|---|---|
| `编码_Utf8到Unicode` | `utf8字节集, 字节集` | **字节集**（UTF-16LE） | 将UTF8数据转换到Unicode |
| `编码_Unicode到usc2` | `欲转换的Unicode, 字节集`<br>`不转换字母和数字, 逻辑型, 可空`<br>`不转换标点符号, 逻辑型, 可空` | **文本型** | `{ 61, 216, 37, 221, … }` => `\uD83D\uDD25\uD83D\uDCE6` |
| `编码_usc2到Unicode` | `欲转换的文本, 文本型` | **字节集**（UTF-16LE + 结束0） | `\uD83D\uDD25\uD83D\uDCE6` => `{ 61, 216, 37, 221, … }` |
| `编码_Unicode到Utf8` | `Unicode字节集, 字节集` | **字节集** | 将Unicode转换到UTF8 |
| `编码_Utf8到Ansi` | `utf8, 字节集` | **文本型** | 由 shituo 优化（UTF-8 → GBK） |
| `编码_Ansi到Utf8` | `参数_ansi文本, 文本型` | **字节集** | 由 shituo 优化（GBK → UTF-8） |
| `编码_Unicode到Ansi` | `Unicode, 字节集` | **文本型** | 将Unicode码转换为Ansi码；成功返回转换后的文本； |
| `编码_Ansi到Unicode` | `Ansi, 文本型`<br>`非标准Unicode编码, 逻辑型, 可空` | **字节集** | 将Ansi码转换为Unicode码；成功返回转换后的字节集； |

**注意参数类型**：`编码_Utf8到Unicode` 收的是**字节集**、还的是**字节集**（UTF-16LE），
不是文本型；`编码_Unicode到usc2` 收的也是**字节集**。链路是

```
局_UTF16 ＝ 编码_Utf8到Unicode (UTF8字节集)          ' UTF-8  → UTF-16 字节集
局_USC2  ＝ 编码_Unicode到usc2 (局_UTF16, 真, 真)     ' UTF-16 → 纯 ASCII 的 \uXXXX 文本
'   ……这一层全是 ASCII，随便用原生文本函数查找/判断/替换……
局_UTF16 ＝ 编码_usc2到Unicode (局_USC2)              ' 转回 UTF-16
局_UTF8  ＝ 编码_Unicode到Utf8 (局_UTF16)             ' 再转回 UTF-8 写出
```

USC2 长这样：

- `❤️`（U+2764 + U+FE0F）→ `\u2764\uFE0F`
- `🔥📦` → `\uD83D\uDD25\uD83D\uDCE6`

⚠️ **是「UTF-16 码元」，不是「码点」。** `编码_Unicode到usc2` 内部逐 2 字节取一个 16 位值、
用 `sprintf("\u%04X", 值)` 拼出来，所以**增补平面字符（emoji 等）会输出成一串代理对的
两个 `\uXXXX`**，`🔥` 是 `\uD83D\uDD25` 而**不是** `\U0001F525`。反向 `编码_usc2到Unicode`
也按同一规则还原，两边是自洽的 —— 但你要是按「一个 emoji ＝ 一个 `\uXXXX`」去数长度，
就会错。

⚠️ **精易模块不是支持库，是 `.ec` 易模块。** 它不在 `lib\*.fne` 里，所以
`导出支持库文档.exe` **查不到它**（导出的全是支持库，`编码_*` / `文本_*` 一条都没有）。
要它函数的真实签名和备注，只能拿 `.ec`（或它的 `.e` 源码）走 e2txt 转文本再检索 ——
做法见正文 §4（「查支持库命令」）。

### 3. ⚠️ `取文本长度` 数的是**字节**，中文一个字算 2

`取文本长度`（系统核心支持库 `krnln`，英文名 `len`）的备注只有一句
「取文本型数据的长度，不包含结束0」—— **它压根没提中文算 2**，但事实就是如此：
返回的是 ANSI/GBK **字节数**。

```
“你好！HelloAbcd”
 中文字符 3 个（你 / 好 / ！，全角叹号也算“中文”）  → 3 × 2 ＝ 6
 英文字符 9 个（HelloAbcd）                       → 9 × 1 ＝ 9
 取文本长度 ＝ 6 ＋ 9 ＝ 15
```

`15` **不是字符数**（字符数是 `12`），也不是任何 UI 上看到的宽度。后果很实在：

- 拿它当循环上界去 `取文本中间 (文本, i, 2)`：纯中文恰好对，**混进英文就整体错位**。
- 用 `取文本中间 (文本, 位置, 1)` 取「一个字符」：中文会被**劈成半个汉字**（乱码）。
- 拿它算显示宽度、算截断、算编辑框容量：中文会被算成两倍。

正确姿势是**全程按字节走**。精易模块自己写 `文本_取声母` 就是这么干的（源码原文）：

```
.计次循环首 (取文本长度 (欲变换的文本), 循环次数)
    …
    取文本中间 (欲变换的文本, 循环次数 × 2 － 1, 2)      ' 起点 = i×2-1，宽度 = 2
```

注意它先把文本 `到全角 (…)` 过了一遍 —— 全角化之后每个字符都占 2 字节，
`i × 2 － 1` 这个「字节起点」公式才成立。**这就是按字节操作中文的标准模板。**

### 4. ⚠️ 别的模块的「取长度」可能按**字符**算 —— 必须先看备注

同一个精易模块里就有四个**语义各不相同**的取长度函数：

| 函数 | 归属 | 备注（源码原文） | 实际口径 |
|---|---|---|---|
| `取文本长度` | 核心库 `krnln` | 取文本型数据的长度，不包含结束0 | **ANSI/GBK 字节数**，中文 2 |
| `文本_取长度ex` | 精易模块 | **全角汉字字符算一个长度** | **字符数**，中文 1、英文 1、全角标点 1 |
| `文本_取长度W` | 精易模块 | 取一段文本的长度，中文和字母都算一个长度 | **UTF-16 码元数**（`lstrlenW`），emoji 算 2 |
| `类_快速文本.取长度` | 精易模块 | 取字符数,汉字算一个 | 字符数 |

`文本_取长度ex` 的实现就是一句话：`返回 (文本_取长度W (编码_Ansi到Unicode (文本)))`
—— 先转成 UTF-16 再数码元，所以「全角汉字算一个」是**真的**，它和 `取文本长度`
可以差出一倍。

> **纪律：永远不要假设两个「取长度」函数语义相同。**
> 用之前先查它的备注 / 说明；查不到就按「语焉不详」处理，宁可自己显式换算。
> 这正是「先查支持库文档再写代码」的最大理由（见正文 §4）。

### 5. 写这类代码时的硬规则（自查清单）

1. **要处理 emoji / 生僻字 / 非 GBK 字符 → 先转 USC2**，别在原生文本型上硬做。
2. **算长度前先确定口径**：字节数（`取文本长度`）｜字符数（精易 `文本_取长度ex`）｜
   显示宽度（没人帮你，得按全角/半角自己加权）。
3. **截取 / 定位 / 替换含中文的文本，索引一律按字节**：`取文本中间 (文本, 起点, 1)`
   里的 `1` 是「一个 ASCII 字符」，取一个汉字要写 `2`；起点也不能 `i ＋ 1` 递增，
   要按上一个字符实际占的字节数累加。
4. **不要用原生文本函数去截 emoji** —— 代理对是两段，从中间截断就是半个字符，
   写进文件就是坏编码。要么整段处理，要么先转 USC2 再按 6 个字符一组切 `\uXXXX`。
5. 要**精确字符数**：`编码_Ansi到Unicode (文本)` → `文本_取长度W`（精易模块）是可靠口径。
6. **别凭记忆写命令名**。`编码_Utf8到Unicode` 的 `tf8` 是小写、`取文本长度` 在 `krnln`、
   `文本_取长度ex` 在精易模块 —— 这些都用正文 §4 的方法查出来再写。
7. 查到的重要备注（尤其是「全角算一个」这种反直觉的），**顺手写进代码注释**。

## 1. 写代码前：格式铁律

| 项 | 要求 |
|---|---|
| 首行 | `.版本 2` |
| 编码 / 行尾 | UTF-8 **带 BOM**、**CRLF**。⚠️ **整个文件必须统一** —— 混用（比如前几行 LF、后面 CRLF）会让 `t2e` **静默丢代码**：照样报 `SUCC`、`[错误] 0 条`，但子程序整段消失。用工具生成文本时最容易犯这个错 |
| 缩进 | **每层 4 个空格**，禁止 Tab |
| 程序集 / 子程序 / 程序集变量 | 顶格（0 空格） |
| 子程序内声明与语句 | 4 空格；块体 8；嵌套块体 12 |
| 子程序体内空行 | 写 **4 个空格**（子程序末尾那行例外，e2txt 会规范化成真空行） |
| 字符串 | 全角 `“ ”` |
| 运算符 | 全角 `＋ － × ÷ ％ ＝ ≠ ＞ ＜ ≥ ≤ 且 或 非` |
| **声明里的尺寸** | **半角**引号，如 `.局部变量 丙, 文本型, , "4"` |
| 命令调用 | `命令名 (参数1, 参数2)` —— 名字与括号间**有一个空格**；省略参数写 `, , ,` |
| 数组下标 | 半角方括号 `数组变量 [1]` |
| 注释 | `'` 开头 |

声明语法（**局部变量/程序集变量用「尺寸位」表示数组，不写 `数组` 两个字**；`数组` 是参数的写法）：

```
.子程序 <名>, <返回类型>, <公开?>, <备注?>
    .参数   <名>, <类型>, <参考?>, <可空?>, <备注?>
    .局部变量 <名>, <类型>, <静态?>, <数组尺寸?>, <备注?>
.程序集变量 <名>, <类型>, <静态?>, <数组尺寸?>, <备注?>

.局部变量 甲, 文本型                     ← 标量
.局部变量 乙, 整数型, 静态                ← 静态标量
.局部变量 丙, 文本型, , "0"               ← 数组（第 3 位留空，不能省逗号）
.参数 结果, 文本型, 参考 数组              ← 参数才有 `数组` 关键字
```

中间的空字段**必须保留** —— `.局部变量 丙, 文本型, , "0"` 里那个连续逗号少一个就变成别的字段了。

程序集文件后缀有语义：`xxx.static.e.txt` 标准程序集、`xxx.class.e.txt` 类程序集、`xxx.form.e.txt` 窗口程序集。

### 1.1 流程控制语句（**写错就不是「格式不好看」，是整个流程线崩坏**）

易语言的块语句全部是「**块首 + 块尾**」两条关键字成对出现，**块尾必须与块首同缩进**，
块体再比块首多 4 空格。缩进错一格不报错，但 IDE 里的流程线会串到别的块上去，整段代码作废。

五种常用结构（对照 C 系语言，**分支差异是重点**）：

| 易语言写法 | 对照 C / C++ | 有没有「失败分支」 |
|---|---|---|
| `.判断开始 (条件)` … `.判断 (条件)` … `.默认` … `.判断结束` | `if` / `else if`（可挂多个） / `else` | **有** —— `.默认` 就是 `else` |
| `.如果 (条件)` … `.否则` … `.如果结束` | `if` / `else` | **有** —— `.否则` 就是 `else` |
| `.如果真 (条件)` … `.如果真结束` | `if`（不带 else） | **没有** —— 只有「判断成功」一条路，条件不成立整块跳过 |
| `.判断循环首 (条件)` … `.判断循环尾 ()` | `while` | — |
| `.计次循环首 (次数, 变量)` … `.计次循环尾 ()` | `for (i = 1; i <= 次数; i++)` | — |

> ★★★ **「判断」的条件必须是逻辑型（布尔）—— 它是 `if / else if / else` 链，
> 不是 switch 那种「按值分派」。** 实测：`.判断开始 (整数变量)` 直接编译报错
> `错误(10044): 不能将 "整数型" 数据转换到 "逻辑型" 数据`。
> 所以 `.判断 (x ＝ 2)` 里的 `x ＝ 2` 是一条**独立的布尔条件**（x 等于 2 吗），
> 只在前面所有分支都不成立时才被求值 —— 语义上就是 C 的 `else if`。
> **千万别把 `.判断` 后面当成「与首行表达式比较的值」**（那是别的语言的 switch 语义，
> 易语言没有）；想按取值分派，就老老实实写若干条 `.判断 (x ＝ 1)`、`.判断 (x ＝ 2)`。

> ★ **「判断」与「如果」的流程线一模一样**：都是一条「判断成功」路 ＋ 一条「判断失败」路。
> 区别只有一点：「判断」可以在中间挂多个 `.判断 (条件)`（`else if`），「如果」只能有一个 `.否则`。
> 实际写代码时任选其一，别纠结哪个更「正统」。

> ★ `.计次循环首` 的循环变量从 **1** 数到 **次数**（不是 0 起）；不需要循环变量时可以整个留空：
> `.计次循环首 (10, )`（实测 IDE 原生就这么写，逗号后面留空即可）。

完整骨架（缩进每层 4 空格；注意 `.判断` 中间分支的写法）：

```
.判断开始 (a ＝ 1)                  ' 判断成功分支
    输出调试文本 (“a 是 1”)
.判断 (a ＝ 2)                      ' else if：前面不成立才求值这条布尔条件
    输出调试文本 (“a 是 2”)
.默认                                ' else：前面全不成立（可省略）
    输出调试文本 (“其它情况”)
.判断结束

.如果 (a ＝ 1)
    输出调试文本 (“a 是 1”)
.否则
    输出调试文本 (“a 不是 1”)
.如果结束

.如果真 (a ＝ 1)
    输出调试文本 (“a 是 1”)            ' 没有 else，条件不成立就整块跳过
.如果真结束

.判断循环首 (i ＜ 10)                    ' while：条件在**首**，可能一次都不执行
    i ＝ i ＋ 1
.判断循环尾 ()

.计次循环首 (10, i)                      ' for：i 从 1 数到 10（不是 0 起！）
    输出调试文本 (到文本 (i))
.计次循环尾 ()
```

**块尾带不带括号是一票否决式硬规则**，写错直接报错或崩流程线：

| 带空括号 `()` | 不带括号 |
|---|---|
| `.计次循环尾 ()`、`.判断循环尾 ()`、`.变量循环尾 ()`、`.循环判断尾 (条件)` | `.判断结束`、`.如果结束`、`.如果真结束` |

另两个不常用但确实存在的结构：

```
.变量循环首 (1, 100, 2, i)                ' for (i = 1; i <= 100; i += 2)
    ...
.变量循环尾 ()

.循环判断首 ()                            ' do { … } while (条件)：至少执行一次
    ...
.循环判断尾 (i ＜ 10)
```

循环体内可以用 `跳出循环 ()`（`break`）与 `到循环尾 ()`（`continue`）；
`返回 (值)` 会直接结束当前子程序。

**一段涵盖全部五种结构的示例**（缩进与空行都照抄；`.如果真` 嵌在 `.判断开始` 里就是 8 空格起）：

```
.子程序 流程演示
    .局部变量 甲, 逻辑型
    .局部变量 乙, 整数型

    甲 ＝ 真
    乙 ＝ 0
    
    ' 计次循环里嵌「如果真」和「判断」—— 三种结构混用最考缩进
    .计次循环首 (3, 乙)
        .如果真 (甲)
            输出调试文本 (“甲为真”)
        .如果真结束
        
        .判断开始 (乙 ＝ 1)
            输出调试文本 (“第一轮”)
        .判断 (乙 ＝ 2)
            输出调试文本 (“第二轮”)
        .默认
            输出调试文本 (“其它轮”)
        .判断结束
        
    .计次循环尾 ()
    
    ' 判断里嵌如果真，并且带着失败分支
    .判断开始 (甲)
        .如果真 (乙 ＞ 0)
            输出调试文本 (“甲为真且乙大于0”)
        .如果真结束
        
    .默认
        输出调试文本 (“甲为假”)
    .判断结束
    
    ' 「如果 / 否则」—— 流程线和「判断」完全一样
    .如果 (甲)
        输出调试文本 (“甲为真”)
    .否则
        输出调试文本 (“甲为假”)
    .如果结束
    
    ' 判断循环（while）
    .判断循环首 (乙 ＜ 3)
        乙 ＝ 乙 ＋ 1
    .判断循环尾 ()
```

#### ⚠️ 块尾后面紧接「另一条块语句」时，必须插一个空行

`.如果真结束` / `.如果结束` / `.判断结束` 这几个块尾在 IDE 里**不占行号**（只画一段流程线），
所以它们后面**紧挨着**另一条块语句时，两条块的流程线会连成一串、看不出谁在哪儿收尾：

```
        .如果真 (A)
            输出调试文本 (“a为真”)
        .如果真结束            ← 不占行号
        .判断开始 (B)          ← 紧跟着又开一个块，流程线串在一起
            ...
        .判断结束
    .计次循环尾 ()             ← 再紧跟外层块尾，彻底乱套
```

**在这两者之间插一个空行**即可，空行缩进 = **前面那个块尾的缩进**：

```
        .如果真 (A)
            输出调试文本 (“a为真”)
        .如果真结束
                                  ← 这一行写 8 个空格
        .判断开始 (B)
            ...
        .判断结束
                                  ← 同样 8 个空格
    .计次循环尾 ()
```

保险起见就统一成一条规则：**只要一个块尾后面还有下一条语句，就空一行**。
空行在 `.e` 里只是一条 19 字节的空表达式记录，多写无害，少写才会串线。

### 1.2 ⚠️ 「有迭代状态」的命令不能边循环边递归

支持库里有一类命令**内部记着迭代位置**，同一个子程序里连续调用会接着上次继续 ——
典型就是 `寻找文件`（英文名 `dir`）。它的备注原文写着：

> 「在某子程序中**第一次**调用本命令时，必须指定『欲寻找文件』参数……
> 在第一次调用以后如果想得到其它匹配的文件名，再一次调用本命令，且**不要提供**欲寻找文件名参数。」

那句「在**某子程序中**第一次调用」说明**迭代位置是记在子程序上的**。据此推断
（备注没有把递归场景写明）：在同一个子程序里一边用 `寻找文件` 遍历、一边递归进子目录，
内层的调用很可能把外层的迭代位置冲掉 —— 而这种错是**静默的**：漏项、提前结束，都不报错。

下面这种「先读完本层，再递归」的写法，**无论它内部实现是哪种口径都安全**，照这么写就行。

```
.局部变量 名称, 文本型
.局部变量 子目录表, 文本型, , "0"
.局部变量 属性, 整数型
.局部变量 i, 整数型

' ① 先把本层的【真子目录】全部收集完（循环自然结束 = 这条搜索已经走完，状态用不着了）
名称 ＝ 寻找文件 (目录路径 ＋ “\*”, 16)      ' 16 = #子目录；⚠ 返回的是全部条目，文件也在内
.判断循环首 (名称 ≠ “”)
    属性 ＝ 取文件属性 (目录路径 ＋ “\” ＋ 名称)
    .如果真 (属性 ≠ -1 且 位与 (属性, 16) ≠ 0)    ' -1 = 取属性失败，必须先排除
        加入成员 (子目录表, 名称)
    .如果真结束
    
    名称 ＝ 寻找文件 ()
.判断循环尾 ()

' ② 本层文件不需要下钻，边找边处理是安全的
名称 ＝ 寻找文件 (目录路径 ＋ “\*”, )
.判断循环首 (名称 ≠ “”)
    写文本行 (输出文件号, 名称)
    名称 ＝ 寻找文件 ()
.判断循环尾 ()

' ③ 到这里①的搜索已经结束，再递归才不会互相干扰
.计次循环首 (取数组成员数 (子目录表), i)
    列目录 (目录路径 ＋ “\” ＋ 子目录表 [i], 当前层 ＋ 1)
.计次循环尾 ()
```

同类「有状态」的命令要按同样思路处理（一次性读完再推进下一步），
别假定它们像纯函数那样每次调用都从头开始。

**`寻找文件` 的常用参数速查**（`krnln`）：

| 命令 | 说明 |
|---|---|
| `寻找文件 (路径 ＋ “\*”, 16)` | ⚠ 16 = `#子目录` **不是「只要子目录」**——实测它返回本层**全部条目**（文件也在内，只是把子目录也放进来）。要真目录必须再按 `取文件属性` 过滤；省略属性则默认「**除子目录外的所有文件**」（这条倒是真的只给文件） |
| `取文件属性 (路径)` | 返回属性整数，`位与 (属性, 16) ≠ 0` 即目录；**失败返回 -1**，而 `位与 (-1, 16) ≠ 0` 恒成立 —— 会把 `hiberfil.sys` 这类被系统独占的文件误判成目录，**必须先排除 -1** |
| `取文件尺寸 (路径)` | 字节数，不存在返回 -1 |
| `文件是否存在 (路径)` | 逻辑型，对目录也返回真 |
| `取运行目录 ()` / `取当前目录 ()` | 程序所在目录 / 进程当前目录 |
| `打开文件 (路径, #重写, )` → `写文本行 (文件号, 文本)` → `关闭文件 (文件号)` | 写文本文件的标准三步；`#重写` 会清空重建 |
| `取重复文本 (次数, 文本)` | 生成缩进用的重复串 |

## 2. 写完必须验证：双次往返收敛

**判据不是「原文 == 回读」**（e2txt 总会规范化空白），而是**收敛**：规范形再走一遍应逐字节不变。

```bash
<PY> "<SCRIPTS>/rtcheck.py" <文本目录>
```

### 2.5 echeck：不进 IDE 的静态语义检查（先跑这个，再跑 rtcheck）

`rtcheck` 只保证「格式对」，不保证「代码对」。`echeck.py` 用**和「导出支持库文档」同源的
`commands.jsonl`**（按本机已装支持库导出，库数与命令数取决于本机环境）对文本源码做静态检查，全程不需要易语言 IDE：

- **块结构**：判断/如果/如果真/四种循环 的 块首-块尾配对、缩进一致、`.判断`/`.默认`/`.否则` 是否挂在正确的块里、缺块尾 —— 这些正是流程线崩坏的根源。
- **命令调用**（含 `f (g (x))` 嵌套）：命令名是否存在于支持库清单；参数个数是否超界；少给/留空的位置是不是「可空」。
- **本工程子程序**：自动收集 `.子程序` 声明，调用时同样校验参数个数。

```bash
<PY> "<SCRIPTS>/echeck.py" <文本目录>              # --lib 可显式指 commands.jsonl
```

产物命令文档的位置：工作区根的 `支持库文档/commands.jsonl`（跑一次 `导出支持库文档.exe` 就有）；
找不到时会提示并跳过命令校验（块结构检查照常进行）。
**判读**：`✗ 错误` 必须修；`⚠ 警告` 逐条核对（「不在清单里」可能是自定义子程序，误报可忽略）。

注意 echeck 的边界：它是**静态检查**，替代不了 IDE 编译——类型转换错误（如把整数给 `判断开始`）
只有编译器能报。所以闭环是：`echeck（语义）→ rtcheck（格式）→ t2e → IDE 编译运行（终审）`。

输出解读：

- `★ 收敛检验 ✓` → 格式对了。
- `⚠️ 原文风格问题` → 逐条按第 1 节改。
- `数组位 ... 受影响声明 N 条` → **信息性，不用管**。`t2e` 产物本来就是这形态，原样交付即可；**不要**去清它（会出人命，见第 3 节）。
- `e2txt 规范化了你的原文 N 处` → 信息性。它会把 Tab 转 4 空格、把 `甲 = "x"` 转成 `甲 ＝ “x”`，但**别依赖容错**。

`rtcheck.py` 会按目录名自动判断命名风格（有 `代码/` 就当 NameStyle=2 处理），不用手动传 `-ns`。

## 3. ⚠️ 别去「修」`t2e` 产物里的变量数组位

`e2t` 把 `t2e` 产物读回来时，局部变量后面会多出一段 `, 数组`：

```
原文：  .局部变量 i, 整数型
回读：  .局部变量 i, 整数型, , , 数组        ← 看着像被污染了
```

**这不是缺陷，不要动它。** 实测更正（拿易语言 IDE 逐项验证过）：

| 流传的说法 | 事实 |
|---|---|
| 「GUI 产物干净、命令行产物脏」 | ❌ 错。同一份文本、同一时刻，两个可执行文件的 `t2e` 产物**逐字节完全相同** |
| 「把那个位清掉更干净」 | ❌ 错。清掉之后 **IDE 直接打不开该 `.e`** |
| 「原样交付能不能用」 | ✅ 能。IDE 打得开，编译运行都正常 |

- IDE 侧**不**把带该位的变量当数组（易语言的数组靠独立的**尺寸块**表达，跟这个标志位无关）。
  `e2t` 显示成 `, 数组` 只是它自己的解读口径。
- ⇒ **不要拿「回读文本干不干净」当质量判据。** 唯一的判据是：
  **用户能不能在 IDE 里打开它并编译运行。**
- ⇒ 本技能的标准做法就一句：**`t2e` 产出什么，就交付什么**，不做任何字节修补。

> 技能自带的 `efix.py` 留着当**读记录的工具**：`find_records()` 能按精确签名解析 `.e` 里的
> 变量 / 参数声明记录，分析字节结构时很有用。**它的 `apply`（清那个位）不要用于交付物。**
>
> 这条曾是本技能最容易搞错的地方，前后翻过两次车：最早说「t2e 通用缺陷」，后来改成
> 「只有命令行版有」，两次都错。**别再凭回读文本的观感下结论** —— 要下结论就进 IDE 验。

## 4. 查支持库命令：技能自带的单文件 exe

不要凭记忆写命令名 —— 支持库的命令名、参数、参数备注都能直接从本机导出来。

```
<ASSETS> 下的  导出支持库文档.exe      ← 32 位 Windows 单文件，零依赖，不需要 Python
```

它自动定位易语言安装目录（顺 `.e` 关联找 `e.exe`，多路注册表回退 + 常见路径兜底），
扫描 `lib\*.fne`，把结果写到 **当前工作目录**（不给输出目录时）。

```bash
"<ASSETS>/导出支持库文档.exe" -q                    # 静默，全自动 → 文档落在【当前目录】
"<ASSETS>/导出支持库文档.exe" <输出目录>             # 位置参数：写到指定目录
"<ASSETS>/导出支持库文档.exe" -o <输出目录>          # 同上（等价写法）
"<ASSETS>/导出支持库文档.exe" -l "<易语言目录>/lib"   # 手动指定支持库目录
"<ASSETS>/导出支持库文档.exe" --json | findstr /i 取文本   # 不落盘，直接检索
"<ASSETS>/导出支持库文档.exe" -h                    # 看用法
```

**推荐给 AI 的用法**（产物落在自己的临时目录，用完即删、不污染任何地方）：

```bash
mkdir -p /tmp/elib && cd /tmp/elib && "<ASSETS>/导出支持库文档.exe" -q
grep -i "取文本中间" commands.jsonl | head -3
```

`--json` 模式**只把 `commands.jsonl` 写到标准输出、不建目录不落盘**，
适合配合 `grep` / `findstr` 做一次性查询；被管道接走时输出是 UTF-8。
三种用法（无参数 → 当前目录、位置参数、`-o`）产物完全一致。

> 它是 **32 位 Windows 程序**（`.fne` 都是 32 位 DLL，导出它的程序必须同为 32 位）。
> 在 macOS / Linux 上跑不了 —— 那些平台上的支持库命令请查目标库自己的文档，
> 本技能其余部分（格式铁律、脚本、`.ec` 转文本查备注）照常可用。

产物（AI 直接读/搜）：

| 文件 | 内容 |
|---|---|
| `索引.md` | 库清单（标识/名称/版本/命令数/说明）+ 定位方式 + 统计 |
| `命令大全.md` | 全部命令，按库分节，一个文件看全 |
| `库/<库标识>.md` | 单库详情：命令名、英文名、返回值、**参数表**（参数名/类型/修饰/备注）、数据类型、常量 |
| `commands.jsonl` | 一行一条命令的 JSON，用 `grep` 检索最快 |

导出的库数与命令数**取决于你装了哪些支持库**（易语言自带的 + 你自己加的），全流程通常几秒内跑完。exe 是 32 位 C 写的，**源码不在包内**；真要改的话注意三点：必须用 32 位 gcc（`.fne` 是 32 位 DLL）；源码用 `-fexec-charset=UTF-8` 且路径另做 UTF-8→ACP 转换（Win32 文件 API 只认 ANSI）；**编译时要把 gcc 所在目录加进 `PATH`** —— 只给 gcc 全路径而不加 PATH，它会找不到自己的 `cc1`/`as`/`ld` 子程序，以 exit 1 **静默失败**（一行错误都不打印，表现为「脚本跑完但 exe 没更新」）。

> **控制台输出编码**：Windows 控制台默认代码页是 936(GBK)，程序内部是 UTF-8，**直接写字节会乱码**（「完成」→「瀹屾垚」）。本 exe 已处理：目标是控制台时转 UTF-16 走 `WriteConsoleW`（与代码页无关）；被重定向到文件/管道时按 UTF-8 原样输出。自己写类似工具时要照做，别只改 `-fexec-charset`。

支持库标识（`Key`）用于在代码里写 `.支持库 <key>`，例如系统核心支持库是 `krnln`、特殊功能支持库是 `spec`。

### ⚠️ 这个 exe 查不到**易模块（`.ec`）**

`*.fne` 是支持库，`*.ec` 是**易模块** —— 两回事。精易模块、NB模块、HP_Socket 这类都是 `.ec`，
**不在**上面导出的支持库清单里，所以 `编码_Utf8到Unicode`、`文本_取长度ex` 这些命令
`导出支持库文档.exe` **一条也查不到**。要精易模块的真实签名和备注，只有把模块本身转成文本：

```bash
# .ec 和 .e 都能转（优先用 .e 源码版，备注最全）
e2txt -mode e2t -src "<你的模块>.e" -dst "<临时目录>" -level 2 -enc UTF-8 -ns 2
#                 ↑ -src/-dst 都要绝对路径
grep -rn "^.子程序 编码_" "<临时目录>/代码/"          # 子程序名, 返回类型, 公开, 备注
grep -rn "^.子程序 文本_取长度" "<临时目录>/代码/"
```

易模块源码文本里，`.子程序 名字, 返回类型, 公开, 备注` 的**第 4 个字段就是函数备注**，
参数紧随其后（`.参数 名字, 类型, 参考?, 可空?, 备注?`）—— 所以这一招同时拿到
「签名 + 参数 + 备注」三样，和 exe 导出支持库文档是同一个信息量。

> ⚠ **务必把参数备注也读进去** —— 模块的调用约定（路径格式、哪个参数是「参考」接收）
> 往往只写在参数备注里，光看参数名看不出来。
> 另外：类方法在文本里写作 `对象.方法 (参数)`；`echeck` 会跳过这类调用
> （它们不在支持库清单里，无法静态校验）。
>
> 模块私有的约定**不要写进技能正文**（会误导不用该模块的人），
> 记在对应工程自己的文档里即可。

## 5. 产出「双击就能在 e2txt GUI 里打开」的项目

**机制**：GUI 双击 `.etprj` 时执行 `e2txt-gui.exe -prj "<项目文件>"`，它把**项目文件所在目录**当作「TXT转E」的文本目录。所以项目目录必须是这个形状：

```
<项目目录>/
├── 项目.etprj              项目描述（GUI 靠它定位；键集照抄 GUI 写的 14 个键）
├── 代码/                   ← 目录名必须是这个（NameStyle=2 中文命名风格）
│   ├── xxx.static.e.txt / xxx.class.e.txt / xxx.form.e.txt
│   └── 排序.list.txt        程序集顺序
├── 常量.e.txt
├── 配置/{支持库,用户,系统}.config.json
└── 代码.e                  生成好的 .e（t2e 产物）
```

一键生成：

```bash
<PY> "<SCRIPTS>/mkproj.py" "<项目目录>"          # 用内置示例初始化
<PY> "<SCRIPTS>/mkproj.py" "<项目目录>" --keep    # 已有 代码/ 时只补全配置与 etprj
```

生成后**双击 `<项目>\项目.etprj`** 即可在 GUI 打开，切到「TXT转E」点「生成」重新出 `.e`。

要点：

- **`项目.etprj` 必须是 GBK（无 BOM）+ CRLF**（`*.e.txt` / `*.config.json` 才是 UTF-8 带 BOM，两者不一样）。e2txt 读 etprj 走 ANSI，写成 UTF-8+BOM 会把 `EF BB BF` 塞到 `{` 前，JSON 解析失败 → **双击打不开**。GUI 和命令行写出来的 etprj 都是 GBK，照抄。
- **etprj 要在 `t2e` 跑完后再写**。命令行 `t2e` 会把 `<项目目录>\项目.etprj` 重写成只剩 4 个 `TXT2E-*` 键（`E2TXT-*` 那批全丢，`Dest` 被写成绝对路径）；先写会被冲掉。`mkproj.py` 已按此顺序做，并做「保留已有值 + 补齐缺失键」的合并。
- 键值以 GUI 自己写的为准：14 个键、`Dest`/`TXT2E-EFile` 留空、`Source` 是**相对项目目录**指向 `.e` 的路径（`.e` 在项目目录内就是 `代码.e`，在上一级就是 `../xx.e`）。
- `mkproj.py` 生成的 `代码.e` **原样交付**，不做任何字节修补。它留了个 `--fix` 开关能走旧的「清数组位」流程，但**实测清过之后 IDE 打不开**，别用（见第 3 节）。
- 目录/文件名必须是中文风格（`代码/` `配置/` `常量.e.txt` `排序.list.txt`），对应命令行 `-ns 2`；不传 `-ns` 会得到英文风格（`class/` `config/` `const.e.txt`），GUI 不认。
- **要给工程追加支持库，改 `配置/支持库.config.json`（在 json 里追加一项），不要写 `.支持库` 行**（2026-09-21 受控实验，四组对照）：只改该 json → `t2e` 产物**变化**且二进制含该 key；只在 `代码/*.e.txt` 加一行顶格 `.支持库 <key>` → 产物**与基线逐字节相同**（换**已安装**的库也一样 ⇒ 与「库是否安装」无关，这条通道不通）。**验收 = 产物 `.e` 的 md5 变化 且 二进制里能找到该 key 的 ASCII**，两项都要过。
- 双击要真能打开，`.etprj` 的文件关联必须在命令里**带上 `-prj`**。出厂 / 部分安装方式写的关联只有 `"%1"`，缺 `-prj` 时 GUI 不知道文本目录在哪 → 双击打不开。两个办法：在 GUI 里点「设置 → 设置文件关联(*.etprj)」（它会自己写对），或手工把关联命令改成 `"…\e2txt-gui.exe" -prj "%1"`。

## 6. 标准工作流

```
1. e2txt -mode e2t -src 原文件.e -dst <临时文本目录> -level 2 -enc UTF-8 -ns 2
   → stdout 必须含 SUCC:（退出码恒为 0，不可信）
2. 读 <临时文本目录>/代码/*.e.txt 了解现有代码与命名风格
3. 改文本（严格按第 1 节格式）
4. 自检：<PY> "<SCRIPTS>/rtcheck.py" <临时文本目录>
   → 看「结论: ✓」；它报的「数组位 ... 受影响声明 N 条」是信息性的，别管（见第 3 节）
5. 写回：e2txt -mode t2e -src <临时文本目录> -dst <新文件.e> -enc UTF-8 -level 1 -ns 2
   （绝不覆盖原文件！dst 的父目录必须先存在）
6. 编译验证，两条路任选（编译能力见 `elang-build` 技能）：
   - **无头编译**（不需要人）：`elang-build` 技能的 `ecompile.py` 出原生 exe 并实测运行；或用 `elang-debug` 技能调试运行并实时抓 `输出调试文本`。
   - **人在场**：让用户在易语言 IDE 里打开 `<新文件.e>` 编译验证。
   两者都过了才算闭环——「能打开」只是下限（见第 3 节），能编译能跑才是验收。
```

**第 4 步之后不要再对 `.e` 做任何字节级「修补」**，原样交付。

**文本往返无损，字节层有损**（回写体积会变小，内部表会被重排）。回写产物只当参考，**永远不要覆盖原始 `.e`**。

## 7. 其它坑

- `-level` 默认 1，会丢空的 `const.e.txt` / `dll.e.txt` / `struct.e.txt` / `icon.ico`，**转文本一定要显式 `-level 2`**。
- **`-src` 用绝对路径**。传相对路径（如 `示例.代码/代码.e`）会报 `ERROR:来源文件不存在`；`-dst` 也一律给绝对路径。
- **`-dst` 的父目录必须先存在**，否则 `t2e` **静默不产出**（连 `[错误]` 都没有），只在 e2txt 自己目录下留一个同名空文件夹。写 `-dst` 前先 `mkdir`。
- `t2e` 还会在 **e2txt 自身目录**里建一个与「`-dst` 父目录名」同名的空目录。无害但会脏；`rtcheck.py` 与 `mkproj.py` 都已自动清理（只删空目录），手写命令行时记得看一眼。
- **etprj 是 GBK，其余文本/json 是 UTF-8 带 BOM** —— 两类文件编码不同，别统一处理（详见第 5 节）。
- `-log` 是开关参数，出现即开，且 `t2e` 时会把 `log/` 写进你的 **src 文本目录**，别加。
- 文本目录必须有 `代码/`（或 `class/`）和 `配置/`（或 `config/`），否则 `t2e` 出错。
- 文本里的 `.支持库 xxx` 行**对 `t2e` 不生效**（受控实验证实，见第 5 节）；**库表只走 `配置/支持库.config.json`**。`e2t` 回读时**任何文本文件里都不会出现 `.支持库` 行**，这是正常的，别当成丢失；也**不要**手工去补这一行。
- 需要读 `.e` 里的变量声明记录时，用 `efix.py` 里那套**带长度自洽校验的精确签名**（`find_records`）；**别用「猜偏移」的启发式扫描**，它会把字段整体错位（曾把 `整数参数` 读成 `字节型`），据此得出的结论全不可信。
