# 易语言无头编译与构建验证

> 三技能分工：`elang-ai-coding` 管「写对代码」，`e2txt-cli` 管「.e ⇄ 文本」，`elang-debug` 管「调试运行 + 抓调试输出」，**本技能管「编译成原生产物」**。
>
> 路径占位符：`<SCRIPTS>` = 本技能目录下 `scripts`；`<PY>` = `python`（3.9+，脚本零第三方依赖）。
> ⚠️ **本技能依赖 `elang-debug` 技能，两者必须同装**：`ecompile.py` 运行时要调用同套装 `elang-debug` 里的 `mkcage.py` / `elaunch.py` / `elang_addin.fne`。定位顺序是「本技能根 → 同级技能目录 → `~/.agents/skills/`」；**单独把本技能的 zip 装进一台没有 `elang-debug` 的机器会缺件失败**。装完先自检：`<PY> "<SCRIPTS>/ecompile.py" --doctor`（缺什么会直接列出来）。

## 0. 原理一句话

易语言官方 SDK 暴露了整套编译功能号（`PublicIDEFunctions.h`，`FNST_RUN` 家族）：`FN_COMPILE_STATIC(0x05020007)`＝静态编译、`FN_STATIC_COMPILE_WINDOWS_EXE(0x05020011)`、`FN_STATIC_COMPILE_WINDOWS_CONOLE_EXE(0x05020012)`、`FN_STATIC_COMPILE_WINDOWS_DLL(0x05020013)` 等。本套装的宿主支持库 `elang_addin.fne`（`elang-debug` 技能自带，源码在 `src/addin/`）被加壳登记进工程后，会在 IDE 进程内收到通知并**代为触发这些功能号**——同一机制也驱动着 `elang-debug` 的「调试运行」。触发后 IDE 会弹「请输入欲编译到的可执行文件名：」保存对话框，宿主库在**同进程内**自动填入期望产物路径并确认（模态对话框会阻塞触发线程，因此填充在独立线程完成——这是实测踩出来的关键点）。

## 1. 一条命令：`ecompile.py`

```bash
<PY> "<SCRIPTS>/ecompile.py" 原始.e 输出.exe                     # 默认 static_console
<PY> "<SCRIPTS>/ecompile.py" 原始.e 输出.exe --kind static_exe
<PY> "<SCRIPTS>/ecompile.py" 工程文本目录 输出.exe               # 目录输入自动 t2e
<PY> "<SCRIPTS>/ecompile.py" 原始.e --check                     # 只判对错、不出产物（§3）
<PY> "<SCRIPTS>/ecompile.py" --doctor [--json]                   # 环境自检
```

- `--kind`：`static_console`（缺省，静态编译为控制台程序——**验证逻辑首选**）/ `static_exe` / `static_dll` / `static`（按工程当前类型）/ `exe` `console` `dll`（对应非静态编译）。
- **无头行为（默认）**：编译全程**不显示任何易语言窗口、不画一个像素**——`e.exe` 以 `SW_HIDE` 启动，宿主库在 IDE 进程内用「事件钩子 + 异步兜底轮询 + 透明斗篷」把包括「创建新项目」向导在内的所有窗口当场隐形（逐像素探针实测全程 0 像素差异）。想**亲眼看** IDE 过程排查问题：加 `--visible`（窗口正常显示，同平时开 IDE）。精细档位 `--headless {park,shide,hide,off}` 见 `elaunch.py --help`，`hide` 为默认。
- `--json` 契约：stdout 只放 JSON `{"ok":true,"status":"ok","output":"…","outputSize":N}`；失败 `status` ∈ `failed`（触发被拒 / 面板报错 / IDE 崩）/ `timeout`，附 `error`。退出码 0/2/3/4。
- 流程与红线（脚本内建）：输入**文本目录**先 t2e → `mkcage` 加壳（**绝不改原 .e**，产物放工作目录）→ 临时投放 `.fne` 到 lib\ → 独立 IDE 实例编译 → 监视期望产物（启动前先清旧产物，**绝不以旧产物判成功**）→ 精确 PID 收尾 → lib 还原 + 安装目录 diff 自证。
- ⚠️ **e2txt 会就地改写文本目录里的 `项目.etprj`**（那是它自己的配置缓存，每次转换都会把本轮的 `Dest`/`Level` 等写回去，等于把我们的临时路径写进用户工程）。脚本已内建**快照 + 还原**（连 mtime 一起还原；原本不存在而被新建的则删除），并在结果 JSON 里报 `inputRestored`。**直接用 `e2txt` 命令行时不享受这层保护**，自己注意这个副作用。
- ⚠️ **输入必须是原始 .e**。已加壳的 .e（库表已登记本套装宿主库）**无法再走 e2t**：该库没装在 IDE 的 `lib\` 里时，`e2t` 会报「加载支持库失败」且**不产出**文本目录。脚本在这一步会明确报错，换原始 .e 重跑即可。
- ⚠️ **前提**：静态编译要求本机 IDE 已配置过「静态编译链接器」。没配置过时，先在 IDE 里手动做一次静态编译完成初始配置（脚本 `--doctor` 会提示）。

## 2. 成功判据与排错

| 现象 | 判定 | 处置 |
|---|---|---|
| `status=ok` 且产物存在 | 成功 | 运行产物做行为验证（§3） |
| `status=failed` + 面板有 `错误(NNNN):` | 源码编译错误 | 读 logFile（UTF-8 视图）第一组根因 → 修源码 → 重跑 |
| `status=failed` + eExitCode=0xC0000005 | IDE 在报错路径上被第三方插件带崩（已知风险） | 同上修源码；崩溃不影响「未产出」判定 |
| `status=timeout` | 90~300 秒无产物 | 查 logFile；确认 IDE 能手动打开该工程、静态链接器已配置。**若日志里 `COMPILE-DIALOG fill+confirm` 反复出现**：那是保存框没被填进去/没被点掉（下面「保存框」小节有判读与修法），**不是**「偶发点了没生效、重跑就好」 |
| `error: 已经加壳过` | 输入是加壳产物 | 换原始 .e |

### 2.1 保存框：一个曾让编译「静默卡死」的坑（2026-09-24 定位并修复）

触发编译后 IDE 会弹「请输入欲编译到的可执行文件名：」。**这是 Vista 风格的公共保存框**
（内含 `DirectUIHWND` / `RebarWindow32` /徽章导航），它的**文件名编辑框是延迟创建的** ——
对话框刚出现的那一两秒里，`EnumChildWindows` 只能看到按钮和 `DirectUIHWND`，**一个编辑框都没有**。
此时若按「写第一个编辑框 + 点确定」去操作，等于**拿空文件名去存**：易语言会退回按工程名另存，
目标已存在就再弹一个「確認另存新檔」覆盖确认框；没人回答它，模态栈就永远不消，
触发线程的 `IdeRunFunc` **永不返回**，表现为编译一路卡到超时。

实测症状很好认：trace 里 `COMPILE-DIALOG fill+confirm` **反复出现上百次**（每次都以为填成功了），
而产物始终不出现。诊断办法：

```bash
ELANG_AI_DLG_ONLY=1 <PY> "<SCRIPTS>/ecompile.py" 工程 输出.exe --timeout 150
# 宿主库只扫描不填不点，把整个控件树打进 trace：
#   DLG-DUMP#1 hwnd=… edits=0 combos=0 btns=4      ← edits=0 就是上面说的延迟创建
#   id=1 cls=Button txt='存檔(&S)'                  ← 注意是繁中资源
```

修法（已在 `elang_addin.fne` 里实现，无需你操作）：

① 先收集**全部**候选编辑框（只收宽 ≥ 40 的），按**屏幕 y 从下往上**排 ——
**文件名框就是这个列表里最靠下的那个**。这个对话框的「保存位置（目录）」框与「文件名」框
**类名、控件号完全相同**，只能靠坐标区分（实测 `top`：地址栏 −31956 / 目录框 −31641 /
**文件名 −31619** / 按钮行 −31541）；
② 写到目标后**立即回读自证**，取不到文本就**拒绝点确定** —— 宁可超时，也不把产物写到别处。
（若候选编辑框的父是 `ComboBox`，要**连它的父一起写**：这种文件名框读的是 `ComboBox`
自己的文本，只改内层编辑框无效）；
③ 每轮先应答「另存新檔」覆盖确认框；
④ 确认改成 `WM_COMMAND(IDOK)` + `BM_CLICK` + 向输入框投 `VK_RETURN` 三连。

⚠️ **别拿 `CDM_GETFILEPATH` 当判据**：这个 Vista 风格对话框**不实现该消息**（恒返回空串），
用它会让填充逻辑**永不点击**、变成连续超时（已实测踩过）。只对支持 CDM 的对话框才用它加固。

实证：修后易模块**连跑 3 次，3/3** 都落在期望路径、尺寸恒为 `263,957 B`
（修复前约 50% 概率落到上一次用过的目录）。

**若你的 `elang-debug` 技能里的 `elang_addin.fne` 是 2026-09-24 之前的**，请更新该技能。

## 3. 只判对错、不出产物：`--check`（编译即检查）

**改完代码但还不想跑，可以用编译器当语法/语义裁判**——易语言编译的第一阶段就是整个工程的静态检查，**只有它全过了，编译器才会弹「请输入欲编译到的可执行文件名：」保存框**。所以「出现保存框」等价于「语法结构没问题」；脚本看到保存框就立刻按 PID 收尾，**等于你看到保存框时点『取消』**，不产出任何东西。

```bash
<PY> "<SCRIPTS>/ecompile.py" 新文件.e --check              # 权威路径：真编译 + 保存框判据（推荐）
<PY> "<SCRIPTS>/ecompile.py" 文本目录 --check              # 目录输入先自动 t2e
<PY> "<SCRIPTS>/ecompile.py" 新文件.e --check --fast       # 官方预编译 FN_PRE_COMPILE（⚠️ 见下）
```

| 结果 | 含义 |
|---|---|
| `status=syntax-ok` | 编译器静态检查全过（不运行、不出产物就能确定的判据） |
| `errors: ["错误(10022): …"]` | 有源码错误，原文直接给你（脚本从面板 UTF-8 视图里抽的） |
| `status=syntax-error`（无原文） | 面板报错但原文没落盘（见下「IDE 崩溃」） |
| `status=failed` + `eExitCode=0xC0000005` | IDE 在报错路径上被第三方插件带崩（已知风险）。**没误判成通过**，但错误原文会丢，需人工开 IDE 看 |
| `status=timeout` | 300 秒内既没保存框也没报错；查 logFile / 确认工程能手动打开 |

只有编译器能报、而文本层检查器（`echeck`）看不见的典型错误：

```
错误(10022): 子程序“_OnGuildPush”具有返回值定义，但实际上却没有返回数据或者并不是所有程序分支都返回了数据。
错误(10044): 不能将 "整数型" 数据转换到 "逻辑型" 数据
```

⚠️ **反过来也成立**：块结构崩坏（`'` 少一行、裸块尾）、缺块尾、不存在的命令，**编译器全都不报错**（照样编译成功）。所以 `--check` 必须和 `echeck` 一起用，两者互补，详见 `elang-ai-coding` 技能 §2.5 / §2.6。

⚠️ **`--fast`（官方预编译 `FN_PRE_COMPILE=0x02020070`）实测不可靠，不要单独当通过判据。** 它属于 `FNST_MODIFY`（`0x0202xxxx`）家族，只作用于「**当前编辑窗口**」；我们用 `e.exe <工程>` 打开却从不激活代码窗口，调用几乎空转，`BOOL*` 回参**恒为 TRUE**——对确定有问题的样本也一律返回成功。保留它只为「已激活窗口」的宿主场景，默认路径请用上面的权威模式。

工作目录（临时目录里的 `ecompile_<随机>`，放加壳副本 + 编译面板日志 + 运行轨迹）的**保留规则按「有没有值得回看的日志」判定**，与是否用 `--check` 无关：

| 情况 | 工作目录 | 路径是否写进结果 |
|---|---|---|
| 成功 | **删**（日志无回看价值） | — |
| 还没跑到编译器就失败（加壳/转换挂了） | **删**（原因已在 `error` 字段里） | — |
| 跑到了编译器才失败 | **保留** | `workdir` / `logUtf8`，里面有面板日志的 UTF-8 视图，可直接回看编译器原始输出 |

保留的目录**只留最近 10 个**，每次调用顺手清理更旧的（不会堆满 `%TEMP%`）。要固定位置就显式给 `--workdir`（给了就从不删）。

## 4. 编译期验证工作流（AI 排错闭环）

```
1. 写/改代码（elang-ai-coding 的格式铁律 + echeck/rtcheck）
2. ecompile.py --check  ← 先只判对错、不出产物（§3），省时间
3. ecompile.py 编译（--kind static_console 出控制台产物便于验证）
4. 失败 → 读 logFile 第一组根因 → 修 → 重跑（别叠补丁）
5. 成功 → 运行产物做行为验证：
     控制台验证：_启动子程序 里 标准输出 (1, "…")，产物直接跑收 stdout
                 （实测真编译器下 标准输出 工作正常；仅第一个参数须显式给 1/2）
     调试输出验证：elang-debug 技能（加壳 → 调试运行 → 实时抓 输出调试文本）
6. 涉及 UI/线程/网络/DLL 的改动：编译通过 ≠ 行为正确，补真实场景测试
```

**程序入口提醒**：工程里存在 `_启动窗口` 时它优先作为入口、`_启动子程序` 不会执行；编译验证前先确认入口归属（详见《程序入口与编译验证》）。

## 5. 红线（与全套装一致）

1. 绝不覆盖、不「修补」用户的原 `.e`；加壳副本与产物都放脚本自己的工作目录。
2. 绝不 `taskkill /F /IM e.exe`——只按本次启动的精确 PID 收尾（脚本内建）。
3. `D:\<易语言目录>\` 视为只读：只允许临时投放/移除 `lib\elang_addin.fne` 并 diff 自证（脚本内建）。
4. 技能/脚本不写任何本机绝对路径；外部依赖一律「怎么找」。
5. 机器码相关工程按《置入代码与机器码》核对（静态编译后端下 `置入代码` 已实测真实执行）；INT3 等调试字节不进交付物。
