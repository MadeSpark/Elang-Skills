# 加壳流程（给目标 `.e` 登记宿主支持库）

> 「加壳」= **不动用户的原 `.e`**，只产出一个「**库表里登记了宿主支持库**」的派生 `.e`，
> 使 `e.exe` 打开它时**按需加载**技能自带的 `elang_addin.fne`。这是本技能最确定、也最容易做错的一步。

## 1. 三步 + 验收点

| 步 | 动作 | 命令 / 要点 | 验收点 |
|---|---|---|---|
| 1 | 把**副本** `.e` 转成文本工程（**绝不改用户原 `.e`**） | `e2txt -mode e2t -src "<原名>.e" -dst "<临时文本目录>" -level 2 -enc UTF-8 -ns 2` | stdout 出现 `SUCC:`；文本目录含 `代码/`（或 `class/`）与 `配置/`（或 `config/`） |
| 2 | **在库表文件里追加本库一项** | 中文命名风格改 `配置/支持库.config.json`；英文命名风格改 `config/lib.config.json`。追加一项：`{"Key":"<key>","Guid":"<32位无连字符小写hex>","Name":"<库名>","Version":{"Major":1,"Minor":0},"CmdCount":0,"MaxRefConstPos":0,"MaxRefObjectPos":0}` | 该文件里**这一项存在**；**不要去改**代码文本里的 `.支持库` 行（无效） |
| 3 | 文本 → `.e`，命名 `<原名>_ai.e` | `e2txt -mode t2e -src "<临时文本目录>" -dst "<原名>_ai.e" -enc UTF-8 -level 2 -ns 2`（`-dst` 父目录**先存在**；**必须 `-level 2`**，`-level 1` 会**静默丢空产物**） | stdout 出现 `SUCC:`；**产出 `.e` 存在且非空** |
| ★ | **总验收（双判据，缺一不可）** | — | ① 产物 `.e` 的 **md5 ≠ 原 `.e`**；② 产物**二进制里能找到该 key 的 ASCII**。**任一项不过 = 加壳失败，不得进入下一步** |

## 2. 三个坑（均有实证）

### 坑 1（关键）：改的是**库表 JSON**，不是代码文本里的 `.支持库` 行

- **`配置/支持库.config.json`（英文风格 `config/lib.config.json`）是 `t2e` 的输入**，`t2e` 从这里读库表。
- **代码文本里写一行 `.支持库 <key>` 对 `t2e` 完全无效。**
  - 受控实验（四组，同源文本只改一处）：**只改库表 JSON** → 产物含该 key、md5 变化（**这才是输入**）；
    **只改代码文本那一行** → 产物与原 `.e` **逐字节相同**、不含该 key（**无效**）；同时改两者 → 结果同「只改 JSON」。
  - 为排除「因为该库没装所以文本被丢弃」这个解释：把文本行的 key 换成**一个确实已安装**的库，
    产物**仍与原件逐字节相同**、不含那个 key ⇒ 文本通道**不是**「被忽略」，而是**根本不参与** `t2e`。
- ⚠️ **一个常见的误判**：`e2t` 文本目录里自带的伴生 `.e`（形如 `代码/…` 或 `代码.e`）**不是 `t2e` 的产物**；
  `t2e` 只写到 `-dst` 指定的路径。**别拿那个伴生文件去论证加壳成功与否** —— 要看 `-dst` 目标文件的 md5 与内容。

### 坑 2：验收必须**双判据**

只用「md5 变了」不够。**判据是双判据：① 产物 md5 ≠ 原 `.e`，且 ② 产物二进制里含该 key 的 ASCII（例如 `elang_addin`）。**
两项都过才算成功；脚本要把这一步做成**硬校验、失败即报错退出**。

### 坑 3（顺序）：加壳后**不要再 `e2t`**

一个**声明了「当前没装的支持库」**的 `.e`，会让 `e2t` **失败**（stderr 报 `加载支持库失败！[名称] … [主键] …`），
**且不产出** `代码/*.e.txt`。所以正确顺序**必须**是：

```
先 e2t（此刻还没声明库）  →  改 库表 JSON  →  再 t2e
```

**加壳完成后绝不要再 `e2t`。**

## 3. `Key` / `Guid` 怎么取（**不写死具体值**）

| 项 | 取法 |
|---|---|
| `Key` | 本库 `.fne` 的**文件名主干**（例：`elang_addin.fne` → `elang_addin`）。 |
| `Guid` | **32 位无连字符、小写 hex**；必须与库自身 `LIB_INFO.m_szGuid` 一致。**从 `.fne` 里现取**：技能自带的 `assets/elang_addin.fne` 会被脚本 `LoadLibrary` + 调 `GetNewInf()` 读出它。 |
| `Name` | 库名（来自 `LIB_INFO.m_szName`）。 |
| `CmdCount` | 本宿主库**不对外暴露命令**，填 `0`。 |

> 技能里**不写死**任何具体 `Key` / `Guid` / 库名样例值 —— 一律「怎么取」。

## 4. 加壳脚本 (`scripts/mkcage.py`) 应做的事

1. 复制用户 `.e` 到临时区，**绝不改原文件**；
2. `e2t`（`-level 2`）转文本；
3. 改**库表 JSON**（追加本库一项，`Key`/`Guid` 按第 3 节现取）；
4. `t2e`（**`-level 2`**）产出 `<原名>_ai.e`；
5. **双判据校验**（md5 变化 **且** 二进制含 key ASCII）；任一不过 → 报错退出。

## 5. 真实工程实测基准（回答「大工程会不会加壳失败」）

对 7 个真实工程（约 0.66 ~ 3.9 MB：普通窗口工程、数据库管理、自绘 UI、OpenGL 向导，
其中 1 个**内嵌两个易模块 `.ec`**）批量实测 `e2t → t2e` 往返：

- 全部 `SUCC`，`[错误]` / `[警告]` 均为 0，无 `<?未知名称:支持库不存在?>` 占位；
- 体积偏差约 −0.2% ~ +1.1%；**内嵌模块的工程回写后小了约 13%** —— 那是 `t2e` 把模块区
  **重建得更紧凑**（日志里两个模块全部重新载入并写出），**不是内容丢失**；
- 两个代表工程（普通窗口工程 + 内嵌模块工程）加壳后走完整链路（`mkcage.py → elaunch.py`）：
  面板报「程序代码编译成功」（数十至数百 ms），真实跑出 `输出调试文本` 的业务行；
  一个自然结束（`ok`），一个被 `FN_END_RUN` 按时中断（`stopped`）。

**结论口径**：

1. **不需要**对「大工程」做禁用/降级；
2. **体积变化不是加壳验收判据**（验收只有双判据：md5 变化 + 含 key ASCII）；模块工程体积骤降属正常；
3. 真正要防的是**依赖缺失**：源工程引用了本机没装的支持库时，文本里会出现 `<?未知名称:支持库不存在?>`
   占位（`t2e` 加 `-log 真` 会打大量 `[错误]`，如 `未定义的常量`）—— 这类工程**原件在本机本来就编不过**，
   不是加壳引入的损失；链路会在编译阶段（面板报编译错误）暴露出来。
