# miniblink 模块（MbKit 宿主层版）—— 使用说明

> 版本：**2026-10-02（内嵌 MbKit v1.4.1 / 117,248 B）**
> 文件：`miniblink.e`（模块源码，可在易语言 IDE 里直接打开/编译）、`miniblink.ec`（已编译的易模块，
> **文件名必须叫 `miniblink.ec`** —— 易语言按文件名重写模块内部名，改名会让类的属主断裂）。
> 契约：内核（node.dll）由 MbKit 独占持有并常驻；业务模块（插件 DLL）可以随时卸载、重新载入。

**本版一共修掉四件事**（一手证据见 `docs/修复-miniblink启动期卡死（2026-10-01）.md`、
`work_mb/repro/` 下的截图与探针输出）：

| # | 问题 | 修法 |
|---|---|---|
| 1 | 宿主启动时自动载入插件 DLL → DLL 在 `_启动子程序`（DllMain/加载锁）里调 miniblink 会卡死宿主（旧版实测 10,015 ms / 60,000 ms，node.dll 永远起不来） | 初始化类调用（`WKE初始化` 等）**只登记、立即返回**（实测 0 ms）；真正的内核初始化推迟到第一个「确实要碰内核」的调用（`绑定`/`载入`）——那时已经不在加载锁里了 |
| 2 | 页面在宿主里**永远渲染不出来**（窗口空白、点什么都没反应、任务管理器才能关） | 内核属主 = **调用线程**（属主直通）：`LoadLibrary(node.dll)` + `wkeInitialize` 就在创建窗口的那个线程上做。旧的「常驻线程 K + 全调用编组」模式保留为逃生阀 `MBKIT_K=1`，但**窗口里渲染不了** |
| 3 | `WKE设置node路径` 第二次调用返回假 → 业务整段跳过绑定与载入 → 窗口空白 | 幂等：路径与已加载内核一致时返回**真**；真换内核才拒绝（并把原因写进第二个参数）。已加载内核常驻进程，换内核只能重启宿主 exe |
| 4 | 热重载：第二次 `绑定` 直接返回假，调用方拿到假仍继续 `载入` → 把 0 当 view 交给内核（崩/白屏） | `绑定` 改成**可重复调用**（先销毁旧浏览框再绑定本窗口）；载入 / 运行JS 家族 13 处补「视图为 0 直接返回」保护 |

> 还想强调一个**排查陷阱**：进程里若已有一份**别的版本**的宿主库（例如另一个插件带的旧版），
> 本模块的修复**根本不会生效**。所以宿主库的文件名改成了版本化的 **`MbKit141.dll`**
> （易语言 `.DLL命令` 声明的库名同步改成 `MbKit141.dll`）—— 详见第 5 节。

## 1. 怎么用（默认：什么都不用做）

```
你的程序目录\
├── 你的程序.exe
├── node.dll            ← 只放这里（或按第 6 节指定位置）
├── MbKit141.dll         ← 首次运行时从模块资源里自动释放出来（117 KB）
└── ...（模块会自动判断是否需要用新版本覆盖）
```

```易语言
.版本 2

.子程序 _启动子程序, 整数型
    ' ★ 这里就是 DllMain（加载锁内）：只能做「登记 / 投递」这类轻活。
    WKE初始化 ()                     ' 安全：只登记，不 LoadLibrary、不 wkeInitialize（0 ms）
    返回 (0)

.子程序 _AppStart, 整数型, 公开   ' 宿主调用「启用插件」时才做重活
    .局部变量 失败原因, 文本型
    ' WKE设置node路径 (“D:\我的内核\chromium_2021”, 失败原因)   ' 可选，必须在首次碰内核前
    载入 (设置窗口, , 假)
    图片框1.置大小 (...)             ' 该线程随后就成为内核属主线程
    mb.绑定 (图片框1.取窗口句柄 ())
    mb.载入 (“https://example.com/”)
    返回 (0)
```

两条时序要点：

* **`_启动子程序`（DllMain）里只能调「初始化类」**：`WKE初始化` / `WKE设置node路径` /
  `WKE载入宿主库` / `WKE卸载`。它们都只登记，不碰 node.dll。
* **第一次 `绑定` / `载入` 会做一次 350 ms 左右的初始化**（`LoadLibrary(node.dll)` +
  `wkeInitialize`），必须发生在**创建窗口/有消息循环的那个线程**上（框架的启用回调就是）。
  之后就都在 50 ms 级以内，页面开始渲染。

## 2. 公开命令

| 命令 | 返回 | 说明 |
|---|---|---|
| `WKE初始化 ()` | — | **非阻塞登记**：只保证「内核会在这条业务线程上被建起来」，不 LoadLibrary、不 wkeInitialize。DllMain 里可安全调用 |
| `WKE卸载 ()` | — | `wkeFinalize`（内核没起来时是无事可做；实测标志位不清，别拿它当「能否重来」的判据） |
| `WKE设置node路径 (路径, 失败原因)` | 逻辑型 | 目录或 `node.dll` 完整文件名；留空=默认（宿主程序根目录）。**必须在首次碰内核前调**。同一路径重复调返回**真**（幂等，热重载/重复启用安全）；真换内核才返回假并写原因。**内核常驻、换内核只能重启宿主** —— 设计行为，不是故障 |
| `WKE取node路径 ()` | 文本型 | 内核实际使用的完整路径（**会触发内核查找/加载**） |
| `WKE宿主自检 ()` | 文本型 | 一行式诊断：内核启动状态、内核状态/路径、**内核属主模式**、缺失导出、加载期错误、编组与回调计数。**排查先看它** |
| `WKE载入宿主库 ()` | 逻辑型 | 手工把内嵌 `MbKit141.dll` 释放+预载（一般不用调） |
| `WKE等待内核就绪 (超时毫秒)` | 逻辑型 | ★ 属主直通下「等待」= **现在就在本线程把内核建起来**（阻塞但正确，本线程从此是属主）；K 模式才是带泵等待。**别在 DllMain 里调它** |
| `WKE取内核启动状态 ()` | 整数型 | ★ `0`未启动 / `1`已登记(等首个内核调用) / `2`已完成 / `3`失败 |
| `WKE全解绑 ()` | 整数型 | ★ **热重载契约**：解绑并销毁本模块登记的全部浏览框（内核保持已初始化）。插件 DLL 被卸载前调一次 |
| `WKE取等待统计 ()` | 文本型 | ★ 诊断：编组等待期间抽掉的消息数 / 等待超时次数（属主直通下都是 0） |

`WKE宿主自检 ()` 的真实输出（宿主里跑出来的原文）：

```
MbKit 自检
  内核状态     : 已加载
  内核启动     : 已完成    等启动次数 0   编组等待抽消息 0 条   等待超时 0 次
  内核属主     : 线程 53712（属主直通（内核主线程=调用线程，可渲染））
  内核路径     : D:\...\框架-爱丽\main\corn\node.dll
  内核模块     : 0x78D80000
  自定义路径   : (未设置 → 默认: 宿主程序根目录)
  宿主程序目录 : D:\...\框架-爱丽
  当前工作目录 : D:\...\框架-爱丽
  内核缺失导出 : 4（其中被真正调用过 0 次）
  缺失清单     : JsBindGetter JsBindSetter wkeGetWebView wkeNetSetURL
  加载期错误   : (无)
  编组调用     : 共 27 次（跨线程 0，失败 0）
  回调登记     : 0 个（存活 0）  命中 0  被挡 0
```

判读：

| 现象 | 含义 / 处置 |
|---|---|
| `内核属主 : 属主直通（内核主线程=调用线程，可渲染）` | ✅ 正确状态，页面能渲染 |
| `内核属主 : K 模式…` | ❌ 走到了逃生阀（`MBKIT_K=1` 或**进程里有旧版宿主库抢了基名**）。页面渲染不出来 |
| `编组调用 …（跨线程 N>0）` / `编组等待抽消息 > 0` | ❌ 说明还在编组（K 模式）。属主直通下这些数应当恒为 0 |
| `内核启动 : 已登记`（状态 1） | 正常：还没人真正碰内核。等第一次 `绑定`/`载入` 就变「已完成」 |
| `等待超时 > 0` | 内核启动被挡住 —— **几乎一定是在 DllMain（`_启动子程序`）里做了碰内核的调用**：把 `绑定`/`载入` 挪到启用回调里 |
| 「★ 警告：进程里已载入另一份 MbKit141.dll…」 | 有插件带了**同名不同版本**的宿主库。本模块已用版本化文件名规避，出现即需统一版本 |
| `内核缺失导出: 4` | **正常**（`JsBindGetter/JsBindSetter/wkeGetWebView/wkeNetSetURL` 内核本来就没导出），已填安全桩，调用只返回 0 |
| 内核加载失败但程序没崩 | 刻意设计：**默认不弹框**（宿主启动期弹模态框 = 卡死），错误记在自检里；要看框设 `MBKIT_SHOW_ERRORBOX=1` |

## 3. 热重载

| 想要的结果 | 顺序 |
|---|---|
| 只换页面内容 | 直接 `载入`，不必卸载模块 |
| 换业务模块（改动大） | `WKE全解绑 ()`（或逐个 `销毁`）→ 卸载模块 → 载入新模块 → 重新 `绑定` |
| 同一个窗口上重新绑定（框架「重新加载插件」） | 直接再 `绑定 (窗口句柄)` —— 现在会**先销毁旧浏览框再重建**，可重复调用 |
| 连内核也要换 | 只能重启宿主 exe（内核被刻意钉住以保证稳定） |

## 4. 环境变量

| 变量 | 作用 |
|---|---|
| `MBKIT_K=1` | **逃生阀**：退回「常驻线程 K + 全调用编组」。离屏/无窗口场景可用，**窗口里渲染不出页面** |
| `MBKIT_PUMP=1` | 只在 K 模式下有意义（编组等待期间抽宿主消息）。属主直通下无用 |
| `MBKIT_SILENT=1` | 永不出框（无人值守/CI） |
| `MBKIT_SHOW_ERRORBOX=1` | 需要人工看错误框时才开（默认关） |
| `MBKIT_FATAL_EXIT=1` | 致命失败时 `ExitProcess(1)`（默认不退出，避免把宿主一起带走） |
| `MBKIT_STRICT=1` | 任何缺失导出都按致命处理（排查用） |

## 5. 两条硬规矩（踩过坑）

1. **不要把模块源码内联进 DLL 工程**。易语言 DLL 编译模式对「公开子程序 + 可空参数」有额外限制
   （实测报 `错误(10061) 被取地址的子程序"WkeA2W"的参数 2 不能具有"可空"标志`）。
   请与本项目现有插件一致：**导入 `miniblink.ec` 易模块**。
2. **宿主库基名是 `MbKit141.dll`，别改回 `MbKit.dll`，也别把版本号从文件名里去掉**。
   易语言 `.DLL命令` 声明的是库基名，Windows 对已载入模块**按基名命中、不看路径**：真实宿主里
   `AILI·LIFE.dll`（同一个 miniblink 模块的旧版本，内嵌 MbKit/1.2）加载顺序排在前面，
   会把 `MbKit.dll` 这个基名占掉 —— 之后本模块所有调用都走那份旧实现（表现为自检里
   「内核属主 = K 模式」、`WKE设置node路径` 返回假、页面空白）。版本化文件名让新旧模块可以同进程共存。
   **为什么版本号必须写进文件名**：模块判断磁盘上那份是不是本版本，靠的是「**尺寸一致**」
   （117 KB 的宿主库两次构建极易同尺寸 —— 实测 v1.4 与 v1.4.1 都是 117,248 B），
   于是旧的、DllMain 会死锁的那份被当成「同一版本」留在盘上，修好的永远不生效、还看不出异常。
   文件名带精确版本号后，新版一定是「文件不存在 → 释放 → 生效」。
   `work_mb/mk_modfixed.py` 已按内嵌宿主库的版本串自动生成这个文件名，重新构建时不用手改。

## 6. 内核（node.dll）查找顺序

未显式设置路径时，按下列顺序取**第一个命中**：

| # | 位置 |
|---|---|
| ① | `WKE设置node路径` 指定的（**设了没命中就明确报错，不静默回退**） |
| ② | `<宿主 exe 目录>\node.dll` ← 默认 |
| ③ | `<MbKit141.dll 目录>\node.dll` |
| ④ | 从宿主 exe 目录逐级上溯 ≤5 级：每级试 `\node.dll` 与 `\main\corn\node.dll` |
| ⑤ | `<当前工作目录>\node.dll` 与 `<当前工作目录>\main\corn\node.dll` |
| ⑥ | 裸名 `node.dll`（交系统搜索路径） |
