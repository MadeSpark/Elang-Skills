# 修复：无头编译隔离桌面与作业对象（v1.4.0，2026-11-14）

> 范围：`tools/elaunch.py`（elang-debug）、`tools/ecompile.py`（elang-build）。新增 `tools/selftest-isolation.py`。
> 起因：2026-11-14 01:45 前后，某次 AI 会话反复调用 `ecompile.py` 做无头编译，用户的键盘鼠标严重阻塞，操作时系统发出嘟嘟声。

## 1. 事故还原

会话日志（`session-e506041b…`）显示该会话 01:00–01:48 间反复启动无头编译：01:04、01:09、01:14、01:18、01:31、01:36 各一次，其中 5 次编译在途中被工具强制结束（01:06:35 / 01:12:10 / 01:13:34 / 01:38:08 以及前一晚 21:37:30），原因是工具调用时限（120 秒）短于 `ecompile` 自身的 300 秒超时。

01:36 那次 `--check` 的 trace 显示：e.exe 启动后主窗口过了约 73 秒才出现（正常不到 1 秒）；01:41–01:45 间 Windows 记录了 `SystemSettings.exe` 与 `ApplicationFrameHost.exe` 的“停止响应”事件（Application Hang 1002）。同时段另一个项目（MOSSS）的会话只在 01:27 与 01:34 各编译了一次 Arduino 固件，和本问题无关。

## 2. 对上一轮判断的更正

上一轮分析认为 `elang_addin.fne` 的窗口隐藏守护（HIDEGUARD）把系统里其他程序的窗口也隐藏了。**这是错的**：`elang_addin.cpp` 的 `CloakWindow`、`ActOnWindow` 改窗口前都会比对 PID，两个 `SetWinEventHook` 也按 `GetCurrentProcessId()` 过滤。trace 里的 `WorkerW`、`tooltips_class32`、`Menulwy` 等窗口是 e.exe 自己和它加载的 IDE 插件建的。

## 3. 根因（推断，无法事后逐项证实）

无头编译启动的是**完整的 e.exe**，会加载 iDraw / CeTools / eTools 等 IDE 插件。仓库里 2026-09-26/27 的两份专项报告已记录：这些插件装全局低级键鼠钩子（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`），e.exe 忙或被强杀时，系统每次输入都要等钩子超时（默认 300 ms）。另外，被设为透明但仍“可见”的 IDE 窗口/模态框可能抢走前台焦点，键盘输入进入看不见的对话框，因此嘟嘟响。

两条都无法在事后精确定罪，所以修复不依赖判断哪个插件是元凶：**让整个 e.exe 碰不到用户的真实桌面**。

## 4. 设计

`elaunch.IsolatedProcess`（纯 ctypes）：

- **私有隐藏桌面**：`CreateDesktopW` + `CreateProcessW(lpDesktop="WinSta0\<名>")`。低级钩子按桌面生效，挂在隐藏桌面上的钩子不在用户的输入链里。旧文档里“e.exe 在独立桌面 0.04 秒就退出”的结论复测不成立。
- **作业对象**：`KILL_ON_JOB_CLOSE`、`DIE_ON_UNHANDLED_EXCEPTION`；活动进程 ≤ 32；单进程内存 ≤ 3 GiB，整体 ≤ 4 GiB；CPU 硬上限（默认 50%，`JobObjectCpuRateControlInformation`）；BelowNormal；UI 限制 `DESKTOP|DISPLAYSETTINGS|EXITWINDOWS|SYSTEMPARAMETERS`。
- **只继承日志句柄**：用 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，e.exe 不继承上游管道，避免残留进程憋住上游的 `subprocess.run(capture_output)`。
- **看守进程**：脱离进程树，等 e.exe 退出后补删 `lib\elang_addin.fne`（elaunch 被强杀时 `finally` 不执行）。
- **降级链**：desktop → job + 窗口守护 → none，原因写入结果 JSON 的 `isolation.fallbackReason`。
- **desktop 模式不再启动窗口守护链**：传 `ELANG_AI_HIDE=0`，没有 TIME_CRITICAL 线程、0.5 ms 定时器精度和 3 ms 一轮的 `EnumWindows`。
- `--visible` / `--headless off|park` 自动用 `job`（窗口要显示在用户桌面）。

## 5. 验收（2026-11-14，本机 28 逻辑核）

`python tools/selftest-isolation.py --with-control`：

| 项 | 结果 |
|---|---|
| 1 钩子隔离 | 隐藏桌面里的“永不处理消息”键鼠钩子，主进程 SendInput 耗时 p50/p90 与基线持平（3.8/17.4 ms vs 4.1/22.8 ms） |
| 1c 对照 | 同一个卡死钩子放在真实桌面：SendInput 每次 314 ms（= 默认 300 ms 钩子超时） |
| 2 强杀安全 | 中间进程被 TerminateProcess，子进程 0.01 s 内消失 |
| 3 CPU 硬上限 | 设 25%，24 个满载进程，整机占用 25.4% |
| 4 内存上限 | 单进程上限 1024 MiB，申请 1536 MiB 得到 MemoryError |
| 5 UI 限制 | 子进程改系统参数、建桌面均失败（err=5） |

真实易语言 IDE（`D:\ides\e`）端到端：

- `ecompile --check`：demo 01、02 均 `syntax-ok`，`isolation.mode=desktop`，`activeAfterKill=0`；连续 3 次约 13–17 s。
- 真编译 `--kind static_console`：`status=ok`，产物 679936 B；链接器等子进程都在作业内（totalProcesses=4），收尾后 activeProcesses=0。
- 调试运行（mkcage + elaunch）：`status=ok`、`panelSeen=true`、`activeAfterKill=0`。
- `--check --visible`：`isolation.mode=job`，`syntax-ok`，收尾后 activeProcesses=0。
- **强杀场景**：编译进行到 9 秒时 `Stop-Process -Force` 杀 elaunch，1.5 秒内 e.exe 消失，`lib\elang_addin.fne` 同时被看守进程删除，无残留进程。

输入延迟（SendInput 耗时，20 ms 间隔注入零位移鼠标移动与 F24 按键）：

- 本机在**没有任何隔离编译**时就会出现 300 ms 级停顿（idle 60 s：p99 76.9 ms，max 320.7 ms，11:14:53–55 连续 7 次约 315 ms，是默认钩子超时的特征）。因此**原计划的“p99 < 50 ms、max < 150 ms”绝对阈值在本机基线上就达不到，没有采用**，改为与基线对比。
- 三次隔离编译期间（11:15:50–11:16:33，约 43 s）：没有一次 > 150 ms 的事件，仅一次 108 ms。该次监测中出现的 300 ms 级停顿簇在 11:15:45–11:15:50（编译开始前）和 11:16:48（编译结束后），与隔离编译无关。
- 这些背景停顿的来源本轮没有定位（候选：用户自己打开的易语言 IDE 里的 iDraw/CeTools 钩子、其他后台程序）。

## 6. 没有做的事与已知限制

- **没有重新编译 `elang_addin.fne`**。原计划把 `HidePollProc` 的 `Sleep(3)` 改成 50 ms，但用当前 msys2 工具链重编未改动的源码，得到的 sha256 与仓库里的不同（大小同为 101888 B），工具链已漂移，无法保证产物等价。desktop 模式不启动该线程，所以这项改动不是修复的必要部分。fne 保持不变。
- 作业对象管不住钩子，隔开键鼠靠隐藏桌面。`job` / `none` 模式下插件的低级钩子仍在用户输入链上，只建议排障时使用。
- 没有加 `JOB_OBJECT_UILIMIT_HANDLES`：它会让 IDE 不能访问作业外的 USER 对象，风险大于收益。剪贴板仍与用户共享（隐藏桌面不隔离剪贴板）。
- CPU 上限只对多线程/多进程负载有意义：e.exe 编译主要是单线程，50% 的整机上限不会拖慢它。
- 没有修改易语言安装目录里的插件，也没有改注册表。
