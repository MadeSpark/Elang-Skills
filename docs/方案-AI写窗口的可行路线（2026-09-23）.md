# 方案：让 AI 写「可视化可编辑」的窗口（2026-09-23）

> 背景：2048 项目死于「AI 手写 `窗口/_启动窗口.form.json` → 易语言 IDE 无法正确解析窗口」，
> 用户因此删掉整个项目。用户明确诉求：**我要的是可视化窗口编辑器** ——
> 上一轮给的 A（黑月界面类）/ B（纯 Win32）都是「代码搓窗口」，等于让用户放弃设计器，**方向错了**。
>
> 本文基于**本机新跑的一手实测**（不是推演），给出真正保留设计器的路线。

---

## 0. 结论速览

| # | 路线 | 窗口数据由谁写 | 用户还能拖控件吗 | 就绪度 |
|---|---|---|---|---|
| **F** | **契约分离**：AI 只写事件代码，骨架由设计器产出 | 设计器 | ✅ 完全能 | **今天可用** |
| **C** | **EPRG 剪贴板**：AI 造组件 → 插件写剪贴板 → 设计器粘贴 | 设计器（IDE 自己的序列化） | ✅ 完全能 | 需 1 次 PoC |
| **D** | **设计器命令族**：AI 发指令，IDE 执行对齐/等宽/居中 | 设计器 | ✅ 完全能（需先选中） | 需 1 次 PoC |
| **E** | **模板化 form.json**：AI 复制真实控件条目改属性 | AI（但用官方模板） | ✅ 能（待实测） | 需 1 次 PoC |
| **G** | **AI 预览稿**：先出 HTML/图片给用户看 → 再落盘 | AI | — | 纯前端，可加 |

**推荐组合：F（基线）+ C（AI 加组件的官方通道）+ D（AI 辅助排版）+ G（先给用户看效果）**，
E 作为离线兜底（不依赖 IDE 在线）。

**核心转变**：不是「让 AI 学会画易语言的窗口数据」，而是**让 AI 通过官方接口指挥设计器**，
或**只写它百分之百能写对的纯文本代码页**。

---

## 1. 为什么 A/B 不行（问题澄清）

易语言 IDE 的窗口有**两个面**：

| 面 | 载体 | 谁能可靠写 |
|---|---|---|
| **设计数据**（控件树 / 坐标 / 类型特有属性） | `.e` 二进制 ↔ `form/<窗体名>.form.json` | **只有 IDE 设计器** |
| **代码页**（事件子程序体） | `.e` 二进制 ↔ `class/<程序集名>.form.e.txt` | AI（这就是普通文本代码） |

A（黑月界面类）、B（纯 Win32）都把**设计数据**搬进了代码 —— 用户从此没有设计器。
2048 的失败则是**越权去写设计数据**：AI 手搓 `form.json`。

⚠️ 上一轮引用上游 `project-model.md` 的「**不要猜测 XML schema**」红线，现在有了本机实证：
`form.json` 里确实存在**AI 不可能正确构造的字段**（见 §2.3）。

## 2. 一手实测证据（本机，2026-09-23 09:22）

### 2.1 官方 SDK 里有完整的「窗体设计器」操作功能族 —— 实测全部可用

来源：`D:\ides\e\sdk\cpp\elib\PublicIDEFunctions.h`（495 行，官方头文件，AGB 注释）。
探测方法：把功能号加进宿主支持库 `elang_addin.fne` 的 `g_ProbeFns`，用 `FN_IS_FUNC_ENABLED` 实测
（插件源码 `src/addin/elang_addin.cpp`，本轮新增约 90 项探针）。

**启动 IDE 后实测结果：`handled=1 / enabled=1`（可用）**

| 功能号 | 值 | 语义（SDK 原文注释） |
|---|---|---|
| `FN_INSERT_NEW_WIN_FORM` | `0x02020037` | **插入一个新窗体** |
| `FN_MENU_MODI` | `0x02020055` | 启动当前窗体的菜单设计器 |
| `FN_REMOVE_SPEC_UNIT` | `0x0202003E` | 删除窗体上当前所有被选择的组件 |
| `FN_MOVE_LEFT/RIGHT/UP/DOWN_ONE(_GRID)` | `0x0202003F~46` | 移动被选组件一像素 / 一格 |
| `FN_RESIZE_LEFT/RIGHT/UP/DOWN_ONE(_GRID)` | `0x02020047~4E` | 缩放被选组件 |
| `FN_HORZ_CENTER` / `FN_VERT_CENTER` | `0x0202004F/50` | 组件居中 |
| `FN_UNIT_GO_TOP` / `FN_UNIT_GO_BOTTOM` | `0x02020052/53` | 置顶 / 置底（重叠序） |
| `FN_LEFT/TOP/RIGHT/BOTTOM_ALIGN` | `0x0202005D~60` | 对齐 |

都需要**先有选中状态**（用户在 IDE 里点选，或其它手段制造选择）。这是路线 D 的边界。

### 2.2 「组件剪贴板」通道 —— 官方提供了读/写易程序数据的接口，实测可用

| 功能号 | 值 | 语义（SDK 原文） |
|---|---|---|
| `FN_CLIP_GET_EPRG_DATA_SIZE` | `0x05030005` | 取剪贴板「易程序数据」尺寸 |
| `FN_CLIP_GET_EPRG_DATA` | `0x05030006` | 取剪贴板「易程序数据」内容 |
| `FN_CLIP_SET_EPRG_DATA` | `0x05030007` | 写剪贴板「易程序数据」内容 |
| `FN_GET_ACTIVE_WND_TYPE` | `0x05030002` | 当前活动文档类型：1 程序集 / 2 自定义数据类型 / 3 全局变量 / 4 DLL 命令 / **5 窗体设计** / 6 常量资源 / 7 图片资源 / 8 声音资源 |

⭐ **这条通道的意义**：设计器里「复制组件」走的就是这个剪贴板格式。
⇒ **能让 IDE 自己序列化组件**，AI 完全不必理解 `ExtensionData` 的二进制语义。

配套（易模块/支持库清单，可程序化读取）：
`FN_INPUT_ECOM 0x05030003`、`FN_ADD_NEW_ECOM2 0x02020087`、
`FN_GET_NUM_ECOM 0x0503000C`、`FN_GET_ECOM_FILE_NAME 0x0503000D`、
`FN_GET_NUM_LIB 0x0503000E`、`FN_GET_LIB_INFO_TEXT 0x0503000F`。

> 探针原始输出：`%TEMP%\gp_ai_092207_trace.txt`（GBK）；探针代码改动见 `src/addin/elang_addin.cpp`。

### 2.3 `form.json` 字段语义 —— 实测（60 个真实 form.json / 2378 个控件条目）

顶层键恒定 8 个：`Class / Comment / Controls / Id / Menus / Name / UnknownAfterId / UnknownBeforeClass`。
`Children` 中出现 **935 个整数**（不是嵌套对象）⇒ 子控件用**索引引用**。

**按 DataType 分组统计（关键三列）**

| 字段 | 结论 | 证据 |
|---|---|---|
| `Cursor` / `UnknownBeforeEvents` / `UnknownBeforeExtensionData` / `UnknownBeforeName` / `UnknownBeforeParent` / `UnknownBeforeVisible` | **同类型恒定** | 如「标签」352 个样本：`Cursor=00000000`、`UnknownBefore*` 全 0 或全 20 个 0 字节 |
| `UnknownBeforeLeft` | ⚠️ **e2txt 的解析残留，值是内存地址** | 426 种取值，其中 **1018 次为 0**、425 次为页对齐大数（`0x0119F000` / `0x05EE0000` / `0x039F0000`）；同一窗体多个控件共享高位 ⇒ 同一次内存读取的基址+偏移 |
| `ExtensionData` | ⚠️ **是「类型特有属性」的序列化，各类型语义完全不同，多数控件为空** | 「矢量动画框」= **0 字节**；「窗口」= 96 B 位配置；「气球提示框」= 1171 B（尾部是 `</span>` + CSS `.comment{color:green}` 文本）；「图形按钮」= 15638 B，含 `424D`（BMP 图标） |

⇒ **结论**：
* 「改已有控件的通用属性（名称/坐标/尺寸/可见/禁用）」= **安全**（字段语义明确）。
* 「新增控件」= 危险区，且**危险的就是 `ExtensionData`**（类型特有，AI 无法凭空生成）。
* 路线 E 若成立，只能**复用真实模板条目**（保留其 `ExtensionData`），不能新建。

### 2.4 已有事实（前序实测，可复用）

* 真实工程 `e2t → t2e` **7 工程矩阵零错误**（0.66~3.9 MB），加壳产物**编译运行通过**。
  ⇒ 说明 e2txt 的窗口处理**本身是成熟的**，2048 的失败**不是工具不行，是 AI 越权手写**。
* `p1` 真实工程的 `class/窗口程序集1.form.e.txt` 就是**纯代码文本**（事件子程序 + 变量声明），
  AI 完全具备正确书写能力（受 `elang-ai-coding` 规范约束）。

## 3. 路线详解

### F. 契约分离（最稳基线，今天可用）

**分工**：窗口由**设计器**产出（用户拖，或用 C/E 生成一次）；AI **只改 `class/*.form.e.txt`**。

* AI 需要新控件时：**输出一份「控件清单」**（类型 / 名称 / 文本 / 坐标），由用户花几秒拖；
  或走路线 C 由插件代劳。
* 好处：**零窗口数据风险**，AI 的产出永远是它 100% 写对的那部分。
* 代价：AI 不能独立完成「从零造界面」。

### C. EPRG 剪贴板（AI 加组件的官方通道）

```
① 模板采集（一次性）：用户在设计器里复制一个「按钮」→ 插件 FN_CLIP_GET_EPRG_DATA 导出为模板文件
② AI 造组件：选模板 → 改可控属性（名称/文本/坐标）→ 生成 EPRG 字节
③ 落盘：插件 FN_CLIP_SET_EPRG_DATA 写回剪贴板 → 在设计器里粘贴 → 控件出现在设计器，用户可继续拖
```

* **优点**：完全走官方序列化，AI 不碰天书字段；**用户全程可视化**。
* **待验证（P0）**：
  1. EPRG 字节里**哪些字段是可定位、可安全改的**（名称/标题/坐标）——需 dump 一份真实 EPRG 做对照分析；
  2. **粘贴的触发方式**：SDK 里**没有** paste 功能号 ⇒ 需要 `SendInput`(Ctrl+V) 或 `WM_COMMAND` 模拟；
  3. 剪贴板 EPRG 与「整窗复制」是否同一格式（若支持整窗，就能一次注入多个控件）。

### D. 设计器命令族（AI 辅助排版）

用户在 IDE 里**选中若干控件** → 说「左对齐、等宽、水平居中、间距平均」→ 插件执行对应功能号。
**价值**：这是 AI 真正"操作"设计器而不碰数据的场景；边界是**必须已有选中状态**。

### E. 模板化 form.json（离线兜底）

用 §2.3 的 60 个真实 form.json / 2378 个控件条目建**控件模板库**（作为技能 `references/` 资产）。
AI 只做「复制同类条目 + 改 `Name` / `Left` / `Top` / `Width` / `Height` / 标题」，
`UnknownBeforeLeft` 一律填 0，`ExtensionData` 保留模板原值。

* **待验证（P0）**：AI 拼装的 form.json 经 `t2e` 后，**IDE 设计器能否正常显示该控件**
  （这是唯一必须实测的一步；「能编译」不等于「设计器能渲染」）。

### G. AI 预览稿（回应用户的「我要看得见」）

AI 先用 **HTML/PNG** 画出界面预览给用户确认 → 确认后再落成易语言窗口（走 C 或 E）。
* 成本极低、体验最好，且**与 C/E 完全解耦**（纯前端产物）。
* 顺带解决「AI 说改好了但我看不见」的信任问题。

* ❌ `FN_EVA_DESIGNER`、`FN_GOTO_LAST_MODI_PLACE`（实测 enabled=0）语义未查。
* ⚠️ 探针时机是 **IDE 刚启动、无活动文档**；各功能号在设计器/代码页下的可用性**可能不同**，需按场景复测。
