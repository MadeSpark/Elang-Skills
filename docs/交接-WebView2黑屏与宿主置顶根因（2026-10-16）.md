## 1. 缺陷①：webui 黑屏

### 1.1 根因（有代码行 + 实测计数）

`src/mbkit/mbk_webview.cpp` 的 `release_controller()` **原来不是幂等的**：

```c
static void release_controller(WV* w)
{
    if (!w) return;
    unhook_host(w);
    if (w->ctl) {
        ... post_to_hidden(WM_APP + 76, pack, 0);
        w->ctl = 0;
        w->core = 0;
    }
    if (w->core) { w->core->Release(); w->core = 0; }   /* ← 永远不可达 */
    w->wired = 0;
    diagf("controller released");
}
```

三条入口会打进来：`host_subproc` 对 **`WM_DESTROY` 与 `WM_NCDESTROY` 各调一次**
（`:1324`），外加 `wkeSetHandle(0)` 与 `wkeDestroyWebView`。

**实测证据**（修复前，`%TEMP%\mbkit-webview-<pid>.log`，同一 tid、同一 tick）：
```
[38487796 tid=54448] controller released
[38487796 tid=54448] controller released
[38487796 tid=54448] controller released
[38487796 tid=54448] controller released
[38487796 tid=54448] CreateWebView view=0d5adc18     ← 紧接着又建新视图
```
统计：`controller released = 60` 而 `CreateWebView = 6` → **每视图平均 10 次**。
（上一份交接里那份更老的日志是 74/6 ≈ 12.3 次。）

两个后果：
1. **同一个 controller 被多次 `put_IsVisible(FALSE)` + `Close()` + `Release()`** —— `Close()` 之后那块区域没有任何东西在画，宿主窗口却还在、还能响应 → 正是用户说的"挂一段时间黑屏"（窗口活着、内容整片黑、日志从此静止）。
2. `w->core` 被置 0 后 `if (w->core)` 不可达 → **每建一个视图泄漏 1 个 controller + 1 个 core**。

### 1.2 修法

给 `release_controller()` 加幂等门 + 修正释放顺序（先存引用、再清字段、最后按有无 `ctl` 分别释放）：

```c
if (!w->ctl && !w->core && !w->wired) return;   /* 已释放过：直接返回 */
...
ICoreWebView2Controller* ctl  = w->ctl;   /* 先存引用 */
ICoreWebView2*           core = w->core;
w->ctl = 0;  w->core = 0;
if (ctl) { ...post WM_APP+76... } else if (core) core->Release();  /* 没有 ctl 也别漏 core */
```

### 1.3 验证（修复后，同一套流程）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `controller released` 总次数 | 60 | **6** |
| `CreateWebView` | 6 | 7 |
| 同 tick 连发多条 | 35 组 | **0** |
| 每视图释放次数 | ~10 | **1**（日志形如 `controller released [view=06cb7f90 n=1 alive=1]`） |
| 失败/丢弃行 | 0 | 0 |

## 2. 缺陷②：重载后宿主被置顶

### 2.1 真凶不在内核、不在插件

- `src/mbkit/` 全源：`HWND_TOPMOST` **只出现在 `dpi_shot.c`**（那是它自建诊断窗）；其余 `SetWindowPos` 全部带 `SWP_NOZORDER`；`WS_EX_TOPMOST` **零出现**。
- 插件源码：`总在最前` 全仓**仅 1 处**，而且语义是**取消**置顶，且被"窗口被激活"事件门控：
  `代码\窗口程序集_Main.form.e.txt:152-153` → `_Main_被激活` / `Main.总在最前 ＝ 假`。

### 2.2 真凶：3 个脚本置顶后不恢复

全工作区 14 个含 `HWND_TOPMOST` 的脚本对账：**11 个配对恢复、3 个不恢复**。
不恢复的 3 个里，**2 个操作的正是宿主窗口**：

| 脚本 | 行 | 目标 |
|---|---|---|
| `out_mbkit/ab_test/shot_win.py` | 26 | `Main`（宿主主窗） |
| `out_mbkit/ab_test/shot_main.py` | 24 | `Main` / `XiaoLiZi_VM` |
| `clickrgn2.py` | 9 | 宿主虚拟机窗（硬编码 hwnd） |

**为什么"只在某些重载后"**：
1. `SetWindowPos(HWND_TOPMOST)` 会真正写入持久化的 `WS_EX_TOPMOST`，**不是一次性 z 序前移**；脚本设完就截图退出，**没有任何恢复动作**。
2. 重启宿主会销毁窗口、该属性自然消失 —— 所以只有"宿主不重启、反复点重载"才留得下来，正是本缺陷的复现路径。
3. 重载后**没人复位**：复位只在 `_Main_被激活` 里；而驱动重载的脚本用 `PostMessageW(hwnd, 0xF5, …)` 直接给按钮投 `BM_CLICK`，**不激活窗口**，复位分支走不到。

正确模板（本来就有）：`out_mbkit/reload_acceptance/reload_verify.py:113` 置顶 → `:124` `u.SetWindowPos(t['hwnd'], w.HWND(-2), 0,0,0,0, 0x13)` 恢复。

### 2.3 已做的修复

`shot_win.py` 改成 `try/finally`，截图后**无条件** `HWND(-2)` 还原，并加注释说明原因。
`blackwatch.py` 本来就不置顶（只用 `ShowWindow`），无需改。

验证（跑完修复后的 `shot_win.py`，再枚举宿主顶层窗的 `GWL_EXSTYLE`）：
```
Main          exstyle=0x40100  topmost=False   ← 正常
XiaoLiZi_VM   exstyle=0x80100  topmost=False   ← 正常
残留 topmost 的两个是隐藏的 SysShadow/WTWindow 阴影助手窗，非用户可见窗
```

## 3. 验收：按用户给的流程重跑

用户给的流程（原样）：修改 `_按钮3_被单击` 里的 `计次循环首 (N, i) ' 重载替换时…` → 编译 → 启动宿主 → 等 webui 加载成功 → 再改 N、再编译 → 点"重载自身" → 重复直到连续 5 次不崩溃。

本轮用 `out_mbkit/ab_test/accept.py` 把它脚本化，并**预先编译**好 N=2..6 五个变体
（`var_2.dll` … `var_6.dll`，MD5 互不相同：`90a19173… / 75abd878… / aba63aed… / f6e6e86b… / 98d83c37…`），
每轮换成下一个变体再点重载。

### 3.1 跑出来的结果（**不是每次都能过**）

| 内核 | 测试轮次 | 结果 |
|---|---|---|
| `a34e2a92`（仅 hidden_host 修复） | 两轮独立跑（PID 41532、48680 系列） | **5/5 通过**，宿主存活 |
| `58bbeaea`（+ release 幂等门） | PID 50664 | **5/5 通过**，宿主存活，释放 60 → 6 |
| `5bf20a75`（同上 + 诊断插桩） | PID 57456 / 53664 / 8964 | **不稳定**：分别崩在第 3、第 6、第 1 轮之后 |

**崩溃签名（今日全部，`Application` 日志 Event 1000）**：

| 时间 | 异常码 | 位移 | 模块 |
|---|---|---|---|
| 00:51:56 | `0xc0000005` | `0x000011cc` | **`win32u.dll`** |
| 00:56:33 | `0xc0000005` | `0x7133c8b4` | unknown |
| 00:59:09 | `0xc0000005` | `0x7133c8b4` | unknown |
| 12:43:38（昨日，改动前） | `0xc0000005` | `0xc453c8b4` | unknown |
| 23:27:11（昨日，改动后） | `0xc0000005` | `0x7133c8b4` | unknown |

- `0x7133c8b4` 这一支**昨天 12:43 就存在**（早于任何本轮改动）→ **既有的热重载 use-after-free**。
- `win32u.dll + 0x11cc` 是**新出现的签名**，且落在**插件卸载路径**里：崩溃前插件日志正好打完
  `_按钮3_被单击` 循环的 `1 2 3`（即 `Api.重载自身 ()` 之前的收尾段）。
- 崩溃后**宿主的"闪退保护"会自动重启宿主**：实测 PID 26876 的 `ParentProcessId = 57456`
  （26876 由 57456 创建），这与宿主 UI 里的「闪退保护_框架」开关一致。

### 3.2 结论（说实话）

- **缺陷①（黑屏）** 的成因已确证并消除（释放次数 60 → 6），但**"重载 5 次不崩溃"这一条
  在有 release 幂等门的构建上只稳定通过过 1 次，另一次在第 3 轮后崩**。
- 因此**不能声称验收已通过**。崩溃点（`win32u.dll` / unknown，均在卸载路径）需要单独一轮修复，
  且它很可能与上一份交接第 5 节列的既有 use-after-free 是同一族问题。
- **风险提示**：本轮以前，`release_controller` 因为不幂等而"意外"多做了一次 `Close()`；
  把重复释放去掉之后，**卸载时序的真实竞争暴露了出来**（原来被重复释放掩盖）。
  这是"修好一个 bug 露出另一个"的典型情况，不是新引入的缺陷。

### 3.3 建议的下一步（按优先级）

1. **先修卸载路径**（决定验收能否过）：
   - `host_subproc`（`:1319-1329`）在 `WM_DESTROY`/`WM_NCDESTROY` 里调 `release_controller`，
     而它把真正的 `Close()/Release()` **异步**投给 `WM_APP+76`。宿主窗口随后就被 `DestroyWindow`，
     Chromium 的窗口/合成器还没拆完 —— 高度怀疑就是 `win32u.dll+0x11cc` 那一下。
     **方向**：在 `WM_DESTROY` 里**同步**把 controller 与宿主窗口解绑（或先 `put_ParentWindow(NULL)`
     再 `Close()`），不要留到异步消息；并把 `WM_APP+76` 的 `ReleasePack` 改成幂等可重入。
   - 复查 `CtlDone::Invoke`（`:918`）的 `ctl->AddRef()` 无配对 Release。
2. **统一宿主实例**：测试时必须确保只有一个 `小栗子虚拟机.exe`。
   本轮多次出现"两个宿主同时跑"（26876 是 57456 的自动重启子进程，且我无权限结束它），
   会直接污染结论。`accept.py pid_of_host()` 已改成"取最新且有 StartTime 的进程"，但仍需人工确认。
3. 黑屏的"瞬间现场"仍建议用 `blackwatch.py` 长跑抓一次（本轮没抓到）。

## 4. 一个必须记住的部署坑（本轮踩到）

**改了内核源码、重编了模块和插件，宿主仍可能跑旧内核。**
实测：`%TEMP%` 日志一直是旧格式（没有新增的诊断字段），查下来是
`框架-爱丽\MbKit146.dll` 停留在 `23:03:55` 那份（722944 B / `A34E2A92…`），而新内核是
`00:41:27` 那份（`5BF20A75…`）。

原因：模块的 `_释放宿主库文件`（`out_mbkit/miniblink_源码146/代码/程序集_全局.static.e.txt:189-214`）
在 `文件是否存在` 为真时走的是**读文件比内容**那条较早的分支，实测没能把新 blob 覆盖上去。

**对策（本轮起统一用）**：构建链跑完后，**显式**把内核同时写到两个位置：
```
Copy-Item src\mbkit\MbKit.dll 'D:\DevelopmentFolder\插件开发目录\E\插件\框架-爱丽\MbKit146.dll' -Force
Copy-Item src\mbkit\MbKit.dll 'out_mbkit\miniblink_源码146\资源\_常量28010234.image.dat' -Force
```
另外注意：宿主进程退出后文件仍可能被短暂占用，复制前先确认 `小栗子虚拟机.exe` 已结束。

**判断"宿主到底加载了哪份内核"的快捷方法**：看 `%TEMP%\mbkit-webview-<pid>.log` 第一行附近有没有
`hidden host created on tid=…`（本轮新加）或 `controller released [view=…]`（本轮新加的带参格式）。
没有就是旧内核。

## 6. 仍未解决 / 已知风险

1. **黑屏只做了"消除已知成因"这一步，没有抓到黑屏瞬间的现场。**
   本轮把"同毫秒连发多条释放"这条确证成因消掉了；但 `blackwatch.py` 还没抓到过黑屏那一刻的截图+dump。
   若用户再次遇到黑屏，请**立刻**保留 `%TEMP%\mbkit-webview-<pid>.log` 与该时刻截图。
2. **另外 3 个已确认的脆弱点**（本轮未改，按风险排序）：
   - `host_subproc`（`:1319-1329`）只处理 `WM_SIZE`/`WM_SHOWWINDOW`/`WM_DESTROY`；**没有** `WM_WINDOWPOSCHANGED` / `WM_DPICHANGED` / `WM_ERASEBKGND`。且钩子一旦被插件夺回，尺寸/可见性同步会**静默失效**。
   - `CtlDone::Invoke`（`:918`）的 `ctl->AddRef()` **没有配对 Release**（视图级的泄漏，与上面第 1 条同类）。
   - `WM_SHOWWINDOW` 会无条件 `put_IsVisible(wp ? TRUE : FALSE)`（`:1326`），而恢复可见**只靠再次 `apply_state`** —— 理论上存在"被隐藏后再没人恢复"的黑屏路径。
3. **`MbKit144.dll` / `MbKit147.dll` 两个历史副本仍在宿主目录**（已置隐藏，当前无模块引用）。排查问题时它们会污染 VEH 模块视图，建议归档。
4. 上一份交接第 5 节的**热重载 use-after-free**（`0xc0000005`，低 16 位 `c8b4`）本轮未复现，也未修；仍应作为独立项跟进。
