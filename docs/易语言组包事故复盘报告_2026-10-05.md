## 二、根因分析

### 2.1 QAQ-ETool 的两种组包模式（事故的技术背景）

`e2t` 拆包时除了产出文本目录，还会写一个**旁路文件** `.qaq/sidecar.json`，里面记录了整个工程的 **28640 个符号的 ID 分配表**（子程序、变量、参数、类型……每个名称对应原 .e 里的数字 ID）。易语言 .e 二进制内部的调用引用**按 ID 绑定**，名称只是给人看的。

`e2t` 拆包时把每个符号的名称 → ID 记进 sidecar，t2e 组包时按文本重建符号表：

| 组包方式 | 符号 ID | 代码单元（子程序等） |
|---|---|---|
| **默认（sidecar）** | 文本里的名称在 sidecar 找得到 → **沿用原 ID** | 比对后未改动的 → **逐字节还原原始二进制**；真改动的 → 按文本重绑 |
| **`-nosidecar`** | 全部新分配 | **全部按文本重新生成**，与原二进制毫无字节级关系 |

### 2.2 为什么 `-nosidecar` 会毁掉这个工程

这个工程的特殊性：**12 个易模块直接内嵌在 .e 里**（精易、HPSocket、miniblink、zyJson、Protobuf、HashMap、winhttpapi、鱼刺类……），模块的公开命令被主工程大量调用。

关键在拆包时的那条警告：**「44 个模块私有数据类型未随 .e 保存（仅有 ID，无名称）」**。这些类型在 .e 二进制里只以数字 ID 存在、没有名称字符串（易模块二进制格式的历史遗留），`e2t` 只能在文本里写成 `<?未知本地类型:0x…?>` 占位。

于是形成死局：

```
e2t 拆包：类型只有 ID → 文本只能存占位符（信息已经丢了）
-nosidecar 组包：全部按文本重建 → 占位符无法还原成有效类型记录
         → 模块里签名用到这些类型的命令记录损坏
         → IDE 打开：模块加载了，但里面那批命令解析异常
         → 编译报「找不到函数」，而模块明明已载入
```

**一句话：模块信息在「拆包」那一步就已经有损（44 个类型只剩 ID），文本通道根本带不动这些信息；`-nosidecar` 相当于宣布「丢弃全部原始字节、只信文本」，把有损变成了损坏。**

### 2.3 为什么当时的自动检查没拦住

- t2e 对此**只报退出码 2 和「未验证代码 13 处」警告，不报错误**（错误 0 处）。
- 我当时做了基线对照（未修改文本组包同样退出码 2），证明 13 处警告是**工程固有**的——这个判断本身没错，但由此推及「组包产物整体安全」是**错的**：对照只能证明警告清单一致，证明不了模块二进制完好。
- 13 处「未验证代码」事后逐行核查：**全部是注释行**（引用 `Service_Gettime`、`编辑框_账号`、`g_user_id_map`、`Android.初始化_仅QQ和密码` 等）——这些名称是 patch 历史遗留，旧版 .e 里也只存在于注释（二进制字符串计数证实），sidecar 符号表里同样没有声明。**注释不参与编译，纯烟雾弹**。真正的问题（模块类型损坏）在警告清单里一条都没出现。

### 2.4 教训归纳

1. **大工程的 .e 文本往返本质是有损通道**：模块私有类型、部分绑定信息只在二进制层存在。文本层验证全绿 ≠ 产物等价于原件。
2. **基线对照证明的是「警告清单一致」，证明不了「产物完好」**——对照组选错了验证目标。
3. **「未验证代码」警告要先看行内容定性**：注释行 → 无害；活代码 → 才是真问题。
4. **模块类工程，模块区域的字节完整性是生命线**，任何「全量重建」类操作都是赌博。

## 三、解决方案

改用 **默认 sidecar 组包**（去掉 `-nosidecar`）：

| 指标 | -nosidecar 版（坏） | sidecar 版（好） |
|---|---|---|
| 退出码 | 2（未验证 13 处） | **0** |
| 符号 ID | 全部新分配 | **沿用 28640、新分配 0** |
| 代码单元 | 全部按文本重建 | **1502 个逐字节还原、仅 2 个按文本重绑** |
| 模块二进制 | 按文本重建（损坏） | **逐字节原样** |
| IDE 编译 | ❌ 找不到函数 | ✅ 通过（用户实测） |

被重绑的 2 个单元正是流程线修复所在的子程序。sidecar 的比对逻辑能识别「子程序**中间**插了行」（真改动 → 按文本重绑，t2e 活代码绑定 0 错误，安全），修复得以落地。回读（e2t 再拆包）+ echeck 复验确认修复在产物里。

## 四、最终修复范围与取舍

**已修复（5 处）**：隐藏块尾紧挨块尾——`.如果真结束` 后紧跟 `.如果结束` / `.如果真结束`，全部集中在 `窗口程序集_界面` 的同一个子程序（行 4982、5032、5033、5034 + 5035 子程序末尾）。这是全量统计 **485:0、零例外**的「IDE 必崩串线」形态，也是本次修复的核心价值。

**有意不修（14 处）**：子程序末行是块尾、后面跟「真空行」。检查器按另一工程的统计（4 空格空行为主流 166:14）判这 14 处违规；但本工程实测 **1040 处子程序边界全部真空行、0 处 4 空格**——这是工程原生惯例，旧版 IDE 一直渲染正常。且 sidecar 机制会丢弃「子程序末尾空行」改动，硬要用 `-nosidecar` 落地会重蹈模块损坏覆辙。**保持原样 = 与旧版渲染完全一致 = 零回归风险。**

**关闭项**：echeck 曾报 `程序结束前操作` 参数个数不符（声明 1 参、2 处 2 参调用）——用户 IDE 实测编译通过，判定为检查器在该工程的误报，此项关闭。

## 五、以后怎么处理（操作规程）

**对含内嵌模块/大体量 .e 工程（如栗子虚拟机）：**

1. **组包一律用默认 sidecar 模式，禁用 `-nosidecar`。** `-nosidecar` 只允许用于无模块、或模块可安全重绑的小工程。
2. **改完文本必须回读复验落地情况**：`t2e` → `e2t` 回读 → `echeck`。sidecar 的比对盲区要背下来：
   - 子程序**中间**插行/改行 → 会被发现、按文本重绑（活代码绑定 0 错误时安全）✅
   - **子程序末尾空行**改动 → 被**静默丢弃** ❌（组包退出码 0 也不代表落地了）
3. **t2e 警告先定性再定性缺席**：警告行是注释 → 无害；活代码「未验证」→ 真问题；**同时要明白：真问题（如模块类型损坏）可能一条警告都不报**——退出码 0 + 错误 0 不足以证明产物完好。
4. **唯一验收标准不变**：IDE 打开 + 编译 + 运行。文本层检查（echeck/rtcheck/基线对照）全部只是前置过滤。
5. 若将来真需要「末尾空行改动 + 模块无损」兼得：目前 QAQ-ETool 无官方开关。可选路径：向工具作者反馈比对规则（忽略行尾空行导致末尾空行改动无法落地）；或手工编辑 sidecar 强制特定子程序重绑（有调用级联风险，需逐例验证）。

**通用链路（修订版）**：

```
改文本 → echeck（0 错误 0 流程线警告）
      → t2e 默认 sidecar 组包（退出码 0、错误 0）
      → e2t 回读 → echeck 复验「改动真的落地了」
      → IDE 打开编译运行 = 唯一验收
```
