## 0. 结论先行

上游对「AI 写窗口」的答案**不是**「教 AI 怎么写表单」，而是：

> **把窗口从「易语言的窗口设计数据」搬到「普通代码 / 标准 RC 文本」里去，并且明确规定 AI 不许碰设计要求。**

三条红线（上游原文）：

| 出处 | 原文 |
|---|---|
| `references/project-model.md` §安全编辑边界 | 「修改窗口布局：优先 IDE 设计器；**不要猜测 XML schema**」 |
| `references/windows-and-interop.md` §窗口与组件 | 「**只修改代码页**；需要新增/删除控件或改变布局时使用 IDE 设计器能力」 |
| `references/windows-and-interop.md` §事件绑定 | 「**新增、删除或修改事件绑定必须由用户在易语言 IDE 中完成**」；「新增事件子程序**不代表**已经建立控件事件绑定」 |

我们 2048 翻车，**恰好**同时踩了前两条：手写 `窗口/_启动窗口.form.json`（19 键 Controls 模板）+ 手工拼 `xxx.form.e.txt` 事件程序集 —— 这就是「猜 schema」+「AI 自建窗口/事件绑定」。

## 1. 上游的三条路线与优先级

出处：`blackmoon.md` §窗口方案优先级（上游 2026-08-04 专门为这一节提交过）。

| 已知条件 | 上游的选择 | 关键接口 |
|---|---|---|
| **新建原生窗口，无 RC 资源** | **与工程版本匹配的 `黑月界面类` 纯代码方案** | `应用程序类` / `窗口类` / 控件类 / 布局类；入口在 `_启动子程序` |
| 已有稳定 RC/资源对话框 | 继续用 RC | `创建自资源` / `载入自资源` + `绑定` |
| **必须复用易语言可视化窗口** | 保留易语言窗口体系，**不引入** `应用程序类.运行` | 只改代码页，设计与事件绑定交 IDE 设计器 |
| 当前模块没有所需能力 | 先确认有无兼容改版，再决定升级/更换 | 不「为了看起来现代」静默换代 |

### 1.1 路线 A（上游首选）：纯代码黑月窗口

窗口、控件、布局**全部在普通程序集的代码里创建**，完全不碰窗口设计数据。骨架（上游原文）：

```text
.版本 2

.程序集 程序集1

.程序集变量 App, 应用程序类
.程序集变量 mainFrame, 窗口类

.子程序 _启动子程序, 整数型

App.初始化 ()
mainFrame.事件_创建完毕 (&mainFrame_创建完毕)
.如果真 (mainFrame.创建 (, “黑月窗口”) == 假)
    返回 (-1)
.如果真结束
返回 (App.运行 (mainFrame))
```

配套硬约束（上游 `黑月界面类` 三节）：控件必须在**父窗口的 `事件_创建完毕` 里**创建/绑定（那时句柄才有效）；创建/绑定后**立即注册控件事件**；**整个程序只有一个消息循环**；对象声明为程序集/全局变量防提前销毁；可调窗口必须用布局类（线性 / Masonry 约束）而非按初始尺寸摆放。

### 1.2 路线 B（上游次选）：RC 资源对话框

`.rc` 与 `.e` **同名同目录**，`.rc` 用标准 Win32 文本语法写对话框，再用 `创建自资源(, #IDD_MAIN)` + `控件.绑定 (main, #IDC_OK)` 包装。RC 是**标准、有文档、AI 可以正确书写**的文本格式 —— 比猜易语言 schema 靠谱得多。
注意：RC 的 `#define` **不会**自动变成易语言 `#常量`，两边要各写一份且数值一致；中文 RC 的编码受 `RC.EXE` 版本限制（已核实示例用 GBK/CP936）。

### 1.3 路线 C：保留可视化窗口（只改代码）

设计器生成窗口后，AI **只改代码页**，用「事件子程序 → 调普通子程序」的拆分模式（上游 `patterns.md` §窗口事件拆分）把逻辑抽出来。控件/布局/事件绑定改动一律交回用户在 IDE 里做。

### 2.1 顺带纠正一条被误读的结论

上游 `patterns.md` 的「**错误的双分支**」**不是**交接文档 §9.2 说的那条：

- 上游禁的是 `.如果真 (…)` + `.否则` + `.如果结束`（`.如果真` 没有 else，结构不自洽），修法是改成 `.如果 / .否则 / .如果结束`；
- 上游**没有**「`.如果` 不带 `.否则` 会让 IDE 编译静默崩溃」这种说法。

⇒ 该规则本身仍然要写进技能（结构自洽是对的），但 **§9.2 陈述的那个「原因」依然无据**。

## 3. 本机可行性（已实测）

| 项 | 结论 |
|---|---|
| 黑月**后端**（`BlackMoon.fne` / `RC.EXE` / `CVTRES` / `LINK`） | ❌ **本机没有**（`D:\ides\e\lib`、`static_lib`、全盘 maxdepth 4 搜索均为空） |
| 但路线 A **是否需要后端**？ | ❌ **不需要**。上游明说「引入界面模块**不等于**已使用黑月后端编译」；黑月界面类只是**提供 UI 对象的易模块**，可走普通/静态编译 |
| 黑月界面类 `.ec` | ✅ 本机有 `黑月界面类3.8.ec` 与 `黑月界面类-修改版.ec`（在 `D:\DevelopmentFolder\Take notes\助手(v3.X)插件开发包(20-10-16)\三方模块\`），3.8 属上游认可的 3.x 家族 |
| **易模块依赖怎么在文本工程里声明** | ✅ **已定位通道**：`module/<名>/`（展开的模块文本）+ `module/<名>.desc.json`，后者形如 `{"Rename":{...},"Source":"<原 .ec 绝对路径>"}` |
| ⚠️ 由此带出的风险 | `Source` 是**绝对路径**指向 `.ec` 原件 ⇒ t2e 重建时**可能仍需该 `.ec` 在本机**。**能否纯文本自包含，是阶段 1 必须先答的问题** |

## 5. 风险与决策点

| 风险 | 影响 | 处置 |
|---|---|---|
| 黑月界面类 `.ec` 依赖要绝对路径 | 技能无法自包含 | 阶段 1.1 先实测；不行就转路线 B |
| 路线 B 无上游先例 | 要我们自己趟坑 | 但全文本可控；已有 DLL/回调/GDI 基础 |
| 本机无黑月后端 | 黑月**编译后端**路线不可用 | 已知不影响路线 A（纯代码窗口 + 普通静态编译） |
| 第三方 `.ec` 再分发授权不明 | 合规 | 阶段 4.3，宁可让用户自备 |
| 易模块多代际不兼容（2.x / 3.x / 第三方改版） | 抄错签名 | 沿用上游「**先识别 API 家族**」，只用本机实际 `.ec` 的公开接口 |

**待用户拍板的两个点**：
1. 主路线选 **A（黑月界面类，省事但依赖第三方便件）** 还是 **B（纯 Win32，零依赖但要从零趟）**？
2. 是否接受「让用户自备 `黑月界面类.ec`」这种非自包含分发？
