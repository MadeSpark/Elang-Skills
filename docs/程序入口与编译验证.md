# 程序入口与编译验证

> 本文回答两个问题：**一段易语言代码的真正入口是谁**、**怎么在不依赖人的前提下验证一段逻辑真的能跑**。
> 文末的「无头编译」小节与 `elang-build` 技能配套使用。
> 改编自 aiqinxuancai/e-language-skill（MIT）同名知识，并经本套装真机验证修订。

## 1. 程序入口的优先级：`_启动窗口` 会**无视** `_启动子程序`

`_启动子程序` 是易语言的标准入口（相当于 C 的 `main`），写在**普通程序集**里。但它**不一定是实际入口**：

| 判断顺序 | 条件 | 实际入口 |
|---|---|---|
| 1 | 工程里存在名为 `_启动窗口` 的窗口程序集 | **直接载入该窗口**，`_启动子程序` 写了也**不会执行** |
| 2 | 否则，普通程序集中有 `_启动子程序` | 从它开始执行 |
| 3 | 易模块（`.ec`）/ DLL | 另有约定（见 §3、§4） |

**为什么这很致命**：IDE 新建「Windows 窗口程序」时默认就带一个 `_启动窗口`。想改成代码入口，必须：

1. **删除或改名** `_启动窗口`（比如改成 `主窗口`）；
2. 新增 `_启动子程序`（新建窗口工程时 IDE 不会自动生成它）；
3. 在 `_启动子程序` 里显式载入窗口：`载入 (主窗口, , 假)`（第三参数 `假` = 非模式，由窗口消息循环维持程序运行）。

排错时同理：**程序行为不像没执行入口？先查工程里是不是还躺着一个 `_启动窗口`。**

## 2. 用 `_启动子程序` + 控制台做逻辑验证

验证某段逻辑/某个支持库命令的真实行为，最省事的路子：

```
.子程序 _启动子程序, 整数型

    标准输出 (1, “结果=” ＋ 到文本 (待验证子程序 (1, 2)))
    返回 (0)
```

要点：

- `标准输出` 是**核心库命令**（英文名 `fputs`，2 参数：输出方向 1=#标准输出设备 / 2=#标准错误设备，可空；内容为通用型），**只在控制台程序里有意义**——验证工程必须**显式编译为控制台 EXE**，不要依赖 `auto` 目标（窗口 EXE 下看不到输出）。
- 验证用入口代码属于**调试脚手架**：交付前还原，或在交付说明里明说。
- ⚠️ **实测缺陷（2026-09，e-packager semantic 后端）**：调用 `标准输出` 的工程编译出的静态产物会**崩溃**（`写文件`、`打开文件` 等其它核心命令全部正常）。在该后端下做控制台验证，**改用「写结果到文件 → 读回」**：

```
.子程序 _启动子程序, 整数型

    .局部变量 号, 整数型

    号 ＝ 打开文件 (“result.txt”, #重写, )
    写文本行 (号, “结果=” ＋ 到文本 (待验证子程序 (1, 2)))
    关闭文件 (号)
    返回 (0)
```

编译后运行产物、读 `result.txt` 即完成验证（此形态已真机实测通过）。

## 3. 易模块（`.ec`）也能自带 `_启动子程序`：模块自测

`.ec` 里同样可以写 `_启动子程序`，但**被主工程引用时它不执行**。想单独验证模块逻辑：把模块工程**显式编译为控制台 EXE**（不要编译成 `ecom`——编译成模块不会执行入口），入口里用 §2 的方式打印/落盘结果。

## 4. 编译目标速查

| 目标 | 产物 | 入口约定 |
|---|---|---|
| 窗口 EXE | `.exe`（GUI 子系统） | `_启动窗口` 优先，其次 `_启动子程序` |
| 控制台 EXE | `.exe`（控制台子系统） | 同上；`标准输出`/`标准输入` 可用 |
| DLL | `.dll` | `Dll命令` 被外部调用；黑月 DLL 用 `Dll入口函数` |
| 易模块 | `.ec` | `_启动子程序` 仅在把模块当独立工程编译成控制台 EXE 时执行 |

## 5. 无头编译：AI 自己编译验证

不打开 IDE 界面、由命令行直接把 `.e` 编译成 exe，有两条通道，**怎么选、命令行怎么写、环境自检**，见 **`elang-build` 技能**（`SKILL.md`）。本机环境能不能跑、跑不通时先查什么，那份技能里有一张按实测写成的排错表。
