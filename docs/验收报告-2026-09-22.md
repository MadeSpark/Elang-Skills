## 4. 发现的问题（按严重度）

### 🔴 P0（需用户决策）：四个 `SKILL.md` 是单点存储，无法从任何源重建

**事实链**：

```
.gitignore:  /Releases/           → 整个发布区不入库
git ls-files | grep skill.md      → 空（四个 SKILL.md 均未被跟踪）
find . -name SKILL.md             → 仅发布区 4 份 + 上游 1 份
sync-release.sh                   → 只同步 scripts/(tools/) 与 references/(docs/)，【不涉及 SKILL.md】
```

⇒ 四个 `SKILL.md`（其中 `elang-ai-coding/SKILL.md` 已达 **42,355 B**）**只存在于发布区这一份**。发布区被删除、挪位或误覆盖 ⇒ **永久丢失且不可重建**（`scripts/`、`references/`、`assets/` 都能重建，唯独 SKILL.md 不能）。

**缓解因素**（不能替代版本控制）：`install-skills.py` 会把技能拷到 9 个安装点，等于散布 9 份副本，但副本无版本历史、且散落在各工具目录。

**建议**：把 `SKILL.md` 纳入版本控制。两个方案（择一即可）——
1. **收窄 gitignore**：`/Releases/` → 仅忽略打包产物（如 `/Releases/**/*.zip`），让 `skills/**` 入库；
2. **引入真源目录**（如 `skills/<名>/SKILL.md`）并让 `sync-release.sh` 一并同步（与现有「tools/docs 真源」思路一致）。

### ✅ 已更正（原判「`pack-skill.py` 非字节幂等」，**归因错了**）

**正确结论：`pack-skill.py` 在同一解释器内是字节幂等的** —— 连打两次，4 个 zip 的 md5 与逐字节内容完全相同。

上一版报告「同内容重打包 md5 会变」的**观察是对的**，但原因不是时间戳。字节级定位（同一个 `raw 14547 B / CRC a46ae028` 的条目）：

| | 文件清单 | 解压内容 | 各条目 CRC | `compress_size` | 内嵌 mtime |
|---|---|---|---|---|---|
| `e2txt-cli.zip` | 一致 | 一致 | 一致 | **7031 → 7307** | 一致 |
| `elang-build.zip` | 一致 | 一致 | 一致 | **3407 → 3532** | 13:25:58 → 13:36:28 |

⇒ 差异**只**在 deflate 流上：HEAD 那份是普通 zlib 压的，本次是 **Python 3.14 的 `zlib-ng`**（`ZLIB_VERSION = 1.3.1.zlib-ng`）压的。同一份内容、不同压缩器实现 → 压缩后长度不同 → 整体 md5 不同。**与 mtime 无关**：`e2txt-cli.zip` 连内嵌 mtime 都一致、md5 仍不同，这一条直接排除了时间戳解释。

**处置（已落地）**：`dist/` 从版本控制移出（见 `.gitignore`）—— 它 100% 可从 `Releases/` 再生，跨环境又不可复现，入库只会每次打包都产生无意义二进制 diff。同时 `verify-release.py` 新增「按当前发布区重新打包、逐字节比对 `dist/*.zip`」——比对在**同一解释器内**进行，因此不受该差异干扰，能真实抓住「分发包与发布区内容不一致」。

## 8. 优化落地记录（2026-09-22 晚）

把 §7 逐条落地时，顺手修掉了验收中**发现但没修**的一个真缺陷和两个隐患。

### 🔴 真缺陷：`verify-release.py` 自我下毒（`__pycache__` 失败项的根因）

上一版把这个失败项判为「检查器 `import` 触发的字节码缓存，**不是 sync 的必然产物**」—— 方向对，但**没定位到产生它的那行代码，也就没修**。本轮定位到：

`verify-release.py` 用 `importlib.spec_from_file_location` + `exec_module` 导入 `install-skills.py`（第 3 项）与 `scan-machineinfo.py`（第 7 项）。`SourceFileLoader` 会把编译结果写回源码目录，生成 `Releases/Elang-AiTools/__pycache__/install-skills.cpython-*.pyc`；而**第 1 项检查恰恰就是「发布区混进 `__pycache__`」，且它在 `load_installer()` 之前执行**：

> 每次总检，都给**下一次**总检埋一个失败项。

**为什么验收时没复现**：本沙箱设了 `PYTHONDONTWRITEBYTECODE=1`（`sys.dont_write_bytecode=True`），所以我这侧跑不出来；**用户的终端没有这个变量，必然踩**。

**修法**：脚本顶部 `sys.dont_write_bytecode = True`（不依赖外部环境变量），失败信息附 `rm -rf <路径>`。
**验证**：显式 `PYTHONDONTWRITEBYTECODE=0` **连跑两次**，均 88/0 且**零 `__pycache__`**。

### 🟡 隐患 1：`SKILL.md` 单点存储（P0）

`bafd77e` 的意图是「把发布用的 `Releases/Elang-AiTools.zip` 移出仓库」，但规则写成了 `/Releases/`，**连整个目录一起忽略** —— 四个 `SKILL.md`、`使用说明.md`、三个安装入口**全部没有版本控制**，工程侧也没有源本。更隐蔽的后果已实测：**`dist/*.zip` 会与发布区内容悄悄漂移而 git 看不见**（HEAD 里 4 个 zip 与当前内容全不同）。

**修法**：把规则改回它本来的意思 —— 只忽略 `/Releases/**/*.zip`（发布附件本身），发布区成品入库。`/dist/` 反而出库（理由见「已更正」一节）。

### 🟡 隐患 2：`core.autocrlf=true` 且无 `.gitattributes` ⇒ clone 出来脚本就跑不起来

实测：本机 6 个 `.sh`（`sync-release.sh`、`src/build.sh`、`src/addin/build.sh` …）在盘上都是 LF，而 autocrlf=true 会在**检出时写成 CRLF** ⇒ 新机器上 `bash tools/sync-release.sh` 直接报 `\r`；新入库的 `install-skills.sh` 是用户入口，同样中招。

**修法**：新增 `.gitattributes`，**只钉死会直接失效的类型**（`*.sh eol=lf`、`*.cmd`/`*.bat eol=crlf`），**刻意不写 `* text=auto`** —— 仓库里 `demos/` 下大量易语言文本格式 `.txt` **本身要求 CRLF**，全局重规范化会制造巨量 diff 并可能破坏这些固定样本。加后确认**无意外重规范化**。

### 🟢 新增 7 项总检（81 → 88）

| 新增 | 作用 | 负向实验 |
|---|---|---|
| 第 8 项「跨技能运行期依赖」 | 扫 `scripts/*.py` 里对同级技能名的引用 → 依赖图显式化；要求在白名单内**且**消费者 SKILL.md 已声明同装 | ✅ 两个分支各验一次：① 删掉 `elang-build/SKILL.md` 里的 `elang-debug` → 报「没声明同装」；② 往 `elang-debug` 脚本塞一条 `e2txt-cli` 引用 → 报「没登记进 CROSS_DEP_ALLOW」 |
| 第 5 项扩充「dist 一致性」 | 按当前发布区**重新打包到临时目录**，与 `dist/*.zip` 比对 | ✅ 改过 SKILL.md 不重打包 → 报「内容不一致」 |

**比对方式刻意用「条目名 + 解压内容 md5」而非字节** —— 第一版按字节比对时，把测试副本 `cp -r` 一遍（mtime 变了）就误报；改成内容指纹后既不误报，又照样抓住了真实的「改过没重打包」。这点也是验收报告原先就建议过的比法。
