# 热重载崩溃根因诊断（2026-10-02）

> 现象：插件里用了 miniblink 浏览框之后，点「重载自身 / 重载插件」按钮 ⇒ **宿主进程直接结束**
> （ExitCode=0，日志断在半句，没有任何崩溃对话框）。不用浏览框则一切正常。

## 一、结论（一句话）

**插件的窗口过程（按钮、窗体）编译在插件 DLL 自己的映像里；宿主执行「重载自身」时先卸载了插件映像，
却没有销毁插件的窗口。** miniblink 的离屏重绘定时器让消息派发永不停止，user32 于是把消息派发给
「窗口还活着、窗口过程已随映像卸载」的窗口 ⇒ 跳到已释放的代码页 ⇒ 访问违例 ⇒ 宿主自己的致命错误
处理把进程收掉（表现为 ExitCode=0）。

这不是「FreeLibrary 失败 / 引用计数没清干净」——卸载**确实成功了**（模块表里那一行消失），
炸的是**卸载之后**。

## 二、证据链

| # | 证据 | 说明 |
|---|------|------|
| 1 | 模块表时间线 | 点击后 +0.43…0.64 s，插件缓存副本从模块表消失 ⇒ **卸载成功**；随后进程死亡 |
| 2 | 变体 D（完全不用 miniblink，重载按钮保留） | **存活**，日志里有真实的 `释放插件文件成功` + `载入成功` ⇒ 用户的「模块有问题」判断成立 |
| 3 | VEH 探针 | `异常 0xC0000005`，出错指令 `17xx27F2 ★不属于任何已加载模块`，故障地址 `MEM_FREE`，`size=2872KB` ⇒ 执行流跳进了**已释放的映像** |
| 4 | 调用栈 | `Esp+00` 返回地址 = `USER32.dll+0x3530F`（即 **user32 调用窗口过程的那条派发路径**）⇒ 被调用的是一个**窗口过程**，不是普通回调 |
| 5 | 窗口过程归属快照 | `Button 标题=重载插件 [proc=657bc290….dll+0xF0E84]`、`Button 标题=加载网页 [proc=同上]` ⇒ **按钮的窗口过程就在插件 DLL 里** |
| 6 | 消息跟踪 | `[MSG #21] 0x0201 WM_LBUTTONDOWN hwnd=Button[proc=657bc290….dll+…]`、`[MSG #60] WM_NULL hwnd=MiniBlinkTimerWindowClass/OffScreenTimer`（宿主过程）⇒ 点击和绘制 tick 都在往这些窗口派发消息 |
| 7 | 僵尸窗口 | 探针安装那一刻（**插件刚启动**）就已存在 `WTWindow 标题=XiaoLiZi_VM [proc=050E0000 ★不属于任何已加载模块]` ⇒ 宿主把**上一次**卸载掉的插件留下的窗口继续挂在窗口链上 |
| 8 | 二分实验 K | 只建视图 + `wkeSetHandle`，**不注册任何事件、不载网页** ⇒ **存活**；注册事件 + 载网页（有渲染流量）⇒ 崩 ⇒ 命案需要「注册给内核的回调 + 持续消息流量」这条链 |
| 9 | 拆解干净 | `mb.销毁 ()` 之后 MbKit 自检：**回调登记 0 个（存活 0）被挡 0** ⇒ 内核侧已无我们注册的回调可跳，**依然会崩** ⇒ 命案不在回调上 |
| 10 | 钉住插件映像（PIN） | 给插件映像加引用、不让卸载 ⇒ **访问违例彻底消失**（探针里连一条 AV 都没有）⇒ 反证命案就是「已卸载映像被调用」；但宿主因此无法完成重载 ⇒ **卡死**，所以不能这么修 |

## 三、为什么「只有用了 miniblink 才炸」

不用浏览框时，点击消息处理完消息队列就空了，卸载期间没有消息要派发给插件窗口 ⇒ 安全。
用了浏览框后，内核的 `MiniBlinkTimerWindowClass / OffScreenTimer` 约每 16 ms 产生一次离屏重绘
相关消息，窗口活动持续不断 ⇒ 卸载窗口期（约 30 ms）里几乎必然有一次派发落到插件窗口上 ⇒ 必炸。

## 四、可用处置

### 插件侧（能做的，已具备）
1. 重载前**同步**做完整拆解：`_设置窗口_将被销毁 ()`（→ `mb.销毁 ()`：还原宿主窗口、释放事件指针、
   `wkeSetHandle(view,0)`、`wkeDestroyWebView`）+ `销毁 ()` 销毁窗体；
2. 拆完**抽干消息泵**（`处理事件 ()` + 延时 + 再抽一次），让 `WM_DESTROY/WM_NCDESTROY` 与内核 tick 跑完；
3. 然后再 `Api.重载自身 ()`。

这样**本实例自己**的窗口不存在了，卸载空窗期没有可派发的目标。

### 宿主侧（**已在宿主源码中定位并打补丁**，见 §六）
宿主卸载插件 DLL 时**没有销毁该插件的窗口**（证据 7：探针在插件刚启动时就抓到一个 proc 已悬空的
`WTWindow 标题=XiaoLiZi_VM`）。只要这类僵尸窗口还在，任何消息（包括 miniblink 的绘制 tick）都会
踩空。正确做法：卸载插件前先销毁其全部窗口、撤掉定时器、排空该线程消息队列。

## 六、宿主侧根因（源码级定位 + 补丁）

### 6.1 卸载链（源码实证）

| # | 位置 | 关键代码 |
|---|------|----------|
| 1 | `代码\_应用API系统\API列表.static.e.txt:3207` `重载自身` | **不** FreeLibrary：`写出数据 (R, -77, index, path)` → `PoolOtherWorks.投递任务 (&system_work_set_t, R, )` |
| 2 | `代码\窗口程序集_界面.form.e.txt:2011` `system_work_set_t`（工作线程） | `Sleep (5)` → `system_work_set`（:1992）→ `标签_系统工作反馈.调用反馈事件 (2, ptr, )` ⇒ **把动作送回 UI 线程** |
| 3 | 同文件 `:1807` `_标签_系统工作反馈_反馈事件` | `行索引 = -77/-78`（:1845）⇒ `FreePlugin (user.列索引, 选择 (行索引 ＝ -78, 真, 假), 真)`；`-33`（卸载）走同一函数 |
| 4 | 同文件 `:2365` `FreePlugin` | ① 置禁用 → ② `Sleep (100)` → ③ 调插件卸载回调 `unaddr`／`banproaddres`（:2394-2399）→ ④ **紧接着** `FreeLibrary (到整数 (addres))`（:2407） |

⇒ **③ 与 ④ 之间没有任何窗口清理、没有 `处理事件`、没有延时。** 插件卸载回调一返回，
宿主立刻释放映像；此时插件窗体/控件窗口若还在（窗口过程就编在插件 DLL 里），
下一次 user32 派发消息就跳进已释放代码页。

原文（`FreePlugin` 卸载段）：

```e
            .如果真 (到整数 (addres) ＞ 0)
                FreeLibrary (到整数 (addres))
            .如果真结束
```

> 附带结论：**「FreeLibrary 在插件自己栈上执行」这个猜想是错的** —— 卸载动作早已被
> `调用反馈事件` 送回 UI 线程，在宿主自己的标签反馈事件里执行。真正的缺陷是
> 「卸载时插件映像的执行入口（窗口过程等）仍然活着且正在被派发」。

### 6.2 补丁 H1：卸载前接管插件窗口过程

`窗口程序集_界面.form.e.txt` 末尾新增两个子程序：

- `插件窗口接管 (模块句柄, 应用名, 文件名)`：用 `FindWindowExA` 遍历全部顶层窗口及其一级子窗口，
  对每个命中窗口改过程、计数、写日志；
- `接管单个窗口 (hwnd, 模块句柄, 默认过程, 明细)`：`GetWindowLongA (hwnd, -4)` 取窗口过程 →
  `GetModuleHandleExA (6, 过程, 所属模块)`（`FROM_ADDRESS|UNCHANGED_REFCOUNT`）判断该过程
  **是否正好落在本插件映像里** → 是则 `SetWindowLongA (hwnd, -4, DefWindowProcA)`，
  把窗口变成「只走系统默认过程」的死窗口。

调用点（`FreePlugin`，`FreeLibrary` 前一行）：

```e
            .如果真 (到整数 (addres) ＞ 0)
                插件窗口接管 (到整数 (addres), appname, filename)
                FreeLibrary (到整数 (addres))
            .如果真结束
```

新增 DLL 声明（`DLL.e.txt`）：`GetModuleHandleExA`（kernel32）。

设计取舍：

| 取舍 | 理由 |
|------|------|
| 只**换窗口过程**，不 `DestroyWindow` | 销毁会向仍在插件映像内的窗口过程发 `WM_DESTROY`，把执行流引回插件代码；换过程则此后该窗口只走系统默认过程 |
| 用「过程地址属于哪个模块」判归属，而非「地址落在 [base, base+size) 区间」 | 不需要解析 PE 头或 `VirtualQuery`，也不怕别的模块紧挨着放 |
| 用 `FindWindowExA (父, 前一个, 0, 0)` 链式遍历，不用 `EnumWindows` | **不需要回调函数**，在易语言里少一层出错面（消息专用窗口不在遍历范围，是已知覆盖缺口） |
| 只处理本进程窗口 | `GetWindowThreadProcessId` 结果与 `GetCurrentProcessId ()` 比对 |
| 写日志「卸载前已接管插件窗口过程 N 个：句柄表」 | PushOne（类型「插件(↓)」）⇒ 每次重载都能从日志判断这条链是否真的命中 |

## 七、根因修正 + 架构方向（2026-10-02 晚补，接手必读）

### 7.1 §六 的「窗口过程接管」**不是有效修复**，真凶是**消息钩子**

同日的 `交接文档-热重载修复（2026-10-02）.md` 给出了更硬的证据链：

* 出错指令恒定 `<插件映像基址>+0x327F2`，反汇编对得上
  `SetWindowsHookExW(3 /*WH_GETMESSAGE*/, 0x100327f2, NULL, tid)` ⇒ **是一个窗口消息钩子**，
  不是窗口过程，也不是消息专用窗口；
* 所以「枚举窗口 / 接管窗口过程 / 清僵尸窗口」（§6.2 的 H1）**全都抓不到它**——
  这正是此前多轮修复无效的原因；
* 有效修复在宿主侧：**装载插件后改写其导入表里的 `SetWindowsHookExA/W` 项**指向宿主代理 →
  代理记 `(lpfn, hhk)` 台账 → **`FreeLibrary` 之前**按"`lpfn` 是否落在本次要卸载的映像范围内"
  逐个 `UnhookWindowsHookEx`。实测连续 3 轮 `0xC0000005` = **0**（修复前每轮 1~3 次）。
* 归属判定用「地址属于哪个模块」（`GetModuleHandleExA(FROM_ADDRESS)`）而不是地址区间，
  所以**卸载 A 插件绝不会碰 B 插件的钩子** —— 多插件安全由这条保证。
* 注意钩子的来源：与插件静态链接的库里就有（`精易模块/DLL.e.txt` 里声明了 `SetWindowsHookExA`；
  易语言静态编译会把运行库/静态库链进 DLL 映像），**不是 miniblink 模块自己装的**。

### 7.2 新的架构方向：**node.dll 挪进辅助进程**

用户随后给了下一步方向（原话见下），已单独成文并**完成原理验证**：

> 「让 mbkit 作为中间件，让 node 绑定在 mbkit 的进程上，就相当于辅助进程……
> 需要重载插件的时候则销毁 mbkit 的进程，让 node 锁死的句柄释放。」
> 「多线程隔离……确保多个插件同时使用 miniblink 模块时，每个插件的 mbkit 不会互相打架。」

⇒ **`docs/方案-MbKit辅助进程架构（2026-10-02）.md`**（含 6 条实测证据：
跨进程离屏渲染 90.83% 非白、内核只在辅助进程、杀进程即释放并可重建、双客户端隔离、输入通路、动态内容）。

### 7.3 两条线是**正交**的，别互相替代

| 症状 | 归属 | 解法 |
|---|---|---|
| 插件卸载后钩子悬空 → AV（本命案） | 插件自己的钩子 | 宿主侧导入表拦截 + 按映像范围摘钩（§6.2 / 交接文档 §3） |
| 内核状态跨重载残留 / 换内核须重启宿主 / 多插件抢内核 | 内核归属 | **辅助进程**（新方案） |

**辅助进程不能替代摘钩补丁**：钩子是插件自己装的，搬到外进程也还在。
反过来，摘钩补丁也不能替代辅助进程：它不解决"内核锁死在宿主进程里"。

### 7.4 本文件 §四「宿主侧」的表述边界

§四说"宿主卸载插件 DLL 时没有销毁该插件的窗口 ⇒ 僵尸窗口"——这条**已被推翻**：
探针抓到的 `WTWindow 标题=XiaoLiZi_VM [proc 不属于任何模块]` 是**上上次**卸载留下的旁观现象，
不是本次命案的成因。以 §7.1 为准。
