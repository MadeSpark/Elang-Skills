# 分析：内存加载 PE 能否用于 miniblink · 多程序共用内核会怎样（2026-09-24）

> 回答两个问题：
> 1. **多个程序共用一个 `node.dll` 会不会受影响？**
> 2. 用户提供的 `PE加载器.zip`（手写机器码的内存加载例子）**能不能用**？
>
> 全部结论都有本次实测物证，脚本见 `re/pe_loader/`。

---

## 一、结论摘要

| # | 问题 | 结论 |
|---|---|---|
| 1 | 多程序共用一个 `node.dll` | **可以安全共用**（同一文件跨进程只共享只读页，可写状态各自私有）。但要接受 3 个代价：升级内核必须停掉所有用它的程序；缓存/用户数据目录要各程序分开；别让同一个进程出现两份内核。 |
| 2 | 用那个 PE 加载器做「内存加载」 | **映射器本身是好的，但对我们的场景不可用**。它能正确映射并调用导出，但映射出来的模块**不在 Windows 加载器链表里** ⇒ 易语言 `.DLL命令` 按名解析（= `LoadLibrary`）**够不着它**。要用就得放弃全部 252 个 `.DLL命令`，改成逐函数取地址调用，代价与风险都不可接受。 |
| 3 | 那现有方案（资源内嵌 → 落盘释放 → 预载 → 按基名复用）要改吗 | **不用改**。它就是「`.DLL命令` 可用」与「你不用再管那个 dll」两者的唯一可行交集。 |

## 二、Q2：PE 加载器实测

### 2.1 样本本身很薄

`PE加载器.e` 内是 4 个「`置入代码` 手写机器码」子程序：`运行内存EXE` / `加载内存DLL` /
`卸载内存DLL` / `MyGetProcAddress`。它自实现的是一条完整的手工映射流程
（PEB 找 kernel32 → 取 `VirtualAlloc`/`VirtualFree` → 校验 `MZ` → 按节拷贝 →
解析导入 → 应用重定位 → 调 `DllMain`；`卸载内存DLL` 则是 `DllMain(DETACH)` + `VirtualFree`）。

配套样本 `test.dll` / `test.exe` 各 688 / 1536 字节：**两个都没有导出表**
（`test.dll` 只在 `DllMain` 里弹个消息框），只导入 1~2 个函数。
⇒ `MyGetProcAddress` 这条最关键的能力**在原样本里根本没被验证过**。

所以我自己造了一个真实些的对照 DLL（`re/pe_loader/exp/expdll.c`，85 KB，
17 个节、带 `.tls`、导入 kernel32/msvcrt/USER32 共 40+ 个函数、7 个具名导出、
`DllMain` 写文件留痕），再逐项验证。

### 2.2 结果：映射器是**能用**的

| 验证项 | 实测结果 |
|---|---|
| 映射并拿到基址 | ✅ `0x02800000`，该地址处签名 = `MZ` |
| 导出按名解析 | ✅ 7 个导出全部取到；`Add2` 得到 `基址+0x1480`，与 PE 导出表里的 `RVA=1480` **完全一致** |
| **真的能调用**（cdecl 无参/1 参/2 参） | ✅ `Const7()=7`、`Echo1(12345)=12345`、`Echo2(1,2)=102` |
| **真的能调用**（stdcall） | ✅ `Add2S(1,2)=1003` |
| 导入表解析 | ✅ 依赖 `kernel32`/`msvcrt`/`USER32` 的函数都能跑 |
| 重定位 | ✅ 实际映射基址 `0x02800000` ≠ 镜像首选基址，说明 `.reloc` 被正确应用 |
| `DllMain` 被调用 | ✅ 落盘痕迹里出现 `DllMain ATTACH base=02800000` |
| `卸载内存DLL` | ✅ 返回真，且痕迹里有对应的 `DETACH` |

### 2.3 结果：但**决定性的一条是坏的**

| 观测 | 实测值 | 含义 |
|---|---|---|
| `GetModuleHandleA("expdll.dll")` | `0x7B060000` | **不是**映射基址 `0x02800000` ⇒ 映射模块**不在加载器链表里** |
| `LoadLibraryA("expdll.dll")` | `0x7B060000` | 又加载了**第二份**（磁盘上的） |
| `DllMain` 调用次数 | **2 次 ATTACH**（`base=02800000` 与 `base=7B060000`） | 铁证：同一进程里两份并存 |
| 映射副本内 `GetModuleHandleA("expdll.dll")` | `0` | 映射副本**连自己都查不到** |

⇒ 易语言 `.DLL命令` 的解析路径就是 `LoadLibrary(名字)` + `GetProcAddress(入口名)`。
`LoadLibrary` 只认**加载器链表**与**磁盘**，所以它永远命中不到手工映射的那一份。

### 2.4 实验中途踩的坑（顺带产出的知识）

第一版探针「调用成功却永远返回 0」。用**同一份 DLL 的磁盘副本**做对照也是 0，
就把嫌疑人锁定在调用外壳上。反汇编最终 exe 后真相是：

```
FF D0            call eax          ; ← 结果在 eax
B8 00 00 00 00   mov  eax, 0       ; ★ 这是易语言为 `返回 (0)` 生成的
```

**机器码把结果放进 `eax`，紧跟着的 `mov eax, 0` 把它盖掉了。**
而原样本那三个子程序同样写 `返回 (0/假)` 却能拿到返回值 —— 因为它们的机器码块
**自带 `leave; ret N`**（实测其静态编译产物里，`加载内存DLL` 的片段在 `0x255F` 处就是
`C9 C2 04 00`），控制流根本不回到那句 `mov eax, 0`。

已把这条例写进 `docs/置入代码与机器码.md` §7.2（连字节证据），
并在 `docs/Win32与DLL互操作.md` 新增 §1.1（`.DLL命令` 惰性解析 + 手工映射够不着）。

## 三、Q1：多程序共用一个 node.dll

### 3.1 实测：两个进程同时用**同一个** node.dll 文件，都正常

`re/pe_loader/share_two.py`：

- 内核只有一份：`share/kernel/node.dll`（33,600,512 B，md5 `154e9143…`）；
- A、B 两个目录各一份 `probe.exe`，都用 `WKE设置node路径` 指到**同一个**内核；
- **同时启动**。

| 实例 | `wkeIsInitialize` | 内核状态 | 内核路径 | 本目录 MbKit.dll |
|---|---|---|---|---|
| A | 1 | 已加载 | 同一个 `kernel\node.dll` | 56,320 B（自己的） |
| B | 1 | 已加载 | 同一个 `kernel\node.dll` | 56,320 B（自己的） |

⇒ 共用同一份内核文件、同时运行，**互不影响**。
（复现 3 次结果一致。）

### 3.2 实测：内核**不派生任何子进程**

运行期间按 0.05 s 采样进程表并抓新进程的**路径与父进程**。唯一反复出现的新进程是
`Appvant.exe`，抓到的路径是 `C:\Program Files (x86)\Lenovo\PCManager\…\Appvant.exe`、
**父进程是 explorer.exe** —— 是联想电脑管家的常驻监控（它盯着进程创建，所以总在新进程
出现时冒头），与内核无关。单独跑一个探针时**一个新进程都没有**。
⇒ 内核不 spawn 子进程，不存在「多个程序争抢同一个 helper 进程」的问题。

### 3.3 实测：内核文件的锁语义（Win32 API 直调，避免被 safe-delete 包装层干扰）

| 状态 | 就地覆盖写 | 真删除 | 改名 | 改名后原位放新文件 |
|---|---|---|---|---|
| 未加载 | ✅ 允许 | ✅ 允许 | — | — |
| **被加载中** | ❌ 被拒 `err=32`（共享冲突） | ❌ 被拒 `err=5`（拒绝访问） | ✅ **允许** | ✅ **允许** |
| 退出之后 | ✅ 允许 | ✅ 允许 | — | — |

⇒ 「程序都在跑就升不了级」的根因是 **`ERROR_SHARING_VIOLATION`**；
但 Windows **允许改名**，而且改名后能在原路径放一份新的 ⇒ 存在
「改名腾位 → 放新内核」这条不停机升级路径（代价：老程序继续用旧内核、新程序用新内核，
版本会**同时存在**）。

### 3.4 机制：为什么共用没事

- 同一份 DLL 文件在多个进程里映射为**同一个 image section**：**只读代码/只读数据**的物理页
  **共享**（所以内存不会 N 倍膨胀）；
- **可写数据段、堆、TLS、句柄表**每个进程**各自私有**（写时复制）⇒ 内核全局状态、视图、
  回调互不可见、互不干扰；
- `node.dll` 不导入任何跨进程单例（无 `CreateMutex` 用于单例、无命名管道服务端），
  实测也不派生进程 ⇒ 没有跨进程的争用点。

### 3.5 真正要注意的三件事

| # | 坑 | 处理 |
|---|---|---|
| ① | 升级/替换内核要停掉所有用它的程序（`err=32`/`err=5`） | 要么全部退出后换；要么「改名腾位」新老并存（注意版本不一致） |
| ② | **缓存 / cookie / 本地储存目录**才是跨程序真正会打架的地方 | **每个程序给独立目录**（`MB浏览框` 有 `Cookie置全路径` / `置本地储存全路径`） |
| ③ | 别让**同一个进程**出现两份内核 | MbKit 已是唯一持有入口（懒加载 + 单份）；不要在工程里另写一条路径自己 `LoadLibrary` |

补充：本套装默认就把 `MbKit.dll` 释放到**各自宿主 exe 目录**并且同尺寸即复用，
所以 N 个程序 = N 份 56 KB 的 MbKit，**彼此不互锁**；只有 `node.dll` 才是「可以共享、
也可以各自一份」的那个。

## 四、顺带修掉的两个工具误报（`echeck.py`）

写这次实验时被两个噪音警告挡住，查实都是误报，已修：

| 误报 | 根因 | 修法 |
|---|---|---|
| `置入代码 ({ ... })` 报「最多 1 个参数，给了 N 个」 | 参数切分只把 `(` `)` 算作嵌套，**没算 `{}`**；字节集字面量里的逗号被当成参数分隔符。一个手写机器码模块会一次报 7 个 ✗，把真问题淹掉 | `split_args` / `parse_calls` 把 `{}` 也计入嵌套深度。回归：用户给的原始工程从 **7 错 → 0 错** |
| `_P_xxx` 报「命令不在支持库清单里」 | 检查器不认识 `.DLL命令` 声明的名字（它们在外部 DLL 里，不在支持库清单里） | 新增 `collect_dllcmds()`，把 `.DLL命令` 名连同参数个数收成已知命令 |

回归结果：`re/pe_loader/txt`、`re/pe_loader/proj`、`re/opt/e2e/proj`、`re/opt/e2e2/proj` 全部 **0 错 0 警**；
模块文本 `re/opt/build_txt` **0 错 1 警**（`右移` 第 3 参数，既有问题，与本次无关）。

## 五、复现

```bash
PY="<python>"
$PY re/pe_loader/build_probe.py                 # 生成实验工程（逐字搬运样本的机器码子程序）
$PY tools/echeck.py re/pe_loader/proj           # 静态检查
$PY tools/ecompile.py re/pe_loader/proj re/pe_loader/out/probe_pe.exe \
        --kind static_console --workdir re/pe_loader/work   # 真编译
cd re/pe_loader/out && ./probe_pe.exe           # 看 peexp.log / dllmain_ran.txt
cd ../.. && $PY re/pe_loader/share_two.py       # Q1：两进程共用同一内核
$PY re/pe_loader/lock_test.py                   # Q1：内核文件锁语义（Win32 API 直调）
$PY re/pe_loader/catch_appvant.py               # 新进程溯源
$PY re/pe_loader/all_imports.py <pe> [关键词]   # 全量导入表
```

物证：`re/pe_loader/out/peexp.log`、`re/pe_loader/out/dllmain_ran.txt`、
`re/pe_loader/share/{A,B}/probe.log`。

> 注意：`holder.exe` / `probe_pe.exe` 都是 32 位；`LoadLibraryA` 收到**被写坏 `MZ` 头**的文件时
> 报的是 `err=193`（`ERROR_BAD_EXE_FORMAT`）而不是「找不到」——写锁实验时别把这两个混淆。
