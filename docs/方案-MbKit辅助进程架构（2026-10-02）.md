# 方案：MbKit 辅助进程架构 —— node.dll 挪进独立进程（2026-10-02）

> 用户的修复方向（原话）：
> 1. 「node 会锁死当前进程第一个初始化的句柄，已是无法突破的限制 ⇒ 让 mbkit 作为中间件，
>    让 node 绑定在 mbkit 的进程上，就相当于辅助进程，在需要的时候创建它，接住 node 的句柄锁死；
>    在需要重载插件的时候则销毁 mbkit 的进程，让 node 锁死的句柄释放。」
> 2. 「热重载仅仅只是第一步，要做好多线程隔离……确保多个插件同时使用 miniblink 时，
>    每个插件的 mbkit 不会互相打架（已知 node 是支持共享调用的）。」
>
> 本文档回答：**这条路怎么走**，以及**哪些已经在本机用真 node.dll 实测通过**。

---

## 0. 一句话

把 `node.dll` 从宿主进程里搬走，放进一个**按需拉起、可随时销毁的辅助进程**；
宿主进程里只留一个**瘦客户端桩**，它只做三件事：**收帧（共享内存 `SetDIBitsToDevice`）
+ 转输入（`wkeFireMouseEvent` 家族）+ 转发上层的 `MbKit_*` 调用**。
插件映像里从此**没有任何内核状态**，所以插件的卸载/重载不再受内核影响；
要彻底重来一遍内核时，杀掉辅助进程即可（锁随进程消亡）。

**已有实测证据**（`src/mbkit/host/`，本机真 `node.dll` 33.6 MB，2021-03-10 build）：

| # | 命题 | 结果 |
|---|---|---|
| 1 | 页面能在辅助进程里渲染出来，并跨进程显示到客户端窗口 | ✅ 非白像素 **90.83%**（267040/294000），窗口画面与共享帧**逐像素一致** |
| 2 | 内核**只**在辅助进程里 | ✅ 客户端进程模块表里**从未**出现 `node.dll`（4 个辅助进程 pid 全部命中，base 均为 `0x78F10000`） |
| 3 | 杀掉辅助进程 = 释放 node 锁，可重新初始化 | ✅ 同一客户端杀进程后重新拉起，**188 ms 载入完成**，页面照常渲染 |
| 4 | 多插件（多客户端）互不干扰 | ✅ 2 客户端 → 2 组独立辅助进程（各自 0.3–3.5 s / 4.3–16.1 s 两代），各画各的 |
| 5 | 输入通路 | ✅ 窗口消息 → 跨进程 → 内核 → 页面 JS（`title` 回传为证：`CLICK 3 at 350,200`） |
| 6 | 动态内容 | ✅ JS `setInterval` 改 DOM 每秒都在变（帧 hash 每秒不同）；14 s 内内核自发失效 27 次 ≈ JS 每 500 ms 一次变更 |

## 1. 为什么**不能**走「跨进程父子窗口」，必须走「离屏 + 共享内存」

第一直觉是：辅助进程建一个窗口，用 `SetParent` 挂到插件的窗口上 —— 画面、输入天然就有了。
**这条路必须放弃**，两条硬证据：

1. Raymond Chen（微软）《Is it legal to have a cross-process parent/child or owner/owned
   window relationship?》：
   > *"Yes, it is technically legal. It is also technically legal to juggle chainsaws. …
   > Creating a cross-thread parent/child … implicitly attaches the input queues …
   > things will definitely stop working if you change that other window from a top-level
   > window to a child window."*
   —— 跨进程父子关系会把两个进程的**输入队列绑死**，且"合法但不推荐"。
2. 社区实测（SO 75060992）：跨进程 reparent 的窗口会**随机丢按键**（`WM_KEYDOWN` 到了、`WM_CHAR` 丢了）。
   而且插件窗口属于宿主进程、辅助窗口属于辅助进程，**两边都"不知道自己被卷进了跨进程窗口树"**。

⇒ 采用**纯应用层**的合成方案（也是浏览器的通行做法）：辅助进程把内核的 view DC
`BitBlt` 进一块**共享内存 DIB**，客户端在 `WM_PAINT` 里用 `SetDIBitsToDevice`
把它贴到自己窗口上；输入则由客户端把窗口消息编组过去，辅助进程用
`wkeFireMouseEvent/wkeFireKey*` 喂回内核。**没有任何跨进程窗口关系，零平台灰色地带。**

## 2. 进程模型与隔离模型

```
┌──────────────────────────── 宿主进程（框架 exe）─────────────────────────────┐
│  插件 A.dll（易语言，编译进来的 miniblink 模块）                              │
│      │  MbKit_xxx / wke* 转发                                              │
│      ▼                                                                     │
│  MbKit20.dll  ← 客户端桩（自 PIN，永不卸载；DLL 内按"调用方模块"分客户端槽）    │
│      · 子类化插件窗口（画帧 + 收输入）—— 过程在**桩**里，不在插件映像里          │
│      · 事件回调转发前做三重存活校验（复用 mbkit.c 的 view_cb_alive）           │
│  ┌────────────┬────────────┬────────────────────────────────┐              │
│  │ 客户端槽 A │ 客户端槽 B │ …（每个插件一个）               │              │
│  └─────┬──────┴─────┬──────┴─────────────────────────────────┘              │
└────────┼────────────┼──────────────────────────────────────────────────────┘
         │ IPC        │ IPC     （命名对象带客户端序号 ⇒ 天然隔离）
         ▼            ▼
   MbKit20Host.exe  MbKit20Host.exe      ← 每个插件一个辅助进程，互不相识
     node.dll         node.dll
     wke view         wke view
```

**隔离的三个层次（缺一不可）**

| 层次 | 做法 | 解决什么 |
|---|---|---|
| **进程** | 一客户端一辅助进程（默认） | 内核全局状态、崩溃、`TerminateProcess` 全部互不影响；杀 A 不碰 B |
| **命名空间** | `MbKitCh_<客户端序号>_<pid>_…` 的 ctl / frame / evt 对象名 | 即使有人误开共享，也不会串台 |
| **会话表** | 桩内 `view 句柄 ↔ 客户端槽` 的映射；辅助进程只认自己那一套 | 上层拿到的是**桩自己的** view 令牌，不是内核指针；跨客户端不可能误用 |

**客户端怎么识别"我是哪个插件"**：桩用 `_ReturnAddress()` + `GetModuleHandleExA(FROM_ADDRESS)`
取调用方模块 —— 也就是那个插件 DLL。所以**模块自己不用改一行**，
同一个 `MbKit20.dll` 被 N 个插件共用时，自动裂成 N 个客户端槽、N 个辅助进程。
（这也顺手解决了老架构里"MbKit.dll 被别的插件抢基名"那个坑。）

**共享模式（可选，默认关）**：`MBKIT_SHARE=1` 时所有客户端槽共用一个辅助进程、各占一个 session；
省内存、省一次内核初始化（33 MB node.dll 只载一次），代价是一个内核死了全死。
用户明确说过"node 是支持共享调用的"，所以这条留成开关而不是默认。

## 3. IPC 契约（`src/mbkit/host/mbk_ipc.h` 已落地并跑通）

| 对象 | 大小 | 方向 | 内容 |
|---|---|---|---|
| `ctl`（file mapping，4096 B） | 固定 | 双向 | 状态机、帧序号/脏矩形、命令槽、**输入环**、标题/错误文本、诊断计数 |
| `frame`（file mapping） | `w*h*4` | 辅助→客户端 | 32bpp 自顶向下 BGRA，`biHeight = -h`，stride = `w*4` |
| `evt`（事件） | — | 辅助→客户端 | 帧发布通知（`SetEvent`） |

**零拷贝**：辅助进程 `CreateDIBSection(..., hSection = 共享段, 0)` 让 GDI 的位图**直接坐在共享内存上**
（实测一次成功，日志 `[2] DIB 直接坐在共享内存上（零拷贝）`）；
客户端不需要 DIB，直接 `SetDIBitsToDevice(hdc, …, 共享指针, &bi, DIB_RGB_COLORS)`。
保留 `CreateDIBSection(hSection)` 失败时"私有位图 + 手工 `memcpy`"的兜底分支。

**为什么 ctl 和 frame 分成两段**：`CreateDIBSection` 的 `hSection` 视图**必须从 0 偏移开始**
（Windows 要求映射偏移按 64 KB 分配粒度对齐）。分两段就不用碰这个坑。

**同步**：单生产者/单消费者；发布者**最后写序号**（`MemoryBarrier` + `InterlockedIncrement`），
消费者只在序号变化时读数据。输入环同理（客户端最后写 `inHead`）。
> 未做：**双缓冲帧**。当前单缓冲在高频刷新下可能撕裂（实测肉眼不可见，但理论存在）。
> 真实版本建议 `frame[2]` + `frameIndex`，客户端读 `frameIndex^1`。

## 4. 生命周期：按需创建 / 销毁即释放

```
插件首次调用 MbKit_创建
        └─► 桩：客户端槽不存在？→ CreateProcess(MbKit20Host.exe) → 等 status>=READY
插件要重载（模块的 将被销毁 / 销毁 路径）
        └─► MbKit_卸载辅助进程()  →  TerminateProcess  →  node.dll 随进程消亡（锁释放）
                                   └─► 下一次 MbKit_创建 会重新拉一个干净的
```

**三层兜底**（辅助进程不能变成僵尸）：

| 兜底 | 机制 | 状态 |
|---|---|---|
| 客户端主动杀 | `MbKit_卸载辅助进程()`（重载/退出时调） | 已实测 |
| 客户端进程崩了 | 辅助进程等 `ctl` 句柄的被杀通知（`WaitForSingleObject(hClientProcess)` 或轮询 `ctl->clientPid` 是否还在） | **待实现** |
| 会话闲置 | 最后一个 view 销毁后 N 秒自杀（可配；默认关，避免频繁重建 33 MB 内核） | **待实现** |

> 反之也要防"辅助进程先死"：桩必须在每次 IPC 前检查 `WaitForSingleObject(hiProcess, 0)`，
> 发现死了就地降级（返回 0 + 记 `LastError`，必要时自动重启辅助进程 + 重放"载入"命令）。
> 这条**必须做**：它把"内核崩了"从"宿主崩了"降级成"网页白了然后自己恢复"。

## 5. 渲染循环：辅助进程是个**自驱帧源**

实测数据（14 s）：

| 指标 | 值 | 含义 |
|---|---|---|
| 辅助进程 render tick | 828 | ≈ 59 fps（15 ms 一拍） |
| 辅助进程 BitBlt 帧数 | 1293 | 每拍都出帧 |
| **内核自发失效 `kernelInvalidates`** | 27 | ≈ **2/s**，与页面里"每 500 ms 改一次 DOM"**精确对应** |

⇒ 两点结论：

1. 内核**会**因内容变化要求重绘（27 ≈ 14 s / 0.5 s），所以不必每次全屏重传；
2. 但**不能只依赖它**：首次载入、窗口离屏、以及内核自己的定时器被节流时它不叫。
   ⇒ 辅助进程保留 `15 ms` 的**自驱 tick**（`wkeRepaintIfNeeded` + `BitBlt`）当兜底；
   真实版本应升级为「内核叫了就只传脏矩形，没叫就低频心跳」。

**离屏窗口的形态**（实测可用）：`CreateWindowExA(WS_EX_TOOLWINDOW|WS_EX_NOACTIVATE,
WS_POPUP|WS_VISIBLE, -4000, -4000, w, h)` —— 屏幕外但 `WS_VISIBLE`。
内核要求"有窗口 + 有消息循环"（见 `docs/方案-MbKit-miniblink热重载（2026-09-23）.md` §2 与
README「v1.4 属主直通」），而窗口**在哪一进程并不重要** —— 这正是本次验证成立的前提。

## 6. 输入通路（两个实测的坑，都踩过）

**接口选择**：不用 `wkeFireWindowsMessage`，用**粒度 API**：

| 客户端消息 | 辅助进程调用 | 参数映射 |
|---|---|---|
| `WM_MOUSEMOVE/LBUTTON*/RBUTTON*/MBUTTON*/…DBLCLK` | `wkeFireMouseEvent(view, msg, x, y, flags)` | `flags = wParam & (MK_LBUTTON\|MK_RBUTTON\|MK_SHIFT\|MK_CONTROL\|MK_MBUTTON)` |
| `WM_MOUSEWHEEL` | `wkeFireMouseWheelEvent(view, x, y, delta, flags)` | **lParam 是屏幕坐标，要先 `ScreenToClient`** |
| `WM_KEYDOWN/UP` | `wkeFireKeyDownEvent/UpEvent(view, vk, flags, false)` | `flags = (KF_EXTENDED?0x0100:0) \| (KF_REPEAT?0x4000:0)` |
| `WM_CHAR` | `wkeFireKeyPressEvent(view, ch, 0, false)` | — |
| `WM_SETFOCUS/KILLFOCUS` | `wkeSetFocus/KillFocus(view)` | — |

> **wke 的鼠标 flags 与 Windows 的 `MK_*` 数值完全一致**（`WKE_LBUTTON=0x01, WKE_RBUTTON=0x02,
> WKE_SHIFT=0x04, WKE_CONTROL=0x08, WKE_MBUTTON=0x10`，见 `wke.h`），所以可以直接位透传。

### 坑 1：`wkeFireWindowsMessage` 会**永久卡死**辅助进程（实锤）

第一版就是拿它透传原始消息，结果：日志停在 `[in>] msg=0x0200 …`，`[in<]` 再也不来，
`renderTick` 冻结、页面永远停住、进程还活着。
（`inCount` 是在调用**之后**自增的，所以表面现象是"输入一个都没转发"，很容易误判成"客户端没发"。）
⇒ **把它从输入路径上彻底剔除**。文档里也提到它"目前 mb 主要用来处理光标相关"，本来就不适合当总入口。

### 坑 2：**页面载入完成前**灌输入，同样会卡死

第二版用粒度 API，但没加就绪门禁，结果又是 `tick` 停在 0。
⇒ 输入必须门禁在 `status >= MBK_ST_LOADED`；就绪前的输入**直接丢**（不排队，避免就绪后突然补放一串旧消息）。
实测：`drop=1`（载入期间那 1 条被丢），之后 9 条正常转发。

### 端到端证据

```
客户端(窗口过程) → 输入环 → 辅助进程 wkeFireMouseEvent → 内核 → 页面 JS
                                                            └─ document.title = "CLICK 3 at 350,200"
                                              辅助进程轮询 wkeGetTitleW → ctl->title → 客户端日志
```
三次点击后客户端日志里的 title 序列全部变成 `CLICK 3 at 350,200`；
截图（`src/mbkit/host/shot_click.png`）里页面写的是 `JS tick 26 点击=3 动态内容已更新`。

## 7. 客户端桩要接的活（下一阶段的主体）

| 职责 | 说明 | 为什么必须在**桩**里做 |
|---|---|---|
| 窗口子类化 | `SetWindowLongPtrW(hwnd, GWLP_WNDPROC, 桩的proc)`，保留原过程链尾 | 过程必须钉在**永不卸载**的模块里，否则重载时"窗口还活着、过程已随映像卸载" ⇒ 就是当前命案的翻版 |
| `WM_PAINT` | 贴共享帧（脏矩形） | 插件自己画不出来（内核在别的进程） |
| 输入转发 | 见 §6 | 内核**无法**子类化别的进程的窗口（跨进程 subclass 不可能） |
| 事件回调转发 | `MB_EV_LOADED/…` 回来前做**三重存活校验** | 回调地址在插件映像里，插件可能已被卸载（`mbkit.c` 里 `view_cb_alive` 直接复用） |
| `DetachAll` | 撤子类化 → 还原原 WndProc → 销毁 view → 杀辅助进程 | 撤销动作必须幂等、可重入 |

**API 面（保持与老 `MbKit141.dll` 同名同参，模块侧改动最小）**：
生命周期/视图/导航/诊断四组照旧；新增 `MbKit_卸载辅助进程`、`MbKit_辅助进程状态`、
`MbKit_帧序号`、`MbKit_输入转发次数`（后两个是自检用）。

**必须诚实标注"跨进程后不好使"的那部分**：模块里 306 个 `wke*` 转发导出，分三类：

| 类 | 例子 | 处理 |
|---|---|---|
| ① 可编组 | 建/销/载入/resize/缩放/取标题/取URL/是否载入完成/输入 | 直接 IPC |
| ② 要回值或指针 | `jsEvalW` `jsCall` `jsGet*` `wkeGetCookie*` `wkeNetHookRequest` | 需要序列化。**建议只保留"文本域"窄接口**（JS 求值返回字符串、Cookie 走字符串），别试图把 `jsValue` 搬过进程边界 |
| ③ 绝不可跨进程 | 任何"回调进插件映像"的注册（事件、资源拦截、下载回调） | 由桩代理：桩注册自己的回调 → 存活校验 → 转发给插件 |

## 8. 与宿主侧钩子补丁的关系：**正交，都要有**（必须说清）

热重载那次命案（`docs/诊断-热重载崩溃根因（2026-10-02）.md`）的真凶是
**插件映像里的消息钩子**（`SetWindowsHookExW(WH_GETMESSAGE, lpfn)`，`lpfn` 落在插件映像内；
调用点来自与插件静态链接的库 —— `精易模块/DLL.e.txt` 里确实声明了 `SetWindowsHookExA`），
配合 miniblink 的 16 ms 绘制 tick 提供"永不间断的消息流量"，在 `FreeLibrary` 后的空窗期被 user32
派发 ⇒ `0xC0000005`。这条链 **辅助进程解决不了**：钩子是插件自己装的。

所以要**分工**：

| 症状 | 归属 | 解法 |
|---|---|---|
| 插件卸载后钩子悬空 → AV | 宿主侧（已打补丁 v5，实测 3 轮 AV=0） | 装载后改写 `SetWindowsHookExA/W` 导入项 → 台账；`FreeLibrary` 前按映像范围摘钩 |
| 内核全局状态跨重载残留 / 换内核必须重启宿主 / 多插件抢内核 | **本方案** | 辅助进程；杀进程即释放 |
| 客户端桩自己不能在插件映像里留过程 | 本方案 | 子类化/回调全放自 PIN 的桩里 |

> 换句话说：辅助进程让"内核"这件事变得**可回收、可隔离**；摘钩补丁让"插件自己的钩子"不再踩着
> 已卸载的映像。两者叠加才是"随便重载、多个 miniblink 插件共存"的完整答案。

变的只是实现走 IPC；真正要动的是**模块里那些回调**（`事件_载入完成` 等）——
它们现在由桩在存活校验后调用，语义不变。

## 10. 未做 / 风险（诚实标注）

* **帧未双缓冲**：高频刷新理论可撕裂（实测肉眼未见）。
* **IME/输入法**：跨进程后 `WM_IME_*` 与 caret 位置需要额外转发（`wkeGetCaretRect` 是跨进程的，
  但 `ImmSetCandidateWindow` 要在宿主进程做）。**未做**。
* **拖拽/光标形状**：`wkeGetCursorInfoType` → `SetCursor` 的回路**未接**（现在鼠标形状永远是箭头）。
* **JS/Cookie/下载类导出**：见 §7 三类划分，第二/三类**未实现编组**。
* **内存**：一插件一进程 = 一份 33 MB 的 `node.dll` 映射 + 内核运行时。
  3 个插件同开约多占几百 MB。可切 `MBKIT_SHARE=1` 换共享。
* **只在 32 位 / 本机这一份内核上实测**（blink 98096，2021-03-10）。换内核要重跑。
* **辅助进程被杀时的自愈**：桩现在会 `TerminateProcess`，但**没做**"辅助进程意外死亡 → 自动重启并重放页面"。
* **崩溃隔离的红利尚未拿到**：现在内核崩了还是会连带影响画面（虽然主进程能活）——需要 S2 的自愈闭环。

## 12. S2 实施设计（2026-10-02 晚补 —— 可直接开工）

### 12.1 现有代码给了什么（关键利好）

| 事实 | 出处 | 意义 |
|---|---|---|
| **全部内核调用已收口在一个函数** | `mbkit_fwd.c: mbk_marshal_exec()` | 换通道只改这一处（+ 生成器），252 个导出一个都不用动 |
| 编组载荷带**可移植下标** `idx` | `mbk_marshal.h: MBKCALL.idx` | 两侧都是同一份 C 代码 ⇒ `mbk_slots[idx]` 指向同一个 API，**指针不用传** |
| K 侧执行体是表驱动 | `gen_thunk.c` / `mbk_tramps[]` | 辅助进程直接复用，不需要为每条 API 写 RPC |
| 签名元数据现成 | `src/mbkit/fwd_list.json`（252 条，含逐参类型） | 编组语义可**自动推导**，不用手写 |
| 离屏渲染/共享内存/杀进程重载/双客户端/输入 | `src/mbkit/host/`（§0 六条实测） | 传输层可以直接抄 `mbk_ipc.h` + `spike_host.c` |

### 12.2 参数元数据（从 `fwd_list.json` 实测统计出来的工作量）

| 类别 | 数量 | 处理 |
|---|---|---|
| 纯标量/句柄（`整数型/字节型/长整数型/小数型/双精度`） | ~160 条 API | **直接塞 8 字节槽透传**。句柄（`wkeWebView/jsValue/wkeString/jsExecState/wkeNetJob`）客户端从不解引用 ⇒ 当不透明值用 |
| **需拷入的指针入参** | **53 条 API** | 见下表 |
| **返回内核自持字符串** | ~15 条（`wkeGetTitleW` `wkeGetURL` `wkeGetStringW` `jsEvalW` `jsToStringW` `wkeNetGetUrlByJob` …） | 返回值在**辅助进程地址空间**，必须拷回客户端暂存区再返指针 |
| **回调登记** | 22 条（`wkeOnXxx`） | 见 §12.4 |
| **必须特判** | `wkeSetHandle` / `wkeSetHandleOffset` | 客户端窗口句柄在**客户端进程**，辅助进程要用自己的离屏窗口 ⇒ 桩记下客户意图、通知辅助进程改用离屏 hwnd |

53 条指针入参的细分：

| 易语言类型 | 条数 | 跨进程语义 |
|---|---|---|
| `文本型` | 41 | 客户端进程内的 **ANSI 串指针** ⇒ 辅助进程 `ReadProcessMemory` 读到 NUL |
| `字节集` | 18 | 客户端进程内的**宽字节缓冲** ⇒ 长度取 `[ptr-4]`（易语言字节集头），或按 `*W` 名字走 NUL 扫描 |
| `_结构...` | 3（`wkeSetDragFiles` / `wkeGetCaretRect`） | 定长结构 ⇒ 按 `struct.e.txt` 定义拷入/拷出 |

> 辅助进程对客户端进程 `OpenProcess(PROCESS_VM_READ|VM_WRITE|VM_OPERATION)` —— 这是它能读客户端字符串的**唯一**依据。
> 反过来输出（§12.3）走共享内存 blob，不必给客户端反向句柄。

### 12.3 编组协议 v2（在 v1 上加两样东西）

```
MBKCALL 在 v1 基础上扩展：
  int   idx;            // 相同（可移植）
  long long a[12];      // 相同；指针型入参填「blob 内偏移」而不是客户端地址
  int   kind;
  union ret;            // 相同
+ int   blobIn;         // 入参 blob 字节数（0 = 无）
+ int   blobOut;        // 出参 blob 字节数（辅助进程回填）
+ int   retIsText;      // 1 = 返回值是指向内核字符串的指针 ⇒ 已拷进 blobOut
```

调用方（桩）流程：
1. 按签名把 `文本型/字节集/结构` 参数**序列化进一个暂存 blob**，`a[i]` 改成 blob 内偏移；
2. 投递 `{idx, a[], kind, blobIn, blob}` 到辅助进程；
3. 辅助进程 `ReadProcessMemory` 不需要 —— blob 已经拷过来了；把 blob 复原成辅助进程本地缓冲，再按 `mbk_tramps[idx]` 执行；
4. 若 `retIsText`，辅助进程把返回的字符串拷进回程 blob 并置 `blobOut`；
5. 桩把回程 blob 写进自己的暂存区，返回**本进程内的指针**（调用方 expect 的就是「能用的指针」，语义不变）。

> 为什么不做「辅助进程反向 `ReadProcessMemory` 客户端」：那要求辅助进程能读到客户端的**临时/栈**内存（可行但脆），而且每次调用都多一次 RPM。blob 单向拷贝更确定。

### 12.4 回调代理（22 条 `wkeOnXxx` + `jsBind*`）

```
客户端桩：wkeOnTitleChanged(view, fn, param)
   ├─ 桩本地登记 (view, 事件类型, fn, param) —— fn 落在插件映像里，只在客户端有效
   └─ 发给辅助进程：注册 **辅助进程自己的** 同名事件 trampoline（带事件类型号）
辅助进程：事件触发
   ├─ 事件载荷序列化（如标题字符串）写进「事件环」（共享内存，与输入环同构）
   └─ SetEvent
客户端桩：消费事件环 → 查表拿到 (fn, param) → **在客户端进程里调用 fn(param, ...)**
           ★ 调用前做三重存活校验（复用 mbkit.c 的 view_cb_alive）：插件可能已被卸载
```

要点：**回调函数体永远在客户端进程执行**（那是它的家），辅助进程只负责「事件发生」这件事。
这同时把「插件卸载后回调火进已释放映像」这条命案链彻底断掉（桩做存活校验 ⇒ 直接不调）。

### 12.7 风险与取舍（必须先说清）

* **内存**：一插件一进程 = 一份 33 MB `node.dll` 映射 + 内核运行时；3 个插件同开多占几百 MB。可切 `MBKIT_SHARE=1` 换共享（用户已指出 node 支持共享调用）。
* **性能**：每次内核调用多一次「共享环投递 + 事件等待」。`wkeRepaintIfNeeded` 这类高频调用要留在**辅助进程内部**由自驱 tick 调，**绝不逐个编组**（否则 fps 崩）。⇒ 桩只编组「业务调用」，不编组「渲染心跳」。
* **文本编码**：客户端是 GBK 进程，内核 `*W` 系列要 UTF-16。编组时**只搬字节、不做转码**（`字节集` 本来就是 UTF-16 原始字节），保持与今天逐字节一致。
* **`wkeSetHandle` 语义变体**：辅助进程用离屏 hwnd，但客户端窗口的**尺寸/DPI**要同步过去；`wkeGetCaretRect` 之类的坐标要在客户端做换算。
* **未做就是不工作**：§12.2 之外的 API（JS 引擎的 `jsValue` 深度操作、下载回调、资源拦截）**跨进程后一律降级**，与 §7 的①②③分类一致。用之前先看 `MbKit_MissingList` / 诊断计数。

### 12.8 与摘钩补丁的关系（复核后仍然成立）

§8 的结论**不变**：摘钩补丁治「插件自己的钩子」，辅助进程治「内核归属」。实测已证实摘钩补丁这一侧有效
（§13），所以辅助进程是**为了**：① 换内核不重启宿主；② 内核崩溃/状态残留的可回收；③ 多插件抢内核。
