## 0. 结论速览（先看这个）

### 0.1 两条路线判定

| 路线 | 判定 | 一句话依据 |
|---|---|---|
| **④a 官方宿主化**（写 .fne/AddIn，被 e.exe 加载，用 `NES_RUN_FUNC` 驱动编译执行 + 监控输出） | **可（证据充分）** | 官方 SDK 完整定义了「库↔IDE」双向通知；e.exe 启动即加载 `lib\*.fne`（实测 77/77）；`NES_GET_MAIN_HWND`/`NES_RUN_FUNC`/`FN_COMPILE_AND_RUN`/`FN_OPEN_FILE2`/`FN_ADD_TAB` 全部存在 |
| **④b 外部 DLL 注入**（`CreateRemoteThread`/`SetWindowsHookEx`/`AppInit`） | **有条件可（技术上无门槛，但收益低）** | e.exe **无导出表**（注入后无官方函数可调）；但 **无 ASLR、无 DEP、无可疑反调试 API 导入**，注入本身容易。**相对 ④a 几乎没有不可替代价值**（见 §5） |

**推荐：走 ④a。** 官方接口把「打开工程→编译执行→结束执行」做成了现成功能号，无需逆向；且 e.exe 的空闲窗口/控件、输出面板都可由支持库在进程内直接拿到。

### 0.2 最关键的 6 条证据（全部已证实，非推断）

1. **库→系统 的通知指针怎么拿**：系统加载库时，用 `PFN_NOTIFY_LIB` 回调通知 `NL_SYS_NOTIFY_FUNCTION(=1)`，`dwParam1` 就是一个 `PFN_NOTIFY_SYS` 函数指针；库保存它，之后用它发 `NES_GET_MAIN_HWND`/`NES_RUN_FUNC`。证据：`sdk/cpp/elib/lib2.h:1173-1177`（定义）、`lib2.h:1242-1251`（typedef）、`sdk/cpp/elib/fnshare.cpp:26-55`（官方实现）、`sdk/cpp/samples/HtmlView/HtmlView.cpp:364-378`（官方示例）。
2. **功能号与参数怎么传**：`NES_RUN_FUNC` 的 `dwParam1`=功能号，`dwParam2`=`DWORD[2]`（参数1、参数2）指针；返回真=被处理。证据：`lib2.h:1019-1022`、`PublicIDEFunctions.h:5-6`。
3. **e.exe 启动即全量加载支持库**：实测 e.exe 启动（未开工程）时加载了 `lib\` 下 **77/77 个 `.fne`**（仅 `eTools.fne` 未加载）。⇒ **把自定义 .fne 放进 `lib\` 即可进入 IDE 进程，无需依赖某个工程**。证据：`re/mods_noproj.txt`、`re/compare.py`。
4. **e.exe 自己就是调试器**：导入 `WaitForDebugEvent`/`ContinueDebugEvent`/`SetThreadContext`/`WriteProcessMemory`；字符串含「开始运行被调试程序」「★ 被调试程序」「被调试易程序运行完毕」「DebugActiveProcessStop」。⇒ 调试运行由 IDE 用 **Windows 调试 API** 托管子进程。证据：`e.exe` 导入表、RVA `0x0025C9B4/0x0025EDD8/0x0025EE4C/0x002648FC`。
5. **调试输出的底层通道**：核心库运行版 `krnln.fnr` **导入 `KERNEL32!OutputDebugStringA`**（编辑器版 `krnln.fne` 同）。⇒ 「输出调试文本」最终走 `OutputDebugStringA` ⇒ 写 **DBWIN 缓冲区**（有监听者时）。**这为现有方案的 P0 假设（无 IDE 时 DBWIN 仍可收）提供了直接支持证据**（待活体探针最终确认）。证据：`re/probe_debug_io.py` 输出、`re/find_classes.py`。
6. **IDE 的编辑器/输出控件来自第三方插件 DLL**：`ScintillaForEIDETools` 类由 `lib\iDraw\superTools\plugin\eOutPutControl.dll` 注册，且该 DLL **已在启动时被加载进 e.exe**。⇒ 支持库/插件向 IDE 进程注入自定义窗口与代码是**官方支持的常规行为**。证据：`re/find_classes.py`、`re/mods_noproj.txt`。

### 0.3 对现有方案的直接影响

- 现有主路线（编译调试版 + DBWIN）**证据更硬了**（证据 5）：`krnln.fnr` 明确 import `OutputDebugStringA`，DBWIN 假设从「推断」升级为「有直接二进制证据支持，待活体验证」。
- 新路线 ④a 可行：可作为 P0 探针**失败时**的强兜底（因为它复用官方编译执行，且能在进程内直接读输出），也可独立成路。

## 2. 官方 SDK「在 IDE 进程内控制 IDE」接口链路

### 2.1 通知机制总览（已证实）

易语言支持库就是一个导出 **`GetNewInf`** 的 DLL（后缀 `.fne`）。证据：`sdk/cpp/docs.txt:73-81`（"此库中必须输出一个名为 GetNewInf 的函数"）、`sdk/cpp/elib/lib2.h:1363-1364`（`FUNCNAME_GET_LIB_INFO "GetNewInf"` / `PFN_GET_LIB_INFO`）、`sdk/cpp/samples/HtmlView/HtmlView.def:4-7`、`HtmlView.cpp:460-463`。

`GetNewInf` 返回 `PLIB_INFO`，其中 **`m_pfnNotify`（类型 `PFN_NOTIFY_LIB`）不能为空**（`lib2.h:1345`）。系统用它**回调库**；库则在收到特定通知后**拿到回给系统的函数指针**。四类通知码：

| 通知族 | 方向 | 谁处理 | 含义 |
|---|---|---|---|
| `NL_*` | 系统 → 库 | 库的 `m_pfnNotify` | 系统生命周期/请求（如 `NL_SYS_NOTIFY_FUNCTION`、`NL_IDE_READY`）|
| `NES_*` | 库 → 系统 | **仅易编辑环境（IDE）** | 取主窗口、运行功能号 |
| `NAS_*` | 库 → 系统 | IDE + 运行环境 | 取图标/路径/版本等 |
| `NRS_*` | 库 → 系统 | **仅易运行环境** | 运行时服务 |

**核心链路（这是打通 ④a 的钥匙）：**

```c
// 1) 系统在装载库前通知：把"通知系统用的函数指针"交给库
//    lib2.h:1173-1177
#define NL_SYS_NOTIFY_FUNCTION   1
//   dwParam1: (PFN_NOTIFY_SYS)

// 2) 库保存它 —— 官方 fnshare.cpp:26-46 / HtmlView.cpp:364-378
INT WINAPI ProcessNotifyLib (INT nMsg, DWORD dwParam1, DWORD dwParam2) {
    switch (nMsg) {
    case NL_SYS_NOTIFY_FUNCTION:
        g_fnNotifySys = (PFN_NOTIFY_SYS)dwParam1;   // ← 保存系统回调
        break;
    ...
    }
    return nRet;
}

// 3) 库用它发通知 —— 官方 fnshare.cpp:48-55
INT WINAPI NotifySys (INT nMsg, DWORD dwParam1, DWORD dwParam2) {
    if (g_fnNotifySys != NULL)
        return g_fnNotifySys (nMsg, dwParam1, dwParam2);
    return 0;
}

// 4) 于是"在 IDE 进程内控制 IDE"变成两行：
HWND hMain = (HWND) NotifySys (NES_GET_MAIN_HWND, 0, 0);          // 取主窗口 (lib2.h:1017)
DWORD params[2] = { 0, 0 };
BOOL ok = NotifySys (NES_RUN_FUNC, FN_COMPILE_AND_RUN, (DWORD)params);  // 编译执行 (lib2.h:1019-1022)
```

`PFN_NOTIFY_SYS` 原型：`INT (WINAPI *)(INT nMsg, DWORD dwParam1, DWORD dwParam2)`（`lib2.h:1244-1245`）。

### 2.2 逐问回答

#### Q1：支持库通过哪个结构/函数指针发起 `NES_GET_MAIN_HWND` 与 `NES_RUN_FUNC`？

**已证实**：通过系统在 `NL_SYS_NOTIFY_FUNCTION` 通知里下发的 **`PFN_NOTIFY_SYS` 函数指针**（库自行保存），调用它并以 `NES_GET_MAIN_HWND`/`NES_RUN_FUNC` 作为 `nMsg`。

- 定义：`lib2.h:1173-1177`、`1017`、`1019`
- 官方实现范例：`fnshare.cpp:9,26-55`（全局 `g_fnNotifySys`）、`HtmlView.cpp:50-56,369-370`
- 代码示例见 §2.1

> 注：`krnllib.h` 内**没有** `NES_*`（已核实，grep 无命中）；`NES_*` 只定义在 `lib2.h`。

#### Q2：`dwParam1`/`dwParam2` 怎么传？返回 BOOL 什么意思？

**已证实**（`lib2.h:1019-1022` + `PublicIDEFunctions.h:5-6`）：

| 形参 | 含义 |
|---|---|
| `nMsg` | `NES_RUN_FUNC (=2)` |
| `dwParam1` | **功能号**（`FN_xxx`，见功能表） |
| `dwParam2` | **双 DWORD 数组指针** `DWORD[2]`，`[0]`=功能参数1，`[1]`=功能参数2 |
| 返回值 | **真=该功能被 IDE 处理；假=未被处理** |

举例（`PublicIDEFunctions.h`）：
- `FN_COMPILE_AND_RUN = FNST_RUN|2`（:400）→ `params={0,0}`
- `FN_OPEN_FILE2 = FNST_FILE|8`（:332）→ `params[0]=(DWORD)文件名字符串指针`
- `FN_ADD_TAB = FNST_ADDIN|1`（:421）→ `params[0]=(DWORD)&ADD_TAB_INF`
- `FN_IS_FUNC_ENABLED = FNST_ADDIN|4`（:444）→ `params[0]=功能号; params[1]=(DWORD)BOOL*`

#### Q3：.fne 满足什么条件才会被 e.exe 加载？必须依赖「项目」吗？

**已证实 —— 不依赖项目**。

- **加载位置**：`<安装目录>\lib\`。证据：`docs.txt:3358-3359`、`3369-3371`（"直接将其拷贝到易语言安装目录的 lib 目录中"）、注册表 `HKCU\Software\FlySky\E\Install\Path = D:\ides\e\lib\`（`re/reg.txt`）。
- **加载时机**：**e.exe 启动即扫描并加载 lib 下全部 .fne**。实测启动（**未打开任何工程**）时模块表含 `lib\*.fne` 共 **77** 个（`re/mods_noproj.txt`；对比 `re/compare.py`：`lib/*.fne` 77 个，仅 `etools.fne` 未加载，另加载 `com.run`）。⇒ **只要把自定义 .fne 放进 `lib\`，它就在每一次 IDE 启动时进入进程，与是否有工程无关。**
- **「启用」的两层含义（需区分）**：
  1. **进程加载层**：e.exe 全量加载 lib 下 .fne（实测）。
  2. **项目引用层**：某个**工程**是否"使用"某库，记录在工程数据里；e2txt 文本格式导出为 `配置/支持库.config.json`（每项含 `Key/Guid/Name/Version/CmdCount`），由文本里的 `.支持库 <key>`（`docs/易语言文本格式规范.md:158,354`）经 `t2e` 消费生成。实测样例见 `…/.tmp/ctrl/配置/支持库.config.json`（krnln、spec 两项）。
- **`配置/支持库.config.json` 的作用域订正**：它是 **e2txt 工程文本**的工程级配置，**不是** e.exe 的加载清单；本报告未在 `D:\ides\e\` 下发现任何 `*.config.json`（`find` 无命中），e.exe 侧无此文件。
- **`LBS_IDE_PLUGIN`**：库要在 IDE 就绪时收到回调，需在 `LIB_INFO.m_dwState` 置 `LBS_IDE_PLUGIN (1<<8)`（`lib2.h:1310-1311`），否则收不到 `NL_IDE_READY`（`lib2.h:1193-1195`）。**建议我们的 AddIn 置此位。**
- **依赖的工程能力**：库能在 IDE 进程里被加载 ≠ 能编译运行一个程序——**编译执行需要一个已打开的当前程序**。可先由库调用 `NES_RUN_FUNC(FN_OPEN_FILE2, 路径)` 打开指定 .e（:332），再 `FN_COMPILE_AND_RUN`。

> **推断**：`lib\` 中 `etools.fne` 未加载，可能与库自检/版本不匹配有关，而非"白名单"。证书/"数字签名"仅在加载失败时用于报错（`e.exe` RVA `0x00261E5C`「不能载入支持库…数字签名为…」），未发现事前签名白名单（`推断`，证伪法：放一个空壳 .fne 进 lib 观察是否加载——见 PoC）。

#### Q5：「监控调试框」怎么落地？

先厘清**调试输出实际走哪条路**（这决定 §5 与现有方案）：

- **已证实**：e.exe 自身用 **Windows 调试 API** 托管"被调试程序"——导入 `WaitForDebugEvent`/`ContinueDebugEvent`/`SetThreadContext`/`GetThreadContext`/`WriteProcessMemory`/`ReadProcessMemory`；含字符串「开始运行被调试程序」(RVA `0x0025C9B4`)、「★ 被调试程序」(`0x0025EDD8`)、「被调试易程序运行完毕」(`0x0025EE4C`)、「DebugActiveProcessStop」(`0x002648FC`，动态导入)。
- **已证实**：调试文本底层是 `OutputDebugStringA`——`krnln.fnr`（运行版核心库）**导入 `KERNEL32!OutputDebugStringA`**。
- ⇒ **两条并存路径**：调试运行时，`OutputDebugStringA` 既产生 `OUTPUT_DEBUG_STRING_EVENT` 给**已附加的调试器（e.exe）**，又写入 **DBWIN 缓冲区**给任意 DBWIN 监听者。

据此评估 4 条「监控输出」手段：

| 手段 | 可行性 | 需要什么额外信息 | 说明 |
|---|---|---|---|
| **a. 子类化/挂钩输出面板窗口** | 可（`推断`） | 输出面板 HWND + 其控件类 | e.exe 已导入 `SetWindowLongA`/`CallWindowProcA`/`SetWindowsHookExA`，进程内可子类化/挂消息；但**面板类名需运行时确认**（见下） |
| **b. `FN_ADD_TAB` 挂自己的日志工作夹** | **可（官方）** | `ADD_TAB_INF{HWND,HICON,标题,提示}` | `PublicIDEFunctions.h:19-27,421`。**AI 可读日志出口的最佳落地**：给自己的 HWND 当容器，日志由我们完全掌控（写入文件/命名管道/共享内存） |
| **c. 拦截 IDE 接收调试输出的路径** | 可（`推断`） | 调试事件处理位置 / DBWIN | 两条子路：(i) hook `OutputDebugStringA`（IAT/inline）在**调试子进程里**截获；(ii) 在**无 IDE** 时用 DBWIN 监听。前者要处理跨进程/位宽 |
| **d. 直接读输出面板控件文本** | 有条件可（`推断`） | 输出面板控件类与取文本方式 | 若面板是 Scintilla（见下），用 `WM_GETTEXT` 拿不到全文，需走 Scintilla 消息（`SCI_GETTEXT`）或 `EM_GETLINE`。**依赖面板控件类型** |

**关于输出面板控件（重要线索）：**
- 启动时 e.exe 已加载第三方插件 DLL：`lib\iDraw\superTools\plugin\eOutPutControl.dll`（172KB）、`CodeView.dll`、`提示输出扩展.dll`、`SciLexer.dll` 等（`re/mods_noproj.txt`）。
- 字符串定位（`re/find_classes.py`）：`ScintillaForEIDETools` 这个**窗口类**由 **`eOutPutControl.dll`** 注册；`CodeView` 由 `lib\eTools\Plugin\CodeView.dll` 注册；`TipLwy` 由 `提示输出扩展.dll` 注册。
- 工程打开后，主框架子窗口里出现 `class='ScintillaForEIDETools'`（可见，`re/proj_out.txt`），说明 IDE 的文本编辑/输出控件是 **Scintilla 系**。
- ⇒ **推断**：「输出面板」大概率也是 `eOutPutControl.dll` 提供的 Scintilla 控件（类名 `ScintillaForEIDETools`）。**证伪/确认法见 PoC-2**（触发一次运行后 `EnumChildWindows` 做差集，定位新出现的、含 `输出` 标题或 Scintilla 类的窗口）。

> **注意**：未能用「发 F5」触发一次真实编译执行（`re/run_f5.py`：`GetMenu` 返回 0、post 的 F5 未被加速键处理，10s 内无子进程产生）。**这不是"不可行"，而是"未打通触发方式"**；官方路径应是让库调用 `NES_RUN_FUNC(FN_COMPILE_AND_RUN)`（PoC-2）。

#### Q6：`FN_ADD_TAB` 能给日志能力带来什么？

**可（官方）**，`PublicIDEFunctions.h:19-27,421`：

## 5. 路线判定与对比（任务 C）

### 5.1 对比表

| 维度 | ④a 官方宿主化（写 .fne/AddIn） | ④b 外部 DLL 注入 |
|---|---|---|
| **可行性** | **可** | **有条件可** |
| **接入方式** | 把 .fne 放进 `lib\`（工具→支持库配置可选），e.exe 启动即加载 | `CreateRemoteThread`/`SetWindowsHookEx`/`AppInit` |
| **能用的接口** | **官方**：`NES_GET_MAIN_HWND`、`NES_RUN_FUNC(FN_*)`（编译/运行/调试/打开文件/加页签…） | **无官方接口**；e.exe **无导出表**，须逆向定位内部函数或发窗口消息 |
| **驱动"编译执行"** | `NES_RUN_FUNC(FN_COMPILE_AND_RUN)` | 逆向出内部函数地址后调用，随版本易碎 |
| **监控调试输出** | ① `FN_ADD_TAB` 自建日志夹 ② 读输出面板(Scintilla) ③ 子类化面板 | 同左，但同样要先拿到 HWND/函数 |

| **进程内前置条件** | e.exe 必须加载该库（实测"放进 lib 即加载"） | 无（注入即得） |
| **e.exe 侧对抗** | 未见 | **未导入 `IsDebuggerPresent`/`CheckRemoteDebuggerPresent`/`NtQuery*`**；`DllCharacteristics=0`（无 ASLR/DEP）。**有**字符串「请不要对本程序进行跟踪调试!」(`0x002648C8`)，`推断`与加密狗/授权校验相关 |
| **证据** | §2、§3、§4 | §3.3、§3.4、§3.5 |

### 5.2 ④b 相对 ④a 还有不可替代价值吗？

**基本没有，理由如下（均已证实或标注推断）：**

1. **④b 想省掉的"安装足迹"在 ④a 里其实很轻**：e.exe 启动即加载 `lib\*.fne`（实测 77/77），**无需工程、几乎无需配置**即可让库进入进程。④b 省下的只是"往 lib 放一个文件"。
2. **④b 得不到任何官方能力**：e.exe **无导出表**，④b 必须逆向找内部函数，而 ④a 直接有 `FN_COMPILE_AND_RUN`/`FN_OPEN_FILE2`/`FN_ADD_TAB` 等**官方功能号**——功能覆盖 ④b 能做的全部，且稳定。
3. **反注入/完整性校验方面 ④b 没有优势**：e.exe **未导入任何反调试 API**，也未做签名校验阻断加载（`推断`；lib 全量加载已侧面支持）。反而 ④a 走的是**官方加载路径**，不触发任何"可疑注入"面。
4. **唯一可能的价值场景（`推断`）**：目标机器**禁止修改易语言安装目录**（只读介质/权限受限），此时投放 .fne 不可行，才轮到 ④b。**除此之外，④a 严格更优。**

> **结论**：优先实现 ④a；把 ④b 仅作为"无法写 lib 目录"的极端兜底，且明确标注高脆弱性。
