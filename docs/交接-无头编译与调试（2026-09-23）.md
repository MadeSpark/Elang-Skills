## 3. ⭐ 本轮（2026-09-23）新增了什么

### 3.1 无头运行（**本轮主要工作**）

**诉求原文**：「继续优化 fne，目前你做的『无头』不是真的无头，因为我能看见易语言窗口被启动了」。

**做了什么**：
1. 找到「看得见窗口」的**直接原因**：`elaunch.py` 两种模式都把 `ELANG_AI_HIDE` 写成 `"0"` ⇒ 隐藏**从未启用**。
2. 建立**逐像素判据**（`re/win_probe/probe_wfp.py`）：对照组 `--headless off` = 89.4% 屏幕 / 5551ms 持续可见；无头 = **0~164 抽样像素**（1 个采样 ≈ 15ms），下降约 4 个数量级。
3. 修了宿主库填充器**两个致命缺陷**（见 §4.4）。
4. 改成**三层叠加**的无头架构（见 §4.3）。

**当前状态**：`hide` 为默认档；**启动闪屏已消除**；**偶发残留未清零**（3 次里 1 次，残留 = 易语言「创建新项目」向导 `NewWindow`「新建：」+ `Static '创建新项目'`，rect `400,226,1290,776`）。**定性尚未完成**——判据 `[B]` 未屏蔽环境漂移，164 像素可能含桌面噪声。这是 §5 的头号未决项。

### 3.2 `--check`：只判对错、不出产物（编译即检查）

**诉求**：「只要通过了语法检测、要求用户选择编译输出路径时，就代表代码结构没有问题，这时直接取消编译即可」。**权威判据 = 保存框**：易语言编译第一阶段是整个工程的静态检查，只有全过了才会弹「请输入欲编译到的可执行文件名：」；脚本看到保存框就按 PID 收尾（**等于用户点「取消」**）。

```bash
python skills/elang-build/scripts/ecompile.py <工程> --check --json
# status: syntax-ok / 或 errors:["错误(10022): …"] / 或 failed + eExitCode
```

⚠️ **`--fast`（`FN_PRE_COMPILE`）不能当判据**：该功能号属 `FNST_MODIFY`（`0x0202xxxx`）家族，**只作用于「当前编辑窗口」**；我们 `e.exe <工程>` 打开却不激活代码窗口 ⇒ 几乎空转、`BOOL*` **恒为 TRUE**。硬对照：同一份坏源码 `--check` 判 `failed`（`eExitCode=0xC0000005`）而 `--check --fast` 判 `syntax-ok`。

⚠️ **两个检查器互补，缺一不可**：
- `echeck.py`（`elang-ai-coding`）抓**块结构崩坏 / 缺块尾 / 不存在的命令** —— **编译器对这些一律不报错**；
- 编译器抓**类型不匹配 10044 / 分支没返回 10022** —— **`echeck` 完全无感**。

闭环：`echeck → rtcheck → t2e → ecompile --check → 按需真编译`。

### 3.3 控制块注释铁律（上一轮的延续，已收口）

**`'` 必须写在最前面**（`' .如果真 (…)`），且**块首/块体/块尾每一行都要加**，缩进原样。

双重实证：用户权威样本 `测试.e` 全工程 `grep "\.'"` **命中 0 行**；往返实验（`re/cmt_test/probe_dotquote.py`）写 `.' 如果真 (真)` → `e2t` 读回 `' .' 如果真 (真) ' !!!无法识别`（整行连同块结构**静默失效**）。

⚠️ **三类错法编译器全都不报错**（照样弹保存框、照样出产物）：① 丢点 `' 如果真` → 退化成普通注释；② 裸块尾 `.如果真结束` → **提前关掉外层块**；③ 点在前 `.'` → `无法识别`。⇒ 块结构问题**只能靠 `echeck.py` 抓**。

## 4. 已钉死的技术事实（含证据路径，别信结论信证据）

### 4.1 无头路线：三条被判伪，一条有效

| 路线 | 结论 | 证据 |
|---|---|---|
| **独立 Windows 桌面**（`CreateDesktopW` + `STARTUPINFO.lpDesktop`） | ❌ **`e.exe` 0.04 秒自行退出**（拒绝在非交互桌面运行） | `re/win_probe/probe_desktop*.py` |
| 只 `SW_HIDE` | ⚠️ 只压得住主窗口 `ENewFrame`，其余照露 | `re/win_probe/probe_hide.py` |
| 只 `SetWindowPos(-32000)` | ⚠️ 易语言会**连位置一起恢复**（拉锯） | `probe_wfp.py` 抓到「守护动作后 35ms 窗口仍在 (400,226,1290,776)」 |
| **事件钩子 + 异步 + 透明斗篷** | ✅ **有效** | 见 §4.3 |

⚠️ **Python 坑**：`subprocess.STARTUPINFO` **不暴露 `lpDesktop`**（`si.lpDesktop = "X"` 只是给 Python 对象加了个没人读的属性，子进程仍在默认桌面）。要用独立桌面必须自己 ctypes 建 `STARTUPINFOA` 调 `CreateProcessW`。`wShowWindow` 是暴露的。

### 4.2 窗口与类名清单（实测）

| 类名 | 是什么 | 出现时刻 |
|---|---|---|
| `ENewFrame` | 易语言主窗口（标题「易语言-加密狗版」） | ≈3.7s |
| `shadow_window` | 全屏**透明**窗口（`IsWindowVisible=TRUE` 但**不画像素**） | ≈1.5s 起 |
| `Afx:400000:0:10003:0:0` | MFC 对话框（「创建新项目」外层） | ≈3.9s |
| `NewWindow` | 同上**内层**（标题「新建：」，内含 `Static '创建新项目'`） | ≈4.4s |
| `_EL_PicWnd` | 与 `Afx:` 同 rect 的图片窗口 | — |
| `#32770` | **编译保存框**（「请输入欲编译到的可执行文件名：」） | 编译触发后 |

⚠️ **`IsWindowVisible == TRUE` 不等于真的画了像素** —— 分层/透明窗口会**假阳性**（独立监视器报 `shadow_window` 535 次「露脸」，而逐像素差异为 **0**）。**判据以逐像素为准**。

### 4.3 有效的无头架构（三层叠加）

**① 事件驱动（宿主库）**：`SetWinEventHook(EVENT_OBJECT_CREATE / SHOW / LOCATIONCHANGE)`，只订阅**本进程**，回调里**当场处理**。

**② 独立兜底轮询线程**：3ms 周期，`THREAD_PRIORITY_TIME_CRITICAL`。**它必须独立**——`EnumWindows` 是唯一会让钩子「饿死」的操作（离场外钩子只有在线程处于取消息状态时才能投递）。

**③ 持久隐身（关键一步）**：
```cpp
SetWindowLongA(hWnd, GWL_EXSTYLE, ex | WS_EX_LAYERED | WS_EX_TRANSPARENT);
SetLayeredWindowAttributes(hWnd, 0, 0, LWA_ALPHA);   // alpha = 0
```
这是**窗口属性**，易语言改可见性/位置都动不了它 ⇒ 无论怎么重新显示都**画不出像素**。

**辅助**：宿主库调 `NtSetTimerResolution(5000, TRUE, &cur)` 把定时器精度提到 0.5ms（Windows 默认 15.6ms ⇒ `Sleep(1)` 实际睡 15.6ms）。

**四档策略**（`--headless {park,shide,hide,off}` / `--visible`）：

| mode | 行为 |
|---|---|
| `park` | 只移出屏幕、保持可见（兜底，任务栏会留按钮） |
| `shide` | 启动即 SW_HIDE 主窗口 + 其余移出屏幕 |
| **`hide`** | **默认**：隐藏 + 移出屏幕 + 披透明斗篷 |
| `off` | 显示窗口（调试用） |

### 4.4 两条「硬伤」——都是我们自己的 bug，不是易语言的

**① 阻塞式窗口 API 会饿死钩子**（最隐蔽的一条）
`ShowWindow` / `SetWindowPos` / `SetWindowLong` 都是**同步**的：向窗口所属线程发消息并**等它处理完**。易语言主线程一忙（加载工程 3 秒），我们就被卡 3 秒 ⇒ 钩子线程停止泵消息 ⇒ 事件积压被丢弃 ⇒ 目标窗口的 CREATE **永远收不到**。
**实测**：`poll iter=1 enumMs=2953`（单次枚举 3 秒）。
**修法**：一律用 `ShowWindowAsync` + `SWP_ASYNCWINDOWPOS`。

**② 填充器不能要求窗口可见，也不能只点一次**
- `FindCompileSaveDlgProc` 原来有 `!IsWindowVisible(hWnd)` 过滤 ⇒ 隐藏后**永远找不到保存框** ⇒ 模态框没人消 ⇒ `IdeRunFunc` **永不返回**（表现为「`FN_COMPILE_STATIC` 发出后卡死、300s 超时」）。我一度**误判**为「易语言编译链路依赖窗口可见」。
- 点击只用一次 `PostMessage(BM_CLICK)` ⇒ 隐藏状态下第一次点击被吞、标志位已置位、再没人重试 ⇒ 同样卡死。
**修法**：去掉可见性过滤；**只要对话框还在就重试**（300ms 限速）。修完后 trace 里出现**两次** `fill+confirm`（第二次才生效）——**重试救了它**。

### 4.5 `WINAPI` 是空宏（跨 DLL 调用约定地雷）

`src/addin/sdk_compat.h` 把 `WINAPI` **`#define` 成空宏**（还原 VC6 约定）。所以手写系统 API 的 `typedef` **必须显式写 `__stdcall`**：

```cpp
typedef LONG (__stdcall *PFN_NtSetTimerResolution)(ULONG, BOOLEAN, PULONG);   // ✅
typedef LONG (WINAPI    *PFN_NtSetTimerResolution)(ULONG, BOOLEAN, PULONG);   // ❌ WINAPI 是空宏 → __cdecl
```
漏了的后果：栈不平衡 12 字节，`-O2`（隐含 `-fomit-frame-pointer`）下局部变量读到垃圾——实测 `mode=2011551771`（= `0x77E5D81B`，一个**系统 DLL 地址**）。
**教训**：凡是从环境变量/线程参数读到的值「明显不合理」，先查调用约定。

### 4.6 判据方法论（**本轮最有复用价值的一条**）

- ⚠️ **只统计「本次新起的 pid」**，**不要按进程名匹配**。按 `e.exe` 匹配会把**用户自己开着的易语言**算进来 —— 实测屏幕上出现 13.7 秒的 `ENewFrame 'AILI·LIFE - …'`，看着像无头彻底失效，实际是别人的窗口。
- ⚠️ **全屏截屏比对会被用户桌面活动污染**（`re/win_probe/measure_visible.py` 连跑 3 次得出 26 / 3.7 万 / 2.4 万，其中还有一次 99.9% 网格被 mask 吞掉的**假通过**）⇒ 需要**双基线 mask**，或改用下面这条天然免疫的方法。
- ✅ **首选判据**：`WindowFromPoint` 问「这个屏幕点上是谁的窗口」+ 比对**真实屏幕像素**与运行前基线（`probe_wfp.py`）。网格 `--step 40` 时单次扫描 ≈9ms（≈110 次/秒），足以分辨 16ms 一帧。

### 6.0 对比实测结论（物证 `re/epk_q/`；用户提供的 2.19MB 大工程测试后已按约定删除，git 无痕）

**解包性能**（2.19MB 工程 ×3 轮）：

| 维度 | e2txt | e-packager v1.2.13 |
|---|---|---|
| 解包速度 | **0.62s**（3 轮极稳） | 1.44~1.67s（**2.4× 慢**） |
| 命令名解析 | **0 退化**（全可读） | ⚠️ **238 处 `_LibXXXCmd` 退化，且无警告**（AI 无法编辑） |
| 工程本体代码 | 全量 | 全量（264 子程序，两工具一致） |

**7 工程矩阵**（0.66~3.9MB）：e2txt 与 09-22 基线逐字节一致（萌尘框架 -13.33% 为基线既有行为，非回归）；e-packager 字节级完美往返（pack 以 `.native_source.bin` 副本为基底）但 src 文本退化 1~1525 处/工程（库定位弱：仅认 `.e` 旁 `lib\`，本机易语言注册表定位不生效）。

### 6.2 ⭐ 头号风险：**加壳机制可能失效**（必须先验证，否则全盘阻塞）

`mkcage.py` 是**纯「改文本」路线**，三步：
```
e2t  →  改 配置/支持库.config.json（追加库表记录）  →  t2e
```
而 **`配置/支持库.config.json` 是 e2txt 独有的**——MEMORY 里那条硬结论「加壳的**唯一**输入通道是 `配置/支持库.config.json`」就是围着它转的。

**e-packager 的 workspace 里没有这个明文文件**（实测 `re/epk_test/rt_ws/original_unpacked/`）：

```
e2txt 布局                      e-packager 布局
项目.etprj                      AGENTS.md  README.md  info.json
代码/代码.e.txt                  src/程序集1.txt  src/.常量.txt  src/.DLL声明.txt …
常量.e.txt                       project/_meta.json  project/.module.json
配置/支持库.config.json  ←★      project/.native_source.bin  ←★（二进制！）
                                 audio/ image/ tool/e-packager.exe
```

⇒ **库表被藏在 `project/.native_source.bin` 这个二进制里**（实测该文件 5,405 B，**恰好等于源 `.e` 的大小** ⇒ 它就是**源 `.e` 的字节副本**，`pack` 以它为基底打补丁）。

⭐ **这其实是好消息**：既然是 `.e` 的字节副本，**我们的加壳逻辑可以直接作用在它上面**——即 `mkcage` 可以退化成「直接改写 `project/.native_source.bin` 里那条库表记录」+ `pack`，**从而彻底不依赖 e2txt 的 `t2e`**。
（`mkcage` 在二进制层面已有能力：`verify_libsource*.py` 的受控实验证明我们能读改 `.e` 的库表记录 —— 格式是 `u16 条数 + Key\rGuid\rMajor\rMinor\rName(GBK)`，见 `re/diff_librec*.py`。）

**必须实测的三问**：
1. `unpack` 一个**已加壳**（含我们库表）的 `.e` → `pack` 回来，库表**还在吗**？
2. 直接改 `project/.native_source.bin` 的库表 → `pack` 出来的 `.e`，**IDE 能打开并自动加载我们的库吗**？
3. 若 1/2 都不行，退路 = **加壳仍走 e2txt，只把「编辑」换成 e-packager**（违背「免装 e2txt」目标，需向用户确认）。

### 7.2 ⭐ 它的实现 vs 我们的实现（逐项对照）

| 环节 | **AutoLinker 做法** | 我们做法 | 该不该抄 |
|---|---|---|---|
| 启动隐藏 | `CreateProcessW` + `STARTUPINFOW.STARTF_USESHOWWINDOW` + `wShowWindow=SW_HIDE`，**`dwCreationFlags = 0`**（不用 `CREATE_NO_WINDOW`） | 同样（`make_hidden_startupinfo()`）+ 额外轮询压制 | 已一致 |
| 移出屏幕 | **完全不用** `SetWindowPos` 移位置 | 用（`-32000`） | — |
| 关弹窗过滤 | 按**子进程 PID + 类名 `#32770` + `IsWindowVisible`** | 按标题 `请输入欲编译到` + 类名 `#32770` | ⭐ **按 pid 过滤更稳**，抄 |
| 关弹窗动作 | `PostMessage(WM_COMMAND, IDCANCEL)` **+** `PostMessage(WM_CLOSE)` | `PostMessage(BM_CLICK)` 点保存按钮 | ⭐ **`IDCANCEL`+`WM_CLOSE` 更通用**，抄 |
| 轮询 | **主线程 `WaitForSingleObject(hProcess, 200)` 循环**，每轮采一次弹窗；**无独立线程、不设优先级** | 独立线程 3ms + `TIME_CRITICAL` | 我们更激进，保留我们的 |
| ⭐ **参数传递** | **请求文件** `{e.exe目录}/AutoLinker/Log/headless_compile_request.json`（字段含 `enabled` / `launcher_pid` / `output_path` / `target` / `static_compile` / `hide_window` / `exit_after_compile` / `startup_timeout_seconds`），**三级来源合并：请求文件 → 环境变量（`AL_` / `AUTOLINKER_` 前缀）→ 命令行（`--autolinker-*`）** | **只用环境变量** | ⭐⭐ **重点参考** |
| 驱动编译 | `AIChatFeature::ExecutePublicTool("compile_with_output_path", …)`（公共工具总线） | 触发官方功能号 `FN_COMPILE_STATIC` 等 | 原理同源 |
| 产物判据 | `ok` **且** `output_file_exists` **且** **`output_file_modified_after_compile`（mtime 在编译后）** | 监视落盘（**不以旧产物判成功**） | ⭐ 他们的 mtime 三条件很干净，可对齐 |
| **对抗重新显示** | **完全没有**（主窗口靠启动时 `SW_HIDE` 一次；弹窗靠 200ms 重复枚举关闭） | 有（透明斗篷 + 钩子） | 我们更强 |
| 超时 | 两层：等 runtime ready + 等 eide info，各 `startupTimeoutSeconds`（默认 60 / 上限 600）；外层 `timeout+30` | 300s | 可参考分段 |
| 并发 | **本文件无调度器**；只 `atomic_bool` CAS 防重入 + `launcher_pid` 存活检测清理过期请求 | 单实例 | — |
| 退出码 | `0`成功 / `1`编译失败或产物未更新 / `2`请求错误 / `3`等 IDE 超时 / `4`工具调用失败 / `6`启动期有阻塞弹窗 | `status` 字段 + `eExitCode` | ⭐ 退出码表可对齐 |

### 7.3 ⭐⭐ 对我们**最有价值**的一条：**请求文件**

我们所有参数都走**环境变量**（`ELANG_AI_HIDE` / `ELANG_AI_TRACE` / `ELANG_AI_TASK` / `ELANG_AI_RUN` …）。而 AutoLinker 用**请求文件**，好处正中我们的痛点：

1. **宿主库加载前就能感知「我是无头」** —— 我们的残留窗口 `NewWindow`「新建：」出现在 **≈4.4s**，而宿主库 **≈3.6s** 才加载；但**真正的问题是「创建新项目向导」可能在更早**。若让 `e.exe` **命令行/文件**一启动就带无头标记（而不是等 fne 加载后读环境变量），就有机会在向导建立**之前**干预。
2. 字段可扩展（`launcher_pid` 存活检测 ⇒ **启动器崩了自动清理过期请求**，避免「下一次跑被上一次的残留请求污染」）。
3. 三级来源合并（文件 → 环境 → 命令行）**对自动化更友好**。

**具体建议**：给 `elang_addin.fne` 增加「请求文件」通道，路径放 `{易语言目录}/elang_ai/headless_request.json`（或与工程同目录），字段至少：
```json
{ "enabled": true, "launcher_pid": 12345, "hide_mode": "hide",
  "task": "check|compile|run", "output_path": "…", "result_path": "…",
  "startup_timeout_seconds": 120 }
```
并保留环境变量作为**兼容**（不要一次性切掉，`elaunch.py` / `ecompile.py` 都在用）。

### 7.4 另外两条**不要抄**的

- ❌ **别把 AutoLinker 当依赖**（三道闸门，§1）。
- ❌ **别照抄它「不做对抗」**：它只靠启动时 `SW_HIDE` 一次。我们实测过「易语言会把窗口重新显示回来」，所以**透明斗篷那层必须保留**。

## 10. 附带说明：几个易踩的认知陷阱

1. **`echeck` 绿 ≠ 能编译**：`echeck` 只管命令存在性/参数个数/块配对；类型错误（10044）、分支返回（10022）、块结构崩坏它**都看不到**。反之编译器**漏报块结构**。**两个都要跑**（§3.2）。
2. **`--fast` 的 `syntax-ok` 是假绿**（`FN_PRE_COMPILE` 恒 TRUE，§3.2）。
3. **`e2t` 回读多出 `, 数组` 不是污染**（`t2e` 产物原样交付即可）；**`efix.py apply` 不要用于交付物**（清 flags bit3 → IDE 打不开）。唯一判据 = **用户能否在 IDE 里打开并编译运行**。
4. **`IsWindowVisible == TRUE` ≠ 看得见**（透明窗口假阳性，§4.2）。
5. **`FN_COMPILE_STATIC` 卡死不是易语言的锅**（是我们填充器要求窗口可见 + 只点一次，§4.4）。
6. **`ENewFrame` 标题不是你工程的** ⇒ 可能是用户自己开着的易语言（按 pid 判，§4.6）。
7. **「大工程往返要降级」不成立**（7 工程 0.66~3.9 MB 实测零 `[错误]`，§6.4）；要防的是**依赖缺失**。
