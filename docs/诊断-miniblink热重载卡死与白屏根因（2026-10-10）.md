# miniblink 热重载「概率卡死 / 白屏」根因诊断与修复方案

- 日期：2026-10-10
- 对象：`AILI·LIFE.dll`（小栗子虚拟机宿主 + 内嵌 `miniblink.ec` 1.4.4）
- 结论：**这不是一个 bug，是两条互相独立的失败链**。之前所有「补丁 A/B/C」都只覆盖了第三条路（悬空钩子），
  所以「偶尔还是会犯」。

---

## 0. 一句话结论

| 症状 | 根因 | 概率来源 |
|---|---|---|
| **卡死**（宿主 UI 冻结，进程还活着、无 WER、日志断在半句） | **ntdll 加载器锁（Loader Lock）循环等待** | 重载窗口内能否同时撞上「插件 LoadLibrary / 线程池线程退出 / SetWindowsHookEx 同步 SendMessage」 |
| **白屏**（不卡死，浏览框空白） | **miniblink 内核是异步启动的，插件没等内核就绪就 `载入文件 ()`，载入请求被内核静默丢弃** | 内核启动耗时 vs 「绑定+载入」时机的赛跑 |

**决定性旁证**：白屏在**用户原版 DLL（零补丁）+ 全新启动的宿主 + 第一次初始化**上就已复现
⇒ 与热重载、与任何补丁都无关，是插件自身的启动时序问题。

---

## 1. 卡死：加载器锁死锁

### 1.1 现场（对活着的卡死宿主 pid 128668 做全线程栈采样，181 条线程）

| 线程 | 栈顶（EBP 帧链 + PE 导出名解析） | 在等什么 |
|---|---|---|
| **宿主 UI 线程 tid=88648**（Main 窗口属主，`SendMessageTimeout(WM_NULL)` 不响应） | `ZwWaitForSingleObject` ← `ntdll+0x44887` `[LdrLoadDll]` ← `KERNELBASE!LoadLibraryExW+0x153` ← `LoadLibraryExA` ← `LoadLibraryA+0x32` ← **插件映像 `+0x104801`** | **加载器锁** |
| 5 条正在退出的线程（4× `TpCallbackIndependent` 系统线程池回调退出、1× `combase!CoRegisterClassObject` → `FreeLibraryAndExitThread+0x35`） | `ZwWaitForSingleObject` ← `ntdll+0x398ED` `[LdrShutdownThread+0x10D]` ← `RtlExitUserThread` | **加载器锁** |
| 3 条宿主线程 | `NtUserMessageCall` ← **`USER32!SetWindowsHookExAW+0x2F8`** ← `USER32!SendMessageA+0x3D` ← `小栗子虚拟机.exe+0x1E2CB0 / 0x18A699 / 0x17CBB8` | 目标线程抽消息 |
| 插件自己的线程池 5 条 | `WaitForSingleObject` / `ZwRemoveIoCompletion` / `Sleep`（帧在插件映像内） | 仍未退出（未被 join） |

死锁时**没有任何 WER / Application Error 记录** ⇒ 不是崩溃，是纯死锁：进程活着，UI 永久冻结。

### 1.2 三条线为什么会撞在一起

1. **插件每次装载都要 `LoadLibraryA("MbKit144.dll")`。**
   `miniblink.ec` 的 `_确保宿主库已载入` 把句柄缓存在**模块程序集全局**里，而这个全局随插件 DLL 一起被卸载清零
   ⇒ 每次热重载，新实例必然重走一遍「释放内置 MbKit 到磁盘 → `LoadLibraryA`」。
2. **`LoadLibraryA` 必须持有加载器锁**；**线程退出时 `LdrShutdownThread` 也要加载器锁**
   （系统线程池线程空闲退出是常态操作，重载时间窗内几乎必然撞上）；
   **`SetWindowsHookEx` 内部会做同步 `SendMessage`**（等目标线程抽消息），并且要经加载器。
3. 三者交错 ⇒ 加载器锁循环等待，谁都不放 ⇒ UI 线程永久冻结。

### 1.3 放大因素 A：一次装载往同一线程上堆 340 个 WH_CBT 钩子

宿主 `main\data\热重载诊断.log` 实测（单个 136 s 装载窗口内）：

```
插件钩子拦截：映像 8A30000 大小 19173376，替换导入项 2 处
插件装了钩子：idHook=5 lpfn=8C075AD tid=16444 hhk=…   ×340   ← 全是 WH_CBT，同一 lpfn、同一目标线程
插件装了钩子：idHook=3 lpfn=8BA8B30 …                 ×2     ← WH_GETMESSAGE
插件装了钩子：idHook=3 lpfn=8AF0042 …                 ×1
```

- `lpfn = 0x08C075AD` 落在插件映像内（`base 0x08A30000 + 0x1D75AD`）。
- **同一个目标线程（tid=16444）的 CBT 钩子链被堆到 340 节** —— 这是失控的重复安装。
- 宿主 `插件卸载前摘钩子` 实测只成功 **0~1 个**（诊断：「摘掉 0~1 个，台账余 0 个」）
  ⇒ 这 340 条基本没摘掉，插件 DLL 被 `FreeLibrary` 之后它们全部指向已释放映像；
  下一次重载再堆 340 条 ⇒ 钩子链越滚越长，加载器锁的竞争窗口越来越大 ⇒ **卡死的概率随重载次数与运行时长上升**。

### 1.4 放大因素 B：宿主摘钩台账的压缩 bug

`宿主源码 窗口程序集_界面.form.e.txt : 5137 .子程序 插件卸载前摘钩子`

```
.如果 (lpfn ≥ 模块基址 且 lpfn ＜ 模块基址 ＋ 大小)
    .如果真 (UnhookWindowsHookEx (hhk))
        摘掉 ＝ 摘掉 ＋ 1
    .如果真结束
    RtlMoveMemory (…＋ 写位, 取变量数据地址 (lpfn), 4)      ' ← 命中项写了 lpfn，却既不推进 写位，也不写 hhk
.否则
    RtlMoveMemory (…＋ 写位 ＋ 4, 取变量数据地址 (hhk), 4)   ' ← 保留项只写 hhk，不写 lpfn
    写位 ＝ 写位 ＋ 8
.如果结束
```

⇒ 只要「命中项后面紧跟保留项」，保留项的 `lpfn` 槽就被前一个命中项的 `lpfn` 覆盖，**台账错位**，
后续按台账卸载会摘错/摘不掉。

### 1.5 卡死怎么修

| # | 位置 | 改法 | 说明 |
|---|---|---|---|
| 1 | 宿主 `钩子代理` | 对 `(idHook, lpfn, tid)` **去重**：已存在同样组合就不再重复 `SetWindowsHookEx` | 直接掐掉 340 节钩子链，从源头消除放大因素 |
| 2 | 宿主 `插件卸载前摘钩子` | 命中项：只 `Unhook`，不写；保留项：写 `lpfn + hhk` 且 `写位 += 8` | 修压缩 bug |
| 3 | 宿主 `FreePlugin` | 卸载前按台账**全量** Unhook（不限映像范围）；`FreeLibrary` 前再 `Sleep(100)`+复摘一次 | 减小卸载窗口内的竞争 |
| 4 | 宿主 `FreePlugin` | 把 `FreeLibrary` 挪到**专用线程**执行 | UI 线程即使被加载器锁扣住，界面至少还能响应（不会「整机僵死」） |
| 5 | 宿主 `插件映像立墓碑` | 启用（已写好、从未被调用）：卸载后把映像区间填 `ret` | 残留回调踩空时变无害返回，兜底 |

> 宿主修改需要重编 `小栗子虚拟机.exe`（源码 = 用户私有 `work_host`，仅在本机 `~/.dsh/hostsrc/host_patchv5_20261006` 保留副本，**不入库、不外发**）。

## 2. 白屏：内核异步启动 vs 载入抢跑

### 2.1 现场

失败那几轮的宿主日志尾巴**恒定**停在：

```
初始化miniblink
node内核设置成功              ← WKE设置node路径 成功
开始载入表情包管理页面：…      ← 到此为止
```

**没有** `[Console] [表情包管理]`、**没有** `[Web -> E] 控件=list,事件=refresh,值=page_ready`、
**没有** `页面文档已就绪`。成功那一轮则是完整走完这三步。

白屏态下：183 条线程里**没有任何一条栈上含 `MbKit144.dll` 或插件映像**；
主窗口 `SendMessageTimeout(WM_NULL)` **响应正常**；`shot_ratio = 0.000`（整块均匀纯色）。
⇒ **不是卡住，是「框架活着、帧是死的」**，与「不卡死，但浏览框也不显示内容」完全吻合。

`mb_veh_*.log` 不存在 ⇒ 从未调用过 `WKE安装崩溃探针`。

### 2.2 成因

`miniblink.ec` 自己的文档写得很明白：

> `WKE等待内核就绪`：等 miniblink 内核（node.dll）在常驻线程上启动完成。……
> 内核是**异步启动**的：`WKE初始化` / 首次创建浏览框**并不阻塞**，本命令用于在需要确定性的地方显式等一次。
>
> `WKE取等待统计`：内核编组等待期间抽掉的消息数 / 等待超时次数。
> ……后者 > 0 说明内核启动被别人挡住了。

而插件 `启动Web表情包管理`（`class/窗口程序集_Main.form.e.txt : 1344`）的流程是
`绑定 (句柄, 假)` → 注册 3 个回调 → `写到文件` → **`载入文件 (示例网页路径)`**，
**中间没有任何等待内核就绪的动作** ⇒ 载入请求在编组阶段被内核丢弃，页面根本不执行。

### 2.3 已实施的修复（插件侧，无需改 `.ec`）

补丁 `aili5`（= A/B/C 之上加 D/E/F，已 `t2e` 组包 → `ecompile` 出 `AILI·LIFE_hr5.dll`，18710528 B）：

- **D 诊断**：`[HR]` 前缀打点 —— 重载前 / 解绑后 / 绑定后 各打一次
  `WKE取内核启动状态` + `WKE取等待统计` + `WKE宿主自检`。
- **E 等内核就绪**：`绑定()` 之后 `内核就绪 ＝ WKE等待内核就绪 (20000)`。
- **F 载入确认 + 重建兜底**：`载入文件` 后轮询 `是否文档已就绪` 最多 12×350 ms；
  仍不就绪则 **`销毁 ()` → `处理事件 ()` → `绑定 ()` → 重注册回调 → `载入文件 ()`** 重建一次
  （实测：`重新载入 ()` **永远救不回来**，只有销毁重建才有效）。

## 3. 顺带确认的三件事

1. **不是我的补丁造成的。** 原版 DLL 同样卡死 / 白屏，且白屏出现在全新启动的第一次初始化上。
2. **`miniblink.ec` 的内部逻辑无法用文本方式修改**：
   `e2t` 回读的 `class/.static.e.txt` **标识符全部丢失**（只有 `()` 占位），
   插件内嵌的 `module/miniblink/**` 更只有**声明、没有函数体**（实现在 `.ec` 二进制块里）。
   ⇒ 想让「每次装载不再 `LoadLibrary`」，只能改宿主侧或走辅助进程，不能改模块文本。
3. **辅助进程架构是治本方案**：内核 + MbKit 搬出宿主进程后，
   宿主进程永不 `LoadLibrary`/`FreeLibrary` `node.dll`/`MbKit144.dll`（消灭加载器锁竞争），
   内核跨插件重载常驻（消灭白屏）。设计已落 `docs/方案-MbKit辅助进程架构（2026-10-02）.md`。
